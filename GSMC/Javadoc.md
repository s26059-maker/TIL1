## Javadoc

Javadoc은 **소스 코드에 쓴 주석을 읽어서 HTML 설명서를 자동으로 만들어주는 도구**다. JDK에 기본으로 들어있어서 자바가 깔려 있으면 그냥 쓸 수 있다.

**중요한 점**: HTML을 따로 만들 필요가 없다. 주석만 잘 써두면 문서는 명령어 한 줄로 나온다. 그리고 그 주석은 문서를 안 뽑아도 그냥 읽기 좋은 주석이다. 손해 볼 게 없는 구조.

## 주석 쓰는 법

Javadoc이 인식하는 주석은 별이 하나 더 붙은 `/**`로 시작한다.

```java
/**
 * 이건 Javadoc 주석
 */

/* 이건 그냥 일반 주석 (Javadoc이 무시함) */
```

여러 줄을 쓸 때는 각 줄 앞에 `*`를 붙이는 게 관례다. 앞의 `*`와 공백/탭은 자동으로 잘려나가고 뒤의 글자만 내용으로 인식된다.

```java
/**
 * 첫 줄
 * 둘째 줄
 */

// 위랑 아래는 Javadoc 입장에서 완전히 똑같다
/**
    첫 줄
    둘째 줄
 */
```

## 주석의 구조

주석 안은 **설명문**과 **태그 섹션** 두 덩어리로 나뉜다.

```java
/**
 * 사용자 정보를 담는 클래스다.      ← 여기부터
 * 여러 줄로 써도 된다.               ← 여기까지가 설명문
 *
 * @author 정성원                     ← 여기부터 태그 섹션
 * @version 1.0
 */
```

`@`로 시작하는 게 처음 나오는 순간부터 태그 섹션이다.

**중요한 점**: 두 가지를 조심해야 한다.

1. **태그 섹션이 시작된 뒤에는 다시 설명문을 쓸 수 없다.** 설명은 무조건 위쪽에 몰아 써야 한다.
2. **설명문은 HTML로 해석된다.** 그래서 엔터를 쳐도 실제 문서에서는 줄바꿈이 안 된다. 줄을 바꾸려면 `<br>`을 직접 써야 한다.

```java
/**
 * 첫 줄이다.<br>
 * 이제 진짜 줄바꿈된다.
 * <a href="https://example.com">링크도 된다</a>
 */
```

## 자주 쓰는 태그

| 태그 | 언제 쓰나 |
|---|---|
| `@param` | 매개변수 설명 |
| `@return` | 반환값 설명 |
| `@throws` / `@exception` | 발생 가능한 예외 설명 (둘은 이름만 다르고 동일) |
| `@author` | 작성자 |
| `@version` | 현재 버전 |
| `@since` | 이 기능이 **처음 추가된** 버전 |
| `@see` | 관련 항목 링크 (HTML의 `<a>` 같은 역할) |
| `@deprecated` | 이제 쓰지 말라는 표시 (나중에 사라질 수 있음) |
| `{@link}` | 문장 중간에 참조 링크 박기 |
| `{@linkplain}` | `{@link}`와 같은데 링크가 일반 텍스트로 보임 |
| `{@code}` | 예제 코드 넣기 |

### 블록 태그와 인라인 태그

- **블록 태그**: `@param`처럼 한 줄을 통째로 차지하는 태그. 줄 맨 앞에 온다.
- **인라인 태그**: `{@link}`처럼 `{}`로 감싸서 **문장 속에 끼워 넣는** 태그. 설명문 안이든 다른 블록 태그 설명 안이든 아무 데나 들어갈 수 있다.

```java
/**
 * 이름을 설정한다.
 * 값을 꺼낼 땐 {@link #getName()}을 참조.   ← 인라인
 *
 * @param name 이름                          ← 블록
 */
public void setName(String name) { }
```

`@version`과 `@since`가 헷갈리는데, `@version`은 "지금 버전", `@since`는 "이게 태어난 버전"이다. 스마트폰으로 치면 `@version`은 현재 OS 버전, `@since`는 그 기능이 처음 나온 OS 버전.

## 문서 생성하기

**터미널**

```bash
javadoc -d doc *.java
```

**VSCode** — 확장에서 `Javadoc Tools` 설치 → `F1` → `Javadoc Tools: Export Javadoc`

**Eclipse** — 프로젝트 우클릭 → Export → Java → Javadoc

### 옵션

| 옵션 | 역할 |
|---|---|
| `-d [경로]` | 문서가 생성될 폴더 지정 |
| `-author` | `@author` 내용을 문서에 출력 |
| `-version` | `@version` 내용을 문서에 출력 |

**중요한 점**: `-author`, `-version` 옵션을 안 주면 주석에 `@author`를 아무리 잘 써놨어도 **문서에 아예 안 나온다.** 태그만 쓰고 왜 안 나오지 하면서 헤매기 딱 좋은 부분.


## 실수하기 쉬운 것

**필드를 한 줄에 여러 개 선언할 때**

```java
/**
 * 폭과 높이를 나타낸다.
 */
int width, height;
```

이렇게 쓰면 Javadoc은 아래처럼 인식한다.

```java
/** 폭과 높이를 나타낸다. */
int width;
/** 폭과 높이를 나타낸다. */
int height;
```

같은 설명이 두 번 복사돼서 붙는다. 문서화할 필드는 한 줄에 하나씩 선언하는 게 안전하다.

**그 외**

- 엔터만 치고 `<br>` 안 써서 문서가 한 줄로 뭉개지는 경우
- 태그 섹션 뒤에 설명을 더 쓰는 경우 (무시되거나 이상하게 나옴)
- `<`, `>`, `&` 같은 문자를 그냥 쓰면 HTML 태그로 먹혀버림 → `&lt;`, `&gt;`, `&amp;`로 쓰거나 `{@code}` 안에 넣기



## 언제 쓰면 좋은가 (내 생각)

Javadoc은 **모든 코드에 다 붙이는 게 아니라, 남이 쓸 코드에 붙이는 것**이다.

- **꼭 쓰면 좋은 곳**: 공통 유틸 클래스, 팀원이 호출할 서비스 메서드, 라이브러리/공개 API, 예외를 던지는 메서드
- **굳이 안 써도 되는 곳**: 게터/세터, 이름만 봐도 뻔한 private 메서드, DTO 필드

Spring Boot 프로젝트로 치면 컨트롤러는 Swagger가 API 문서를 담당하니까 Javadoc이 덜 필요하고, 오히려 **서비스 계층의 복잡한 비즈니스 로직 메서드**에 붙였을 때 값어치가 크다. "이 메서드가 어떤 조건에서 예외를 던지는지"는 코드만 봐서는 한참 읽어야 알 수 있는데, `@throws` 한 줄이면 IDE 툴팁에 바로 뜬다.

**중요한 점**: Javadoc의 진짜 이득은 HTML 문서가 아니라 **IDE 자동완성 툴팁**이다. IntelliJ에서 메서드에 커서 올리면 Javadoc 내용이 그대로 뜬다. 문서를 한 번도 안 뽑아도, 팀원이 내 메서드를 쓸 때마다 설명이 따라다닌다. 이게 사실상 Javadoc을 쓰는 가장 현실적인 이유다.

그리고 주석 유지보수는 코드 유지보수만큼 중요하다. **틀린 주석은 없는 주석보다 나쁘다.** 메서드 시그니처를 바꿨으면 `@param`도 같이 고쳐야 한다. 안 고칠 거면 처음부터 안 쓰는 게 낫다.
