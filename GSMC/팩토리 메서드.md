# 팩토리 메서드 패턴

## 정의

객체를 만드는 일(`new`)을 **공장(Factory) 클래스에 맡기고**, 어떤 객체를 만들지는 **자식 공장 클래스가 결정**하게 하는 생성 패턴이다.

## 왜 필요한가

선박 객체를 만드는 코드를 생각해보자. 제일 단순하게 짜면 이렇게 된다.

```java
public static Ship orderShip(String name) {
    Ship ship = new Ship();

    if (name.equals("ContainerShip")) {
        ship.capacity = "20t";
        ship.color = "green";
    } else if (name.equals("OilTankerShip")) {
        ship.capacity = "15t";
        ship.color = "blue";
    }
    // 배 종류 늘어날 때마다 여기가 계속 늘어남...
    return ship;
}
```

문제가 두 개다.

1. 배 종류가 하나 늘 때마다 `if` 분기가 계속 붙는다.
2. `Ship` 클래스 구조가 바뀌면 이 메서드를 통째로 고쳐야 한다.

## 구조

등장인물은 딱 4명이다.

| 이름 | 역할 |
|---|---|
| **Product** | 제품의 인터페이스 (예: `Ship`) |
| **ConcreteProduct** | 실제 제품 구현체 (예: `ContainerShip`) |
| **Creator** | 최상위 공장. 팩토리 메서드를 추상 메서드로 선언 |
| **ConcreteCreator** | 실제 공장. 팩토리 메서드를 재정의해서 자기 제품을 반환 |

Creator 안에는 메서드가 두 종류 들어간다.

- **팩토리 메서드** (`createShip()`): 객체를 만드는 추상 메서드. 자식이 구현한다.
- **템플릿 메서드** (`orderShip()`): 만들기 전후 처리(검증, 메일 발송 등)를 묶어놓은 공통 메서드. `final`로 막아서 자식이 못 건드리게 한다.

## 코드로 보기

### 1단계 — 제품

```java
class Ship {
    String name, color, capacity;
}

class ContainerShip extends Ship {
    ContainerShip(String name, String capacity, String color) {
        this.name = name;
        this.capacity = capacity;
        this.color = color;
    }
}

class OilTankerShip extends Ship {
    OilTankerShip(String name, String capacity, String color) {
        this.name = name;
        this.capacity = capacity;
        this.color = color;
    }
}
```

### 2단계 — 공장

```java
abstract class ShipFactory {

    // 공통 로직 (전처리 → 생성 → 후처리), final이라 자식이 못 바꿈
    final Ship orderShip(String email) {
        validate(email);
        Ship ship = createShip();   // ← 실제 생성은 자식에게 위임
        sendEmailTo(email, ship);
        return ship;
    }

    // 팩토리 메서드 : 여기가 핵심
    abstract protected Ship createShip();

    private void validate(String email) {
        if (email == null) throw new IllegalArgumentException("이메일을 남겨주세요");
    }

    private void sendEmailTo(String email, Ship ship) {
        System.out.println(ship.name + " 다 만들었다고 " + email + "로 메일 보냄");
    }
}

class ContainerShipFactory extends ShipFactory {
    @Override
    protected Ship createShip() {
        return new ContainerShip("ContainerShip", "20t", "green");
    }
}

class OilTankerShipFactory extends ShipFactory {
    @Override
    protected Ship createShip() {
        return new OilTankerShip("OilTankerShip", "15t", "blue");
    }
}
```

### 3단계 — 사용

```java
Ship containerShip = new ContainerShipFactory().orderShip("inpa@naver.com");
Ship oilTankerShip = new OilTankerShipFactory().orderShip("inpa@naver.com");
```

**중요한 점**: `if` 분기가 완전히 사라졌다. 문자열로 종류를 넘기는 게 아니라, **어떤 공장을 고르냐**로 종류가 결정된다.

### 확장할 때

전함(BattleShip)을 추가한다고 하면, 기존 코드는 **한 줄도 안 고치고** 클래스 두 개만 추가하면 끝난다.

```java
class BattleShip extends Ship {
    BattleShip(String name, String capacity, String color) { ... }
}

class BattleShipFactory extends ShipFactory {
    @Override
    protected Ship createShip() {
        return new BattleShip("BattleShip", "10t", "black");
    }
}
```

## 장점과 단점

**장점**

- 클라이언트가 구체적인 제품 클래스를 몰라도 된다 (결합도 down)
- 객체 생성 후 공통으로 할 일(검증, 로깅 등)을 한 곳에 모을 수 있다
- **단일 책임 원칙(SRP)**: 생성 코드가 한 곳에 모여서 유지보수가 쉽다
- **개방/폐쇄 원칙(OCP)**: 기존 코드 수정 없이 새 제품 추가 가능 (확장엔 열리고 수정엔 닫힘)

**단점**

- 제품 하나당 공장 하나씩 필요해서 **클래스 수가 폭발**한다
- 그만큼 코드가 복잡해진다

## 비슷한 패턴과 비교

### vs 추상 팩토리 (Abstract Factory)

추상 팩토리가 한 단계 더 추상화된 상위 버전이다.

| | 팩토리 메서드 | 추상 팩토리 |
|---|---|---|
| 목적 | 생성 과정을 자식 클래스로 넘기기 | 서로 연관된 **제품군**을 통째로 만들기 |
| 범위 | 한 공장 = 한 종류 제품 | 한 공장 = 여러 종류 제품 세트 |
| 초점 | 메서드 레벨 | 클래스(공장) 레벨 |

### vs 템플릿 메서드 (Template Method)

이름이 비슷하지만 템플릿 메서드는 **행동 패턴**, 팩토리 메서드는 **생성 패턴**이라 아예 다른 분류다.

다만 클래스 구조는 똑같다. 부모가 뼈대를 잡고 자식이 알맹이를 채우는 방식인데,

- 그 알맹이가 **실행할 알고리즘**이면 → 템플릿 메서드
- 그 알맹이가 **객체 생성**이면 → 팩토리 메서드

## 변형 패턴

클래스 폭발이라는 단점을 보완한 변형들이 있다.

- **Enum Factory Method** — 공장을 클래스 대신 `enum`으로 구성
- **Dynamic Factory** — Reflection API로 동적 생성해서 서브 클래스 폭발을 막음
