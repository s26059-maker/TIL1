## 단위 테스트

단위 테스트(Unit Test)는 클래스나 메서드 **하나만** 떼어놓고 잘 동작하는지 확인하는 테스트다.

문제는 Spring에서는 클래스가 혼자 못 산다는 것. Controller는 Service를 쓰고, Service는 Repository를 쓴다. 이걸 **의존성(dependency)** 이라고 하는데, Controller 하나 테스트하려고 DB까지 다 켜야 한다면 그건 이미 단위 테스트가 아니다.

## Mockito

Mockito는 이 "가짜 객체"를 만들어주는 라이브러리다. 진짜처럼 생겼지만 속은 비어 있고, 내가 시키는 대로만 대답한다.

**중요한 점**: Mockito가 필요 없으면 안 쓰는 게 제일 좋다. 의존성이 없는 순수한 클래스는 그냥 `new` 해서 테스트하는 게 훨씬 빠르고 깔끔하다.

## @Mock, @Spy, @InjectMocks

| 어노테이션 | 하는 일 |
|---|---|
| `@Mock` | 완전 가짜 객체 생성. 모든 메서드가 껍데기 (null, 0, 빈 리스트 반환) |
| `@Spy` | 반쪽 가짜. 내가 지정(Stub)한 메서드만 가짜고, 나머지는 **진짜 코드가 실행됨** |
| `@InjectMocks` | 위에서 만든 가짜들을 자동으로 꽂아 넣을 **테스트 대상** |

```java
@ExtendWith(MockitoExtension.class)
class UserControllerTest {

    @InjectMocks                      // 테스트 대상 (진짜)
    private UserController userController;

    @Mock                             // 여기에 주입될 가짜
    private UserService userService;
}
```

`@Spy`는 언제 쓰나? 비밀번호 암호화(`BCryptPasswordEncoder`)처럼 **실제로 동작해야 의미가 있는** 객체일 때 쓴다. 가짜로 만들면 암호화 결과가 null이라 검증이 불가능하다.

## Stub

Stub은 가짜 객체에게 "이거 물어보면 이렇게 대답해" 하고 대본을 쥐여주는 것이다.

```java
doReturn(response).when(userService).signUp(any(SignUpRequest.class));
// "userService.signUp()이 호출되면 response를 리턴해라"
```

| 메서드 | 상황 |
|---|---|
| `doReturn()` | 특정 값을 반환해야 할 때 |
| `doNothing()` | 반환값이 없을 때 (void) |
| `doThrow()` | 예외를 던져야 할 때 (실패 테스트용) |

**중요한 점**: `when(...).thenReturn(...)` 형태도 있는데 결과는 같다. 다만 `@Spy` 객체에 `when().thenReturn()`을 쓰면 **진짜 메서드가 한 번 실행되고 나서** 값이 덮어써진다. `doReturn().when()`은 실행 자체를 안 한다. 그래서 헷갈리기 싫으면 `doReturn()` 스타일로 통일하는 걸 추천한다.

`any()`는 "이 타입이면 뭐가 오든 상관없다"는 뜻이다. HTTP 요청은 Spring 내부에서 JSON → 객체로 변환되기 때문에 내가 만든 객체와 **주소값이 다르다**. 그래서 `any(SignUpRequest.class)`처럼 타입만 지정해준다.

## given-when-then

테스트 코드의 표준 구조다. 주석으로 구분만 해줘도 가독성이 확 오른다.

```java
// given  : 준비 (데이터 만들고, Stub 걸고)
// when   : 실행 (테스트할 메서드 호출)
// then   : 검증 (결과가 기대와 같은가?)
```

**중요한 점**: 테스트 하나에 검증 대상은 하나여야 한다. 한 테스트에 이것저것 다 넣으면 실패했을 때 뭐가 문제인지 모른다.

## JUnit5와 결합

Mockito도 독립된 프레임워크라서 JUnit과 연결해줘야 한다.

- JUnit4: `@RunWith(MockitoJUnitRunner.class)`
- **JUnit5 (현재 표준)**: `@ExtendWith(MockitoExtension.class)`

Spring Boot 2.2.0부터 JUnit5가 기본이므로 `@ExtendWith`를 쓰면 된다.


## 컨트롤러 테스트

컨트롤러는 HTTP 요청을 받아야 의미가 있다. 그런데 테스트 코드에서 진짜 서버를 띄우고 요청을 보낼 순 없으니, Spring이 주는 **MockMvc**를 쓴다. HTTP 요청을 흉내 내주는 도구다.

```java
@ExtendWith(MockitoExtension.class)
class UserControllerTest {

    @InjectMocks private UserController userController;
    @Mock private UserService userService;

    private MockMvc mockMvc;

    @BeforeEach
    void init() {
        mockMvc = MockMvcBuilders.standaloneSetup(userController).build();
    }

    @DisplayName("회원 가입 성공")
    @Test
    void signUpSuccess() throws Exception {
        // given
        SignUpRequest request = signUpRequest();
        doReturn(userResponse()).when(userService)
                .signUp(any(SignUpRequest.class));

        // when
        ResultActions resultActions = mockMvc.perform(
                MockMvcRequestBuilders.post("/users/signUp")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(new ObjectMapper().writeValueAsString(request))
        );

        // then
        resultActions
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.email").value("test@test.test"))
                .andExpect(jsonPath("$.role").value("ROLE_USER"));
    }
}
```

객체를 그대로 못 보내니 JSON 문자열로 바꿔서 보낸다. Gson을 써도 되지만 Spring이 이미 쓰고 있는 **Jackson(ObjectMapper)** 을 쓰는 게 의존성 추가도 없고 자연스럽다.

**중요한 점**: 참고 글에는 `status().isOk()`로 되어 있는데, 컨트롤러가 `HttpStatus.CREATED`를 반환하면 **201**이므로 `isCreated()`가 맞다. 상태 코드 검증은 컨트롤러 테스트의 핵심이니 실제 반환값과 꼭 맞춰야 한다.

**중요한 점**: `jsonPath`는 `jsonPath("$.email").value(기댓값)` 형태로 쓴다. `exists()`는 "값이 존재하냐"만 보기 때문에 값이 틀려도 통과한다. 값까지 검증하려면 `value()`를 써야 한다.

## @WebMvcTest

MockMvc를 매번 손으로 만드는 게 귀찮다면 이걸 쓴다.

```java
@WebMvcTest(UserController.class)
class UserControllerTest {

    @MockitoBean                 // Spring Boot 3.4+ (이전엔 @MockBean)
    private UserService userService;

    @Autowired
    private MockMvc mockMvc;
}
```

MockMvc가 자동 생성되고, `@ControllerAdvice`(예외 처리), Filter, Interceptor까지 빈으로 등록해준다. 즉 **웹 계층 전체가 진짜처럼 돌아간다**. 예외 처리나 필터까지 검증하고 싶다면 이 방식이어야 한다.

**중요한 점**: `@Mock`/`@Spy` 대신 `@MockitoBean`/`@MockitoSpyBean`을 써야 한다. Spring 컨테이너에 등록된 빈을 바꿔치기하는 개념이라 어노테이션이 다르다. (Spring Boot 3.4부터 `@MockBean`은 deprecated되고 `@MockitoBean`으로 바뀌었다.)

**중요한 점**: 대신 느리다. Spring은 테스트 환경이 같으면 컨텍스트를 캐싱해서 재사용하는데, `@WebMvcTest`는 컨트롤러마다 다른 환경이라 매번 새 컨텍스트를 만든다. 테스트가 수백 개가 되면 체감이 크다.

## 서비스 테스트

서비스는 비즈니스 로직이 들어있는 곳이라 **가장 테스트 가치가 높은 계층**이다. Repository만 가짜로 바꿔치기하면 된다.

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @InjectMocks private UserService userService;
    @Mock private UserRepository userRepository;
    @Spy private BCryptPasswordEncoder passwordEncoder;   // 진짜 암호화 필요

    @DisplayName("회원 가입")
    @Test
    void signUp() {
        // given
        SignUpRequest request = signUpRequest();
        doReturn(new User(request.getEmail(), "encrypted", UserRole.ROLE_USER))
                .when(userRepository).save(any(User.class));

        // when
        UserResponse user = userService.signUp(request);

        // then
        assertThat(user.getEmail()).isEqualTo(request.getEmail());

        // verify
        verify(userRepository, times(1)).save(any(User.class));
        verify(passwordEncoder, times(1)).encode(any(String.class));
    }
}
```

## verify

`verify()`는 **결과가 아니라 과정**을 검증한다. "그 메서드가 정말 호출됐는가? 몇 번 호출됐는가?"

```java
verify(userRepository, times(1)).save(any(User.class));
verify(userRepository, never()).delete(any(User.class));
```

> 비유: 요리 결과물(맛)을 보는 게 `assertThat`이라면, 요리사가 소금을 정말 한 번만 넣었는지 CCTV로 확인하는 게 `verify`다.

**중요한 점**: 반환값이 없는(void) 메서드나, "중복 저장이 안 일어났는지" 같은 걸 확인할 때 유용하다. 단, 남발하면 내부 구현이 조금만 바뀌어도 테스트가 깨진다. 정말 중요한 호출에만 쓰자.

## 레포지토리 테스트

Repository는 가짜로 만들면 **의미가 없다**. JPA가 쿼리를 제대로 만드는지 확인하는 게 목적인데, 그걸 가짜로 대체하면 아무것도 검증하지 않는 셈이다. 그래서 여기만큼은 진짜 DB와 통신한다.

```java
@DataJpaTest
class UserRepositoryTest {

    @Autowired
    private UserRepository userRepository;

    @DisplayName("사용자 추가")
    @Test
    void addUser() {
        // given
        User user = User.builder()
                .email("email").pw("pw").role(UserRole.ROLE_USER).build();

        // when
        User savedUser = userRepository.save(user);

        // then
        assertThat(savedUser.getEmail()).isEqualTo(user.getEmail());
    }
}
```

`@DataJpaTest`는 메모리에서 돌아가는 가벼운 DB(H2)를 자동으로 띄우고, 테스트가 끝나면 **트랜잭션을 롤백**해준다. 즉 테스트 데이터가 남지 않아서 몇 번을 돌려도 결과가 같다.

**중요한 점**: H2와 실제 MySQL은 문법이 조금 다르다. 네이티브 쿼리를 쓰거나 MySQL 전용 함수를 쓴다면 H2에서는 통과하고 운영에서 터질 수 있다. 이 경우엔 Testcontainers로 진짜 MySQL을 띄워서 테스트하는 방법이 있다.

## 실패 테스트

가장 자주 놓치는 부분이다. 성공 케이스만 짜면 "잘 될 때 잘 되는 것"만 확인한 것이다. 진짜 버그는 **예외 상황**에서 나온다.

```java
@DisplayName("중복 이메일 회원가입 실패")
@Test
void signUpFail() {
    // given
    doReturn(Optional.of(user())).when(userRepository)
            .findByEmail(any(String.class));

    // when & then
    assertThatThrownBy(() -> userService.signUp(signUpRequest()))
            .isInstanceOf(DuplicateEmailException.class);
}
```

이메일 중복, 존재하지 않는 ID 조회, 권한 없는 접근 — 이런 것들을 반드시 같이 짜야 한다.

## TDD

TDD(Test-Driven Development)는 **테스트 코드를 먼저 쓰고, 그걸 통과시키는 실제 코드를 나중에 쓰는** 방식이다.

`실패하는 테스트 작성 → 통과할 만큼만 구현 → 리팩터링` 을 반복한다.
