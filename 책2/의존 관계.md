# 의존 관계

## 의존 관계 예

A가 B를 알아야 동작한다면 **A는 B에 의존한다**고 말한다. 의존은 나쁜 게 아니라 **불가피한 것**이고, 문제는 항상 "얼마나 강하게, 어느 방향으로 의존하는가"다.

의존은 생각보다 다양한 형태로 생긴다.

```kotlin
// 1) 필드로 갖고 있음 — 가장 흔한 의존
class OrderService(private val paymentClient: PaymentClient)

// 2) 인수로 받음
fun createOrder(user: User, items: List<Item>)

// 3) 반환 타입
fun findOrder(id: Long): Order

// 4) 상속 — 가장 강한 의존 중 하나
class AdminUser : User()

// 5) 함수 안에서 직접 생성
fun send() {
    val client = TossPaymentClient()   // 여기서 의존이 생김
}

// 6) 전역 상태 참조
fun now(): LocalDateTime = SystemClock.current   // 보이지 않는 의존
```

의존이 많아지면 이런 일이 생긴다.

- B를 고치면 A도 같이 터진다 (**변경의 파급**)
- A를 테스트하려면 B도 같이 띄워야 한다 (**테스트 곤란**)
- A만 떼어 다른 곳에 쓸 수 없다 (**재사용 불가**)

## 의존의 강도: 결합도

**결합도(coupling)** 는 의존의 세기다. 강할수록 떼어내기 어렵다. 아래로 갈수록 약해지고, **약할수록 좋다.**

| 강도 | 이름 | 한 줄 요약 |
|---|---|---|
| 최악 | 내용 결합 | 남의 속을 직접 헤집음 |
| ↑ | 공통 결합 | 전역 변수를 같이 씀 |
| | 외부 결합 | 외부 포맷·프로토콜에 묶임 |
| | 제어 결합 | 플래그로 남의 동작을 조종함 |
| | 스탬프 결합 | 필요 없는 것까지 통째로 넘김 |
| ↓ | 데이터 결합 | 딱 필요한 값만 넘김 |
| 최선 | 메시지 결합 | 알릴 뿐, 아무것도 안 넘김 |

### 내용 결합

**다른 모듈의 내부 구현을 직접 만지는 것.** 남의 집 벽을 뚫고 들어가는 수준이라 가장 나쁘다.

```kotlin
// 나쁨 — 내부 리스트를 직접 꺼내 조작
class Cart {
    val items = mutableListOf<Item>()   // 그대로 노출
}

fun addItem(cart: Cart, item: Item) {
    cart.items.add(item)                // Cart의 규칙을 무시하고 직접 변경
    cart.items.sortBy { it.price }      // 정렬 순서까지 밖에서 결정
}

// 좋음 — 정해진 창구로만
class Cart {
    private val _items = mutableListOf<Item>()
    val items: List<Item> get() = _items.toList()

    fun add(item: Item) {
        require(_items.size < MAX_ITEM_COUNT) { "담을 수 있는 개수를 초과했습니다" }
        _items += item
    }
}
```

리플렉션으로 private을 뚫는 것도 내용 결합이다.

```kotlin
// 나쁨 — 필드명 바뀌면 런타임에 터짐
val field = user::class.java.getDeclaredField("password")
field.isAccessible = true
```

### 공통 결합

**여러 모듈이 같은 전역 상태를 공유하는 것.** 누가 언제 바꿨는지 추적이 안 된다.

```kotlin
// 나쁨 — 어디서든 바꿀 수 있는 전역 상태
object Session {
    var currentUserId: Long? = null
    var isAdmin: Boolean = false
}

class OrderService {
    fun createOrder() {
        val userId = Session.currentUserId!!   // 언제 세팅됐는지 알 수 없음
    }
}

// 좋음 — 필요한 값을 명시적으로 전달
class OrderService {
    fun createOrder(userId: Long) { ... }
}
```

### 외부 결합

**외부 시스템의 데이터 포맷이나 프로토콜에 코드가 직접 묶이는 것.** 외부가 바뀌면 내부가 통째로 흔들린다.

```kotlin
// 나쁨 — 외부 API 응답 구조가 도메인까지 침투
class OrderService(private val client: TossApiClient) {
    fun pay(order: Order) {
        val response = client.request(order)
        if (response.resultCode == "0000") {      // 토스 규격이 도메인에 노출
            order.status = OrderStatus.PAID
        }
    }
}

// 좋음 — 경계에서 우리 언어로 번역(Anti-Corruption Layer)
interface PaymentClient {
    fun pay(amount: Int): PaymentResult          // 우리 도메인 타입
}

class TossPaymentClient(...) : PaymentClient {
    override fun pay(amount: Int): PaymentResult {
        val response = api.request(amount)
        return if (response.resultCode == "0000") PaymentResult.Success
               else PaymentResult.Failure(response.message)
    }
}
```

### 제어 결합

**플래그 인수로 상대의 동작을 조종하는 것.** 호출자가 상대 내부 로직을 알아야 하므로 결합이 생긴다.

```kotlin
// 나쁨 — true가 뭔지 호출부만 봐선 모름. 내부에 if가 생김
fun save(user: User, sendMail: Boolean) {
    repository.save(user)
    if (sendMail) mailSender.send(user.email)
}
save(user, true)
save(user, false)

// 좋음 — 하는 일이 다르면 함수를 나눈다
fun save(user: User) { repository.save(user) }
fun saveAndNotify(user: User) {
    save(user)
    mailSender.send(user.email)
}
```

분기가 정말 필요하면 **boolean 대신 enum**을 쓴다. 호출부에서 의미가 읽히기 때문이다.

```kotlin
// 그나마 나음
enum class SortOrder { ASC, DESC }
fun findOrders(sort: SortOrder): List<Order>

findOrders(SortOrder.DESC)   // true/false보다 훨씬 명확
```

### 스탬프 결합

**필요한 건 일부인데 통째로 넘기는 것.** 쪽지 한 장이면 되는데 서류철 전체를 건네는 셈이다.

```kotlin
// 나쁨 — 이름만 쓰면서 User 전체를 받음. User가 바뀌면 이 함수도 영향
fun greeting(user: User): String = "안녕하세요, ${user.name}님"

// 좋음 — 진짜 필요한 것만
fun greeting(name: String): String = "안녕하세요, ${name}님"
```

이게 문제인 이유는 **테스트할 때 드러난다.**

```kotlin
// 나쁨 — 인사말 하나 테스트하는데 User를 다 채워야 함
greeting(User(id = 1, name = "정성원", email = "...", age = 18, status = ..., ...))

// 좋음
greeting("정성원")
```

> **중요한 점** 다만 **인수가 4~5개로 늘어날 정도라면** 객체로 묶는 게 낫다. 스탬프 결합을 피하려다 인수 폭발이 나면 오히려 손해다. 기준은 **"이 값들이 항상 같이 다니는가"** 이다.

### 데이터 결합

**필요한 데이터만 인수로 주고받는 것.** 실무에서 목표로 삼는 현실적인 수준이다.

```kotlin
// 좋음 — 주는 것도 받는 것도 딱 필요한 만큼
fun calculateShippingFee(totalPrice: Int, region: Region): Int
fun findOrdersByUser(userId: Long): List<Order>
```

### 메시지 결합

**가장 약한 결합.** 데이터를 주고받지 않고 **"이런 일이 일어났다"는 사실만 알린다.** 보내는 쪽은 누가 받는지조차 모른다.

```kotlin
// 나쁨 — 주문 서비스가 메일, 포인트, 통계를 전부 알고 있음
class OrderService(
    private val mailSender: MailSender,
    private val pointService: PointService,
    private val statisticsService: StatisticsService,
) {
    fun completeOrder(order: Order) {
        order.complete()
        mailSender.send(order.email)          // 기능 추가할 때마다 여기가 늘어남
        pointService.accumulate(order)
        statisticsService.record(order)
    }
}

// 좋음 — "주문이 완료됐다"는 사실만 알림. 누가 듣는지는 모름
class OrderService(private val events: ApplicationEventPublisher) {
    fun completeOrder(order: Order) {
        order.complete()
        events.publishEvent(OrderCompletedEvent(order.id))
    }
}

@Component
class OrderMailListener(private val mailSender: MailSender) {
    @EventListener
    fun handle(event: OrderCompletedEvent) { ... }
}
```

> **중요한 점** 메시지 결합이 무조건 정답은 아니다. **흐름이 눈에 안 보인다는 대가**가 있다. 부가 기능(알림, 통계, 로그)에는 좋지만, **반드시 성공해야 하는 핵심 로직**은 직접 호출이 낫다.

### 디미터의 법칙

**"직접 아는 사람하고만 대화하라"** 는 원칙. 최소 지식 원칙이라고도 한다. 택배 기사가 내 지갑을 열어 돈을 꺼내가면 안 되듯이, **남의 내부를 타고 들어가면 안 된다.**

한 함수 안에서 호출해도 되는 대상은 이것뿐이다.

- 자기 자신의 메서드
- 인수로 받은 객체
- 자신이 만든 객체
- 자신의 필드

```kotlin
// 나쁨 — 점(.)을 타고 남의 내부로 들어감
val cityName = order.getUser().getAddress().getCity().getName()
```

이게 왜 나쁘냐면, 이 한 줄이 **User, Address, City 세 클래스에 모두 의존**하게 만들기 때문이다. `Address`의 구조가 바뀌면 관계도 없는 이 코드가 깨진다.

```kotlin
// 좋음 — 물어보지 말고 시켜라
class Order(private val user: User) {
    fun cityName(): String = user.cityName()
}

class User(private val address: Address) {
    fun cityName(): String = address.cityName()
}
```

이걸 **"묻지 말고 시켜라(Tell, Don't Ask)"** 라고 부른다.

```kotlin
// 나쁨 — 상태를 물어보고 밖에서 판단
if (order.status == OrderStatus.PENDING && order.createdAt.isAfter(now().minusDays(1))) {
    order.status = OrderStatus.CANCELED
}

// 좋음 — 판단과 처리를 아는 쪽에 맡김
order.cancel()   // 안에서 가능 여부를 검사하고 처리
```

**주의: 점이 여러 개라고 다 위반은 아니다.**

```kotlin
// 괜찮음 — 같은 흐름 안에서 자기 결과를 이어받는 체이닝
val names = users.filter { it.isActive }.map { it.name }.sorted()

// 괜찮음 — 빌더
val request = OrderRequest.builder().userId(1L).build()

// 위반 — 다른 객체의 내부를 타고 감
order.getUser().getAddress().getCity()
```

> **중요한 점** 판단 기준은 **점의 개수가 아니라 "낯선 타입이 몇 개 등장하는가"** 다.

## 의존 방향

의존은 **한 방향으로만** 흘러야 한다. 양방향이 되면 둘은 사실상 한 덩어리가 된다.

### 순환 의존

```kotlin
// 나쁨 — 서로를 참조. 하나만 떼어 테스트할 수 없음
class OrderService(private val userService: UserService) {
    fun createOrder() { userService.usePoint(...) }
}
class UserService(private val orderService: OrderService) {
    fun withdraw() { orderService.cancelAll(...) }
}
```

푸는 방법은 세 가지다.

```kotlin
// 1) 공통 부분을 위로 뽑는다
class OrderFacade(
    private val orderService: OrderService,
    private val userService: UserService,
) {
    fun createOrder() {
        userService.usePoint(...)
        orderService.create(...)
    }
}

// 2) 이벤트로 뒤집는다 (메시지 결합)
class UserService(private val events: ApplicationEventPublisher) {
    fun withdraw(userId: Long) {
        events.publishEvent(UserWithdrawnEvent(userId))
    }
}

// 3) 방향을 하나 끊는다 — 필요한 값만 인수로 받기
class OrderService {
    fun createOrder(userId: Long, availablePoint: Int) { ... }
}
```

### 의존성 역전 (DIP)

**"중요한 것이 덜 중요한 것에 의존하지 않게 뒤집는다."** 콘센트 규격(인터페이스)만 정해두면 어떤 가전이든 꽂을 수 있는 것과 같다.

```kotlin
// 나쁨 — 도메인이 인프라를 알고 있음. 방향: 도메인 → 인프라
class OrderService {
    private val client = TossPaymentClient()   // 결제사 바꾸면 도메인이 바뀜
}

// 좋음 — 도메인이 인터페이스를 정의하고, 인프라가 그걸 구현
//        방향: 인프라 → 도메인 (뒤집힘)
interface PaymentClient {                       // 도메인 계층
    fun pay(amount: Int): PaymentResult
}

class OrderService(private val payment: PaymentClient)   // 도메인 계층

class TossPaymentClient(...) : PaymentClient             // 인프라 계층
```

이렇게 하면 테스트가 쉬워지는 게 바로 보인다.

```kotlin
class FakePaymentClient : PaymentClient {
    override fun pay(amount: Int) = PaymentResult.Success
}

val service = OrderService(FakePaymentClient())   // 외부 API 없이 테스트
```

> **중요한 점** 인터페이스는 **쓰는 쪽(도메인)이 소유**해야 의미가 있다. 구현체 쪽에 인터페이스를 두면 이름만 인터페이스일 뿐 방향은 그대로다.

## 의존의 중복

같은 대상에 **여러 경로로 의존**하면, 하나가 바뀔 때 여러 군데를 고쳐야 한다.

```kotlin
// 나쁨 — 같은 정책이 세 곳에 복제됨
class OrderService {
    fun createOrder(order: Order) {
        if (order.amount > 50_000) applyFreeShipping()
    }
}
class CartService {
    fun showEstimate(cart: Cart) {
        if (cart.total > 50_000) showFreeShippingBadge()
    }
}
class OrderResponse(order: Order) {
    val isFreeShipping = order.amount > 50_000
}

// 좋음 — 정책을 한 곳에만 둔다
object ShippingPolicy {
    const val FREE_SHIPPING_THRESHOLD = 50_000
    fun isFree(amount: Int): Boolean = amount >= FREE_SHIPPING_THRESHOLD
}
```

**같은 개념을 여러 타입이 중복해 표현하는 것**도 의존의 중복이다.

```kotlin
// 나쁨 — 같은 유저를 세 가지 타입이 각자 표현. 필드 추가하면 셋 다 수정
class User(...)
class UserDto(...)
class UserVo(...)

// 좋음 — 계층별 목적이 다를 때만 나누고, 변환은 한 곳에서
class User(...)                                  // 도메인
data class UserResponse(...) {                   // API 응답
    companion object {
        fun from(user: User) = UserResponse(...)  // 변환 지점이 하나
    }
}
```

**전이 의존(간접 의존)** 도 조심해야 한다. A → B → C 인데 A가 C의 사정까지 알게 되는 경우다.

```kotlin
// 나쁨 — Controller가 JPA 엔티티를 그대로 반환 → API가 DB 스키마에 묶임
@GetMapping("/orders/{id}")
fun getOrder(@PathVariable id: Long): Order = orderService.find(id)

// 좋음 — 경계에서 끊는다
@GetMapping("/orders/{id}")
fun getOrder(@PathVariable id: Long): OrderResponse =
    OrderResponse.from(orderService.find(id))
```

> **중요한 점** 중복 제거의 기준은 **"코드가 같은가"가 아니라 "같은 이유로 바뀌는가"** 다. 우연히 코드가 같을 뿐인 둘을 묶으면, 나중에 한쪽만 바뀔 때 더 큰 문제가 된다.

## 의존의 명시성

의존은 **코드만 봐도 보여야 한다.** 숨은 의존은 리뷰어도 테스트도 못 잡는다.

### 생성자 주입

```kotlin
// 나쁨 — 함수 안에서 몰래 생성. 시그니처만 봐선 의존을 알 수 없음
class OrderService {
    fun pay(order: Order) {
        val client = TossPaymentClient()   // 숨은 의존
        client.pay(order.amount)
    }
}

// 좋음 — 생성자에 다 드러남. 이 클래스가 뭘 필요로 하는지 한눈에 보임
class OrderService(
    private val paymentClient: PaymentClient,
    private val orderRepository: OrderRepository,
) { ... }
```

생성자 주입의 부가 효과가 하나 더 있다. **의존이 너무 많으면 눈에 띈다.**

```kotlin
// 생성자 인수가 7개 → "이 클래스 책임이 너무 많은 거 아냐?" 라는 신호
class OrderService(
    private val a: A, private val b: B, private val c: C,
    private val d: D, private val e: E, private val f: F, private val g: G,
)
```

### 숨은 의존의 대표 사례

```kotlin
// 1) 정적 메서드 — 인수에 안 보이는데 결과가 달라짐
fun isExpired(order: Order): Boolean =
    order.expiredAt.isBefore(LocalDateTime.now())   // 시간에 몰래 의존 → 테스트 불가

// 좋음 — 시간도 인수로 받는다
fun isExpired(order: Order, now: LocalDateTime): Boolean =
    order.expiredAt.isBefore(now)
```

```kotlin
// 2) 싱글턴 직접 참조
class OrderService {
    fun create() {
        val config = ConfigManager.getInstance()   // 숨은 의존
    }
}

// 좋음
class OrderService(private val config: OrderConfig)
```

```kotlin
// 3) 필드 주입 — 무엇이 필요한지 생성자에 안 보이고, 테스트에서 주입도 어려움
class OrderService {
    @Autowired lateinit var paymentClient: PaymentClient   // 나쁨
}
```

### 타입으로 의존을 좁히기

**필요한 만큼만 아는 타입을 받으면** 의존이 자동으로 약해진다.

```kotlin
// 나쁨 — 구현체를 직접 받음
fun process(client: TossPaymentClient)

// 좋음 — 인터페이스만 알면 됨
fun process(client: PaymentClient)
```

```kotlin
// 나쁨 — 밖에서 내용을 바꿀 수 있음
fun summarize(items: MutableList<Item>): String

fun summarize(items: List<Item>): String
```

> **중요한 점** 명시성의 최종 점검은 **"이 클래스를 테스트로 만들 수 있는가"** 다. `new`(또는 생성자 호출) 한 줄로 만들어지지 않는다면, 어딘가에 숨은 의존이 있다는 뜻이다.
