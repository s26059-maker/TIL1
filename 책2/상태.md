# 상태

## 가변 값이 더 적합한 경우

기본은 **불변(`val`)** 이다. 값이 안 바뀌면 읽는 사람이 "지금 이 값이 뭐지?"를 추적할 필요가 없기 때문이다.

```kotlin
// 나쁨 — 아래로 내려갈수록 total이 뭔지 계속 따라가야 함
var total = 0
for (item in items) total += item.price
if (isVip) total -= 1000
if (total < 0) total = 0

// 좋음 — 각 단계가 이름을 갖고, 값은 안 바뀜
val subtotal = items.sumOf { it.price }
val discounted = if (isVip) subtotal - VIP_DISCOUNT else subtotal
val total = discounted.coerceAtLeast(0)
```

그렇다고 **모든 걸 불변으로 만드는 게 정답은 아니다.** 아래 경우엔 가변이 오히려 읽기 쉽고 안전하다.

**1) 값이 큰데 조금씩 자주 바뀔 때**
매번 통째로 복사하면 성능도 손해고 코드도 장황해진다.

```kotlin
// 나쁨 — 10만 건짜리 리스트를 매 반복마다 새로 만듦
var result = listOf<String>()
for (line in lines) result = result + line.trim()

// 좋음 — 지역 범위 안에서만 가변으로 쌓고, 밖으로는 불변으로 내보냄
fun normalize(lines: List<String>): List<String> {
    val result = mutableListOf<String>()
    for (line in lines) result += line.trim()
    return result.toList()   // 밖에서는 못 바꿈
}
```

> **중요한 점** 가변을 쓰더라도 **범위를 함수 안으로 가둔다.** 안에서 `var`을 쓰는 건 괜찮지만, 밖으로 새어 나가면 그 순간부터 추적 대상이 된다.

**2) 본질적으로 "계속 변하는 것"을 표현할 때**
현실에서 상태가 있는 대상은 억지로 불변으로 만들면 오히려 어색해진다.

```kotlin
// 게임 캐릭터의 HP, 커넥션의 연결 상태, 캐시 — 원래 변하는 것들
class GameCharacter(val name: String) {
    var hp: Int = MAX_HP
        private set                       // 밖에서는 못 바꿈

    fun takeDamage(damage: Int) {
        hp = (hp - damage).coerceAtLeast(0)
    }
}
```

**3) 만드는 단계가 여러 번 나뉠 때 (빌더 패턴)**

```kotlin
val request = OrderRequest.builder()
    .userId(1L)
    .addItem(item)
    .coupon(coupon)
    .build()      // 여기서부터 불변 객체가 됨
```

정리하면

| 상황 | 선택 |
|---|---|
| 계산 결과, 설정값, DTO | 불변 |
| 함수 내부의 임시 누적 | 가변(단, 지역 한정) |
| 실제로 변하는 도메인 상태 | 가변(단, `private set`으로 통제) |
| 여러 스레드가 함께 봄 | 불변 우선 |

## 변수 간의 관계, 직교

**직교(orthogonal)** 는 수학에서 온 말인데, 쉽게 말하면 **"서로 영향을 주지 않는 관계"** 다. 오디오의 볼륨 노브와 밝기 노브는 서로 상관없다 = 직교한다. 반대로 두 노브가 몰래 연결돼 있으면, 하나 돌릴 때마다 다른 걸 확인해야 한다.

변수도 똑같다. **직교하지 않는 변수들은 "같이 바꿔야 하는 짐"** 이 된다.

### 종속 관계 — 파생 값을 따로 저장한 경우

```kotlin
// 나쁨 — items가 바뀌면 count, totalPrice도 같이 고쳐야 함
class Cart {
    val items = mutableListOf<Item>()
    var count: Int = 0            // items에서 나오는 값
    var totalPrice: Int = 0       // items에서 나오는 값

    fun add(item: Item) {
        items += item
        count++                    // 하나만 빼먹으면 즉시 버그
        totalPrice += item.price
    }
}

// 좋음 — 파생 값은 저장하지 않고 계산한다
class Cart {
    private val _items = mutableListOf<Item>()
    val items: List<Item> get() = _items.toList()

    val count: Int get() = _items.size
    val totalPrice: Int get() = _items.sumOf { it.price }

    fun add(item: Item) { _items += item }
}
```

### 불가능한 조합이 생기는 경우

변수를 따로 두면, 실제로는 존재할 수 없는 조합이 **타입 위에서는 가능해진다.**

```kotlin
// 나쁨 — 4가지 조합이 가능하지만 실제로 말이 되는 건 2개
class LoadResult {
    var isLoading: Boolean = false
    var data: List<User>? = null
    var error: String? = null
}
// isLoading=true 인데 data도 error도 있는 상태? → 불가능한데 표현은 됨
```

이럴 땐 **sealed class로 "가능한 상태만" 표현**한다.

```kotlin
// 좋음 — 존재할 수 있는 상태만 타입으로 못 박음
sealed interface LoadResult {
    data object Loading : LoadResult
    data class Success(val data: List<User>) : LoadResult
    data class Failure(val message: String) : LoadResult
}

when (result) {
    is LoadResult.Loading -> showSpinner()
    is LoadResult.Success -> render(result.data)     // data 접근이 안전
    is LoadResult.Failure -> showError(result.message)
}
```

같은 원리로, **묶여 다녀야 하는 값은 한 객체로** 묶는다.

```kotlin
// 나쁨 — 셋이 항상 같이 바뀌는데 따로 놀고 있음
var address: String? = null
var latitude: Double? = null
var longitude: Double? = null

// 좋음 — 하나로 묶으면 "반쪽짜리 상태"가 안 생김
data class Location(val address: String, val latitude: Double, val longitude: Double)
var location: Location? = null
```

## 상태 전이의 설계

상태가 있는 코드는 **"어떻게 변할 수 있는가"** 를 설계해야 한다. 여기에 쓰는 세 가지 무기가 불변성, 멱등성, 비순환이다.

### 불변성

**한 번 만들어지면 절대 안 바뀌는 성질.** 전이 자체를 없애서 문제를 원천 차단한다.

```kotlin
// 가변 — 어디서든 바뀔 수 있어 "지금 값"을 믿을 수 없음
class Money(var amount: Int) {
    fun add(other: Int) { amount += other }
}

val price = Money(1000)
applyDiscount(price)   // 이 안에서 price가 바뀌었을까? 열어봐야 앎
println(price.amount)  // ???

// 불변 — 바꾸는 게 아니라 "새로 만든다"
data class Money(val amount: Int) {
    fun plus(other: Int): Money = Money(amount + other)
}

val price = Money(1000)
val discounted = price.plus(-200)   // price는 그대로 1000
```

불변이면 이런 게 공짜로 따라온다.

- 스레드 여러 개가 동시에 봐도 안전
- 함수에 넘겨도 원본이 안 망가짐
- `equals`/`hashCode`가 안정적이라 Map 키, Set 원소로 써도 됨

#### 부분적인 불변성

현실에서는 **전부 불변**이 불가능한 경우가 많다. 그래서 **바뀌면 안 되는 것만 골라서** 불변으로 만든다. 이걸 부분적 불변성이라 한다.

**1) 식별자와 생성 시각처럼 절대 안 변하는 것만 `val`**

```kotlin
@Entity
class Order(
    @Id val id: Long,                     // 절대 불변
    val userId: Long,                     // 주문자는 안 바뀜
    val createdAt: LocalDateTime,         // 생성 시각도 안 바뀜
) {
    var status: OrderStatus = OrderStatus.PENDING   // 이건 변해야 함
        private set                                  // 단, 밖에서는 못 바꿈

    fun pay() { status = OrderStatus.PAID }
}
```

**2) 안은 가변, 밖은 불변 (방어적 노출)**
컬렉션은 `val`로 선언해도 **내용물은 바뀔 수 있다.** `val`은 "참조가 안 바뀐다"는 뜻이지 "내용이 안 바뀐다"는 뜻이 아니다.

```kotlin
// 나쁨 — val인데도 밖에서 마음대로 추가/삭제 가능
class Cart {
    val items = mutableListOf<Item>()
}
cart.items.clear()   // 막을 방법이 없음

// 좋음 — 안쪽만 가변, 밖으로는 읽기 전용으로만
class Cart {
    private val _items = mutableListOf<Item>()
    val items: List<Item> get() = _items.toList()

    fun add(item: Item) { _items += item }
    fun remove(item: Item) { _items -= item }
}
```

**3) 특정 시점 이후로 불변이 되는 것 (한 방향 잠금)**

```kotlin
class Invoice {
    var isConfirmed: Boolean = false
        private set

    var amount: Int = 0
        set(value) {
            check(!isConfirmed) { "확정된 청구서는 금액을 바꿀 수 없습니다" }
            field = value
        }

    fun confirm() { isConfirmed = true }   // 이 순간부터 amount는 불변
}
```

> **중요한 점** 부분적 불변성의 핵심 질문은 **"이 값이 바뀌면 안 되는 시점이 언제부터인가?"** 다. 그 시점을 코드로 못 박으면, 문서나 리뷰로 지킬 필요가 없어진다.

### 멱등성

**같은 연산을 몇 번 해도 결과가 같은 성질.** 엘리베이터 버튼을 다섯 번 눌러도 한 번 누른 것과 같은 게 멱등이다. 반대로 "카운터 +1"은 누를수록 값이 달라지니 비멱등이다.

```kotlin
// 비멱등 — 몇 번 불렀느냐에 따라 결과가 달라짐
fun increasePoint(amount: Int) { point += amount }
increasePoint(100)
increasePoint(100)   // 200이 됨

// 멱등 — 몇 번 불러도 결과 동일
fun setPoint(amount: Int) { point = amount }
setPoint(100)
setPoint(100)        // 여전히 100
```

#### 멱등성으로 내부 상태를 숨기기

멱등성의 진짜 가치는 여기 있다. **호출하는 쪽이 "지금 상태가 뭔지" 몰라도 되게 만드는 것.**

```kotlin
// 나쁨 — 비멱등이라 호출자가 상태를 먼저 확인해야 함
class Connection {
    var isOpen: Boolean = false     // 상태가 밖으로 노출됨

    fun close() {
        check(isOpen) { "이미 닫힌 커넥션입니다" }   // 두 번 부르면 터짐
        isOpen = false
    }
}

// 호출부가 내부 사정을 알아야 함 → 결합도 상승
if (connection.isOpen) {
    connection.close()
}
```

```kotlin
// 좋음 — 멱등으로 만들면 상태를 숨길 수 있음
class Connection {
    private var isOpen: Boolean = false    // 이제 감춰도 됨

    fun close() {
        if (!isOpen) return                // 이미 닫혔으면 조용히 아무것도 안 함
        socket.disconnect()
        isOpen = false
    }
}

// 호출부는 아무것도 몰라도 됨
connection.close()
connection.close()   // 여러 번 불러도 안전
```

이 패턴이 이렇게 쓰인다.

```kotlin
// 상태 확인 없이 그냥 호출하면 되는 API들
fun ensureDirectoryExists(path: Path) {
    Files.createDirectories(path)   // 이미 있으면 아무 일도 안 일어남
}

fun cancel() {
    if (status == CANCELED) return
    status = CANCELED
    refund()
}

fun logout() {
    session.clear()   // 로그인 상태든 아니든 결과는 "로그아웃됨"
}
```

**API/네트워크에서는 멱등성이 안전장치가 된다.** 응답이 유실돼 클라이언트가 재시도해도 중복 처리가 안 되기 때문이다.

```kotlin
// 멱등 키를 받아 같은 요청은 한 번만 처리
fun pay(idempotencyKey: String, amount: Int): Payment {
    paymentRepository.findByIdempotencyKey(idempotencyKey)
        ?.let { return it }                     // 이미 처리됐으면 그 결과를 그대로
    return paymentRepository.save(Payment(idempotencyKey, amount))
}
```

> **중요한 점** 함수 이름이 **`set`, `ensure`, `clear`, `cancel`, `close`** 계열이면 멱등이어야 자연스럽고, **`add`, `increase`, `append`, `send`** 계열이면 비멱등이 자연스럽다. 이름과 성질이 어긋나면 호출자가 반드시 실수한다.

### 비순환

**상태가 앞으로만 흐르고 되돌아오지 않는 성질.** 강물처럼 한 방향으로만 흐르면 "지금 어디쯤인지"만 알면 되지만, 빙글빙글 돌면 "몇 바퀴째인지"까지 알아야 한다.

```kotlin
// 순환하는 설계 — 어떤 순서로도 갈 수 있어 경우의 수가 폭발
enum class OrderStatus { PENDING, PAID, SHIPPED, DELIVERED, CANCELED }

fun changeStatus(status: OrderStatus) {
    this.status = status   // DELIVERED → PENDING 도 가능해짐
}
```

```kotlin
// 비순환 설계 — 갈 수 있는 방향을 못 박음
enum class OrderStatus {
    PENDING, PAID, SHIPPED, DELIVERED, CANCELED;

    fun canMoveTo(next: OrderStatus): Boolean = when (this) {
        PENDING   -> next in setOf(PAID, CANCELED)
        PAID      -> next in setOf(SHIPPED, CANCELED)
        SHIPPED   -> next == DELIVERED
        DELIVERED -> false     // 종착점. 여기서 되돌아갈 수 없음
        CANCELED  -> false     // 종착점
    }
}

class Order {
    var status: OrderStatus = OrderStatus.PENDING
        private set

    fun moveTo(next: OrderStatus) {
        require(status.canMoveTo(next)) { "$status → $next 는 불가능한 전이입니다" }
        status = next
    }
}
```

비순환으로 얻는 것들이다.

- **불가능한 상태가 애초에 안 생김** — 배송 완료된 주문이 다시 결제 대기로 돌아가는 버그가 원천 차단
- **테스트할 경우의 수가 줄어듦** — 순환이 없으면 경로가 유한하고 셀 수 있음
- **이력 추적이 쉬움** — 상태만 봐도 어디까지 진행됐는지 알 수 있음

"되돌리기"가 필요하면 **뒤로 가는 게 아니라 새 상태를 추가**한다.

```kotlin
// 나쁨 — 취소하면 결제 전으로 되돌림 (순환 발생)
fun cancelPayment() { status = PENDING }

// 좋음 — 새로운 종착 상태로 나아감
fun cancelPayment() { moveTo(OrderStatus.CANCELED) }
```

객체 사이의 참조도 마찬가지다. **양방향 참조는 순환이라 추적이 어려워진다.**

```kotlin
// 나쁨 — 서로 참조. 누가 누구를 바꿨는지 추적 불가
class Order { var user: User? = null }
class User  { val orders = mutableListOf<Order>() }

// 좋음 — 한 방향으로만
class Order(val userId: Long)
// 필요한 조회는 Repository가 담당
fun findOrdersByUser(userId: Long): List<Order>
```
