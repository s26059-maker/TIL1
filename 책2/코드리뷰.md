# 코드 리뷰

## 리뷰이의 주의사항 1: 리뷰하기 쉬운 PR 만들기

### PR 목적 명시

리뷰어가 가장 먼저 알아야 할 건 **"이 변경이 왜 필요한가"** 다. 목적을 모르면 리뷰어는 코드가 맞는지조차 판단할 수 없다. 목적지를 모르는 사람에게 지도를 보여주는 것과 같다.

```markdown
// 나쁨 — 무엇을 했는지만 있고 왜인지가 없음
## 내용
주문 취소 API 추가했습니다.

// 좋음
## 목적
고객센터에서 취소 요청을 받으면 개발자가 직접 DB를 수정하고 있습니다.
운영 리스크가 커서 API로 대체합니다. (#412)

## 변경 내용
- 주문 취소 API 추가
- 취소 가능 조건(결제 전 / 배송 전)을 도메인에 정의

## 이번 PR에서 하지 않은 것
- 부분 취소는 정책 미확정이라 제외 (#418)
```

**하지 않은 것**을 적어주는 게 특히 중요하다. 리뷰어가 "이거 왜 빠졌지?" 하고 물어볼 시간을 아껴준다.

리뷰받고 싶은 지점을 직접 지목하면 리뷰어의 시간이 정확한 곳에 쓰인다.

```markdown
## 리뷰 포인트
- `OrderService.cancel()` 의 트랜잭션 범위를 봐주세요.
- 재고 복구를 이벤트로 뺄지 고민했는데, 실패 시 롤백이 필요해 직접 호출로 두었습니다.
```

> **중요한 점** 목적은 **코드를 보면 알 수 있는 것**이 아니라 **코드로는 절대 알 수 없는 것**을 적는다. "무엇을 바꿨는지"는 diff가 이미 말해준다.

### PR 분리

**하나의 PR은 하나의 목적만** 담는다. 목적이 둘이면 PR도 둘이다.

```text
// 나쁨 — 성격이 다른 변경이 섞임 (+2,400 -300)
[PR] 주문 기능 구현 + 기존 코드 리팩터링 + 컨벤션 정리

// 좋음 — 순서대로 쌓기
[PR 1] refactor: 주문 금액 계산을 Order로 이동 (동작 변경 없음)
[PR 2] feat: 주문 도메인 상태 전이 규칙 추가
[PR 3] feat: 주문 취소 API 추가
[PR 4] feat: 취소 알림 발송 추가
```

**리팩터링과 기능 변경을 절대 섞지 않는다.** 섞이면 리뷰어가 "이 동작 변경이 의도된 건지, 정리하다 실수한 건지" 구분할 방법이 없어진다. diff 2,000줄 중 진짜 봐야 할 20줄이 묻힌다.

분리 기준은 이렇다.

| 섞이면 안 되는 조합 |
|---|
| 리팩터링 + 기능 추가 |
| 포맷팅/이름 변경 + 로직 변경 |
| 라이브러리 업그레이드 + 기능 변경 |
| 서로 관련 없는 두 기능 |

PR이 커지는 게 불가피하면 최소한 **커밋으로라도 분리**한다.

### 커밋 구조화

PR 전체가 커도 **커밋 단위로 읽으면 따라갈 수 있게** 만든다. 리뷰어에게 결과물이 아니라 **생각의 순서**를 보여주는 것이다.

```text
// 나쁨 — 커밋만 봐선 아무것도 모름
- wip
- 수정
- 다시 수정
- 오타
- 리뷰 반영
- 진짜 마지막

// 좋음 — 커밋 하나하나가 의미 단위
- feat: 주문 상태 전이 규칙 추가
- feat: 주문 취소 API 추가
- refactor: 금액 계산 로직을 Order로 이동
- test: 취소 불가 조건 테스트 추가
```

커밋을 나누는 기준은 **"이 커밋만 되돌려도 말이 되는가"** 다.

- 한 커밋 = 하나의 의미 있는 변경
- 커밋 하나하나가 **빌드와 테스트를 통과**하는 상태
- 포맷팅/이름 변경만 하는 커밋은 **따로** (섞이면 diff가 오염된다)

커밋 메시지는 **제목에 "무엇", 본문에 "왜"** 를 쓴다.

```text
refactor: 주문 금액 계산을 Order 내부로 이동

OrderService가 Order의 필드를 꺼내 계산하고 있어
계산 규칙이 바뀔 때마다 서비스까지 함께 수정해야 했다.
계산을 Order로 옮겨 규칙 변경이 한 곳에서 끝나도록 했다.
```

### 하향식 설명

PR 설명은 **큰 것부터 작은 것 순서**로 쓴다. 리뷰어가 세부 코드를 보기 전에 **전체 그림을 먼저 갖게** 하기 위해서다. 골목 사진부터 보여주면 아무도 길을 못 찾는다.

```markdown
1) 목적       왜 이 변경이 필요한가
2) 접근 방식   어떤 구조로 풀었는가
3) 주요 변경   핵심 클래스/함수 단위로
4) 세부 사항   신경 쓴 예외 처리, 트레이드오프
5) 확인 방법   테스트, 로컬 검증 결과
```

```markdown
## 목적
결제 실패 시 재고가 복구되지 않는 문제를 해결합니다. (#420)

## 접근 방식
재고 차감과 결제를 하나의 트랜잭션으로 묶고,
재고 복구는 도메인 이벤트가 아니라 직접 호출로 처리했습니다.

## 주요 변경
- `OrderService.cancel()` : 결제 취소 → 재고 복구 → 상태 변경 순서로 처리
- `OrderStatus.canMoveTo()` : 취소 가능한 상태를 명시

## 세부 사항
- 결제 취소 API가 멱등이라 재시도해도 중복 환불이 나지 않습니다.

## 확인 방법
- `OrderCancelTest` 통과
- 로컬에서 취소 후 결제사 대시보드에서 취소 확인
```

코드 안에서도 하향식으로 안내할 수 있다. **"여기부터 읽으세요"** 를 알려주는 것이다.

```kotlin
// PR 코멘트: "이 함수가 이번 변경의 진입점입니다.
//            아래 private 함수들은 여기서 갈라져 나온 것들이에요."
fun cancel(orderId: Long) {
    val order = findOrder(orderId)
    order.cancel()
    refundPayment(order)
    restoreStock(order)
}
```

## 리뷰이의 주의사항 2: 리뷰 코멘트 적용하기

### 의도 파악하기

코멘트에 **적혀 있는 말**과 **하고 싶은 말**은 다를 수 있다. 표면만 보고 고치면 리뷰어가 원한 게 해결되지 않는다.

```text
// 코멘트
"이 함수 좀 긴 것 같아요."
```

```kotlin
// 나쁨 — 글자 그대로만 처리. 줄 수만 줄고 문제는 그대로
fun processOrder(request: OrderRequest) {
    part1(request); part2(request); part3(request)   // 의미 없이 3등분
}

// 좋음 — 의도(책임이 섞여 있다)를 파악하고 대상별로 분할
fun processOrder(request: OrderRequest) {
    validate(request)
    val total = calculateTotal(request.items)
    val order = saveOrder(request, total)
    sendConfirmationMail(order)
}
```

의도가 확실하지 않으면 **반드시 묻는다.** 가장 나쁜 건 이해 못 한 채로 그냥 반영하는 것이다. 그 코드는 다음에도 똑같이 문제가 된다.

```text
// 나쁨
"넵 수정했습니다."   (사실 왜 그래야 하는지 모름)

// 좋음
"불변으로 바꾸라는 말씀이 클래스 전체인지 items 컬렉션만인지 헷갈립니다.
 JPA 엔티티라 전체를 data class로 바꾸긴 어려울 것 같은데,
 items만 읽기 전용으로 노출하는 방향이 맞을까요?"
```

### 원인 찾기

코멘트가 가리키는 건 **증상**이지 **원인**이 아닐 때가 많다. 증상만 덮으면 같은 문제가 다른 얼굴로 다시 나온다.

```text
// 코멘트
"여기 null 체크가 빠진 것 같아요."
```

```kotlin
// 증상만 처리
fun send(userId: Long) {
    val user = repository.find(userId)
    if (user?.email != null) mailSender.send(user.email)   // 일단 막음
}

// 원인 처리 — 애초에 null이 될 수 있는 구조가 문제였음
class User(
    val id: Long,
    val email: Email,          // 값 타입으로 만들어 null 자체를 없앰
)
```

원인까지 내려가는 질문은 이런 것들이다.

- **왜 이 실수가 나왔나?** → 타입이 느슨해서? 이름이 헷갈려서?
- **비슷한 실수를 막을 방법이 있나?** → 타입, 테스트, 린트 룰
- **이게 이 자리에 있는 게 맞나?** → 책임 위치가 잘못된 건 아닌지

```text
// 좋음 — 원인을 짚어 답글
"말씀하신 null 체크를 추가하려다 보니, 이메일이 없는 User가
 애초에 존재할 수 있는 게 이상하다는 걸 발견했습니다.
 Email 값 타입을 만들어 필수로 바꿨습니다. → a3f1c2d"
```

### 다른 부분에 적용하기

하나 지적받았다면 **같은 문제가 다른 곳에도 있을 확률이 높다.** 리뷰어가 12곳을 다 찾아 지적하게 두지 않는다.

```text
// 코멘트
"OrderService에서 TossPaymentClient를 직접 생성하고 있네요."
```

```text
// 나쁨 — 지적받은 한 줄만 고침
// 좋음 — 같은 패턴을 스스로 찾아 정리
"말씀하신 부분 수정했습니다.
 확인해 보니 PaymentService, RefundService에도 같은 패턴이 있어
 함께 인터페이스 주입으로 바꿨습니다. → b7e2a91"
```

다만 **범위가 넘치면 이슈로 넘긴다.** PR이 커지면 리뷰가 다시 어려워진다.

```text
"UserService에도 같은 문제가 있는데, 이번 PR 범위를 넘어설 것 같아
 별도 이슈로 등록했습니다. (#419)"
```

**지식 자체를 다음으로 옮기는 것**도 여기 포함된다.

- 반복해서 받은 지적 → 팀 컨벤션 문서에 추가
- 도구가 잡을 수 있는 것 → ktlint / detekt 룰로 등록

> **중요한 점** 같은 지적을 두 번 받았다면 그건 개인 실수가 아니라 **팀에 규칙이 없다는 신호**다. 규칙으로 승격시켜야 세 번째가 없다.

## 리뷰어의 주의사항 1: 리뷰어의 원칙

### 리뷰 방치하지 않기

리뷰가 늦어지면 손해가 눈덩이처럼 불어난다.

- 리뷰이가 **맥락을 잃는다** — 3일 뒤엔 자기 코드도 남의 코드다
- 브랜치가 낡아 **충돌이 쌓인다**
- 리뷰이가 그동안 **아무것도 못 하고 대기**한다

시간이 없으면 **부분 리뷰라도 남긴다.** 침묵이 가장 나쁘다.

```text
// 나쁨 — 3일째 무응답

// 좋음
"오늘은 도메인 부분만 봤습니다. 컨트롤러는 내일 오전에 볼게요.
 급하시면 도메인 쪽 코멘트 먼저 반영하셔도 됩니다."

// 좋음
"지금 다른 이슈 대응 중이라 오늘 안엔 어려울 것 같습니다.
 급한 건이면 @민우님께 요청해 주세요."
```

**완벽한 리뷰를 늦게 하는 것보다 괜찮은 리뷰를 빨리 하는 게 낫다.** 큰 문제만 먼저 짚어도 리뷰이는 그동안 작업할 수 있다.

### 문제 있으면 거부하기

승인(Approve)은 **"이 코드가 메인에 들어가도 된다"는 책임 표명**이다. 애매하면 승인하지 않는다.

거부해야 하는 경우는 명확하다.

- 버그가 있거나 요구사항을 만족하지 못할 때
- 구조가 잘못돼 나중에 되돌리기 어려워질 때
- 이해가 안 되는 코드일 때 (**이해 못 한 코드는 승인 대상이 아니다**)

```text
// 나쁨 — 애매한 채로 통과
"음... 잘 모르겠지만 LGTM 👍"

// 좋음 — 모르면 모른다고
"이 부분 흐름이 이해되지 않아서 아직 승인하기 어렵습니다.
 상태가 세 곳에서 바뀌는 것 같은데, 어느 시점에 최종 확정되는 건가요?"
```

거부는 **사람이 아니라 코드에 대한 것**이고, 반드시 **무엇을 고치면 통과되는지**를 함께 알려준다.

```text
// 나쁨
"이대로는 안 됩니다."

// 좋음
"[P1] 재고 차감과 결제가 다른 트랜잭션이라, 결제 실패 시 재고가 복구되지 않습니다.
 같은 트랜잭션으로 묶거나 보상 로직이 필요할 것 같습니다.
 이 부분 해결되면 승인하겠습니다."
```

반대로 **완벽하지 않아도 명백히 나아졌다면 승인**한다. 리뷰의 목적은 완벽한 코드가 아니라 **지금보다 나은 코드베이스**다. 남은 개선은 이슈로 넘긴다.

```text
"[P2] 로 남긴 것들은 다음 PR에서 하셔도 될 것 같습니다. 승인합니다."
```

### 기한을 지나치게 의식하지 않기

"급하다"는 이유로 리뷰를 흐리게 하면, **그 급함은 나중에 몇 배로 돌아온다.** 잘못된 구조는 계속 쌓이고, 결국 더 큰 시간을 쓴다.

```text
// 나쁨 — 기한에 밀려 판단을 접음
"내일 배포라 하시니 일단 승인할게요."
```

기한이 진짜 급하면, **판단을 낮추는 게 아니라 범위를 조정**한다.

```text
// 좋음 — 무엇이 필수고 무엇이 미룰 수 있는지 구분
"[P1] 결제 실패 시 재고 복구 — 이건 데이터가 깨지는 문제라 배포 전 필수입니다.
 [P2] 구조 정리 — 다음 스프린트로 미뤄도 괜찮습니다.
 P1만 해결되면 오늘 안에 승인하겠습니다."

// 좋음 — 부채를 남길 거면 기록으로 남긴다
"급하신 상황 이해했습니다. 이번엔 이대로 가되,
 이 부분은 이슈(#421)로 남기고 다음 주에 정리하는 걸로 하시죠."
```

> **중요한 점** 기한을 무시하라는 게 아니라 **기한이 판단 기준을 바꾸게 두지 말라**는 뜻이다. "급해서 통과시켰다"는 나중에 아무도 기억해 주지 않는다.

### 하향식으로 보기

**큰 것부터 작은 것 순서로** 읽는다. 세부부터 보면 정작 중요한 걸 놓치고, 설계가 뒤집히면 앞서 단 코멘트가 전부 무의미해진다.

```text
1단계  목적    이 변경이 필요한가? 문제를 제대로 푸는가?
2단계  설계    책임 분배와 의존 방향이 맞는가?
3단계  정확성  로직, 경계값, 예외, 동시성
4단계  표현    이름, 가독성, 중복
5단계  사소    오타, 포맷
```

**1~2단계에 문제가 있으면 3단계 아래는 아직 달지 않는다.** 구조가 바뀌면 그 코드는 사라질 수도 있다.

```text
"먼저 큰 부분 하나만 여쭤볼게요. 재고 복구를 OrderService가 직접 하고 있는데
 StockService로 옮기는 게 맞지 않을까요?
 구조가 바뀔 수 있어서 세부 코멘트는 방향 정해지고 남기겠습니다."
```

**5단계는 사람이 하지 않는다.** 오타, 포맷, 컨벤션은 린터와 포매터에게 넘긴다. 사람이 매번 지적하고 있다면 도구 설정이 빠졌다는 신호다.

## 리뷰어의 주의사항 2: 코멘트 내용

### 제안이 아닌 의견 제시하기

**"이렇게 바꾸세요"라는 완성된 해결책(제안)만 던지면** 세 가지가 망가진다.

- 리뷰이가 **왜 바꾸는지 모른 채** 그대로 복붙한다 → 다음에 또 같은 실수
- 리뷰이가 아는 **맥락(제약, 이미 시도해 본 것)** 이 무시된다
- 더 나은 세 번째 방법이 나올 기회가 사라진다

그래서 **"무엇이 왜 문제인가"라는 의견을 먼저 말하고, 해결은 리뷰이에게 맡긴다.**

```text
// 나쁨 — 제안만. 이유도 선택지도 없음
"여기 fetch join으로 바꾸세요."

// 좋음 — 문제와 근거(의견) → 해결은 열어둠
"items를 순회하면서 매번 조회하고 있어 주문 수만큼 쿼리가 나갈 것 같습니다.
 주문이 많은 사용자에서 응답이 느려질 수 있어 보이는데,
 어떻게 푸는 게 좋을지 의견 주실 수 있을까요?"
```

```text
// 나쁨
"이거 인터페이스로 바꾸세요."

// 좋음
"TossPaymentClient를 직접 참조하고 있어서, 결제사를 바꾸거나
 테스트에서 대체할 때 서비스까지 수정해야 할 것 같습니다.
 이 결합을 끊을 방법이 있을까요?"
```

**단정 대신 질문으로 열어두는 것**도 같은 맥락이다. 리뷰어가 맥락을 모를 수 있고, 내가 틀렸을 가능성을 열어두는 게 논의를 빠르게 만든다.

```text
// 나쁨 — 단정
"이건 N+1 납니다. 고치세요."

// 좋음 — 확인
"제가 보기엔 N+1이 날 것 같은데, 혹시 캐시가 걸려 있는 부분일까요?"
```

**해결책이 필요한 순간도 있다.** 리뷰이가 방향을 못 잡고 있거나, 팀에 정해진 방식이 있을 때다. 이때도 **의견 → 제안** 순서를 지킨다.

```text
// 좋음 — 문제 설명 후 예시로 제안
"조건이 네 단계로 중첩돼 있어 마지막 줄까지 조건 네 개를 기억해야 합니다.
 가드 절로 빼면 평평해질 것 같은데, 이런 형태는 어떨까요?

```kotlin
if (user == null) throw UserNotFoundException()
if (user.isBanned) throw BannedUserException()
return Order(user.id, items)
```
 물론 더 나은 방법 있으시면 그쪽으로 가셔도 됩니다."
```

의견의 세기도 라벨로 구분해 준다. **무엇이 필수고 무엇이 취향인지** 알려주지 않으면 리뷰이는 사소한 것까지 다 고치느라 시간을 쓴다.

```text
[P1] 필수 — 머지 전 반드시 수정
[P2] 권장 — 고치면 좋지만 이번 PR 아니어도 됨
[nit] 사소 — 취향 수준. 무시해도 무방
[question] 질문 — 지적이 아니라 이해하려는 것
```

```text
[P1] 결제 실패 시 재고가 복구되지 않습니다.
[P2] calculateTotal()이 Order로 들어가면 서비스가 가벼워질 것 같아요.
[nit] userLst → users 가 자연스러울 것 같습니다. 무시하셔도 됩니다.
[question] 재시도 3회로 정한 기준이 있을까요?
```

> **중요한 점** **"내가 그렇게 안 짜서"** 는 의견이 아니다. 팀 컨벤션에도 없고 설명할 근거도 없다면 `[nit]`으로 달거나 아예 달지 않는다.

### 사례 분석

**추상적인 지적은 움직이지 않는다.** "결합도가 높습니다", "가독성이 떨어집니다" 같은 말은 맞는 말이지만 리뷰이가 뭘 해야 할지 모른다.

**구체적인 사례**를 들어야 문제가 눈에 보인다. 방식은 세 가지다.

**1) 실제로 터지는 시나리오를 든다**

```text
// 나쁨 — 추상적
"동시성 문제가 있을 것 같습니다."

// 좋음 — 사례로
"재고가 1개 남았을 때 두 사용자가 동시에 주문하면,
 둘 다 재고 조회(1개) → 둘 다 차감 → 재고가 -1이 될 것 같습니다.
 실제로 이벤트 때 이 패턴으로 오버셀링이 났던 적이 있습니다."
```

**2) 앞으로 생길 변경 상황을 든다**

```text
// 나쁨
"확장성이 부족합니다."

// 좋음
"지금은 카드 결제만 있어서 문제없지만,
 다음 달 계좌이체가 들어오면 이 if문이 세 군데로 늘어날 것 같습니다.
 그때 한 곳만 빠뜨려도 조용히 잘못 결제될 것 같아 걱정됩니다."
```

**3) 이 코드를 쓰는 사람 입장을 든다**

```text
// 나쁨
"인수가 헷갈립니다."

// 좋음
"호출부에서 `transfer(1L, 2L, 5000)` 로 보이는데,
 앞의 두 개 중 누가 보내는 쪽인지 시그니처를 열어야 알 수 있습니다.
 순서를 바꿔 써도 컴파일이 되니 조용히 잘못 송금될 수 있어 보입니다."
```

같은 패턴이 여러 곳에 있으면 **한 곳에만 사례를 분석해 달고, 범위를 알려준다.** 12곳에 같은 코멘트를 다는 건 리뷰이에게도 리뷰어에게도 낭비다.

```text
"여기 포함해 UserService 안 5곳에 같은 패턴이 있습니다.
 위에 설명한 이유로 한 번에 정리해 주시면 좋겠습니다."
```

**잘한 부분도 사례로 짚는다.** 지적만 오가면 사람들이 리뷰를 피하게 되고, 좋은 사례를 짚는 건 그 방식을 팀 전체에 퍼뜨리는 방법이기도 하다.

```text
"상태 전이를 enum의 canMoveTo로 막아둔 거 좋네요.
 예전에 배송 완료된 주문이 결제 대기로 돌아가는 버그가 있었는데,
 이 구조면 애초에 컴파일 단계에서 걸러지겠어요. 다른 도메인에도 쓰면 좋겠습니다."
```
