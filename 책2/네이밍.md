#  네이밍

## 네이밍에 사용하는 영문법

이름은 "짧게"보다 **읽었을 때 문장처럼 들리게** 짓는 게 먼저다. 그래서 품사를 맞추는 게 규칙의 시작이다.

### 명사, 명사구

**값을 나타내는 것**은 명사(구)로 짓는다. 변수, 프로퍼티, 클래스, 상수가 여기 해당한다.

```kotlin
// 클래스 — 명사
class OrderValidator
class PaymentClient
class UserProfile

// 변수 / 프로퍼티 — 명사구
val totalPrice: Int
val loggedInUser: User
val remainingCount: Int
```

명사구는 **"수식어 + 핵심 명사"** 순서로 놓고, 마지막 단어가 진짜 정체를 말하게 한다.

```kotlin
// 나쁨 — 마지막 단어가 정체를 안 알려줌
val priceTotal: Int
val userLoggedIn: User

// 좋음 — 끝 단어만 봐도 "가격이구나", "유저구나"
val totalPrice: Int
val loggedInUser: User
```

컬렉션은 **복수형**으로, boolean은 **is / has / can / should**로 시작해 형용사구처럼 만든다.

```kotlin
val users: List<User>          // 여러 개
val userIds: Set<Long>

val isActive: Boolean          // ~인 상태다
val hasPermission: Boolean     // ~을 가지고 있다
val canPublish: Boolean        // ~할 수 있다
```

### 명령문

**동작하는 것**은 명령문(동사로 시작)으로 짓는다. 함수와 메서드가 여기 해당한다.

```kotlin
// "무엇을 해라" 형태
fun createOrder(request: OrderRequest): Order
fun cancelReservation(id: Long)
fun sendConfirmationMail(order: Order)
```

동사 뒤에 목적어를 붙여 **"동사 + 목적어"** 로 완성한다.

```kotlin
// 나쁨 — 동사만 있어 뭘 하는지 모름
fun process()
fun handle()
fun update()

// 좋음 — 대상이 붙음
fun processPayment()
fun handleExpiredToken()
fun updateNickname(nickname: String)
```

> **중요한 점** 값을 돌려주는 함수라도 **동작이면 동사**로 짓는다. 다만 계산이 아니라 **단순 조회 프로퍼티**라면 명사로 두는 게 자연스럽다.

```kotlin
// 계산/조회 동작 → 동사
fun calculateTotalPrice(): Int
fun findByEmail(email: String): User?

// 그냥 값 → 명사 (Kotlin 프로퍼티)
val size: Int
val name: String
```

### 문법을 무시하고 네이밍하는 이유

문법보다 **관례와 가독성이 우선**일 때가 있다. 무조건 완전한 영어 문장을 만들 필요는 없다.

**1) 이미 굳어진 관용 표현**

```kotlin
// 문법적으론 이상하지만 모두가 아는 이름
fun toString(): String
fun setUp()          // 테스트 준비
val i, j             // 반복문 인덱스
val e                // catch (e: Exception)
```

**2) 너무 길어져 오히려 안 읽힐 때**

```kotlin
// 나쁨 — 문법은 완벽하지만 아무도 안 읽음
val theNumberOfUsersWhoHaveNotVerifiedTheirEmailAddress: Int

// 좋음 — 맥락상 충분히 통함
val unverifiedUserCount: Int
```

**3) 도메인 용어를 그대로 써야 할 때**
현업에서 쓰는 단어를 억지로 영어 문법에 맞추면 오히려 소통이 깨진다.

```kotlin
// 팀/기획서에서 "정산"을 settlement라 부른다면 그대로 쓴다
class SettlementBatch
fun runSettlement(date: LocalDate)
```

**4) 프레임워크·라이브러리 규칙**

```kotlin
// JPA, Spring이 요구하는 형태를 따름
fun findAllByUserIdAndStatus(userId: Long, status: Status): List<Order>
```

## 이름에서 알 수 있는 내용

좋은 이름은 **구현을 안 열어봐도** 그 코드가 뭘 하는지 알려준다.

### 함수 이름

함수 이름은 **"무엇을 하는지"** 와 **"무엇을 돌려주는지"** 를 담는다. 반대로 **"어떻게 하는지"(구현 방식)** 는 넣지 않는다.

```kotlin
// 나쁨 — 구현 방식이 이름에 박힘. 방식 바꾸면 이름도 거짓말이 됨
fun getUserByHashMap(id: Long): User
fun sortUsersWithQuickSort(users: List<User>): List<User>

// 좋음 — 목적만 담음
fun findUser(id: Long): User
fun sortUsersByName(users: List<User>): List<User>
```

이름과 실제 동작이 다르면 그게 최악이다. **부수 효과(side effect)** 는 이름에 반드시 드러낸다. 부수 효과란 값을 돌려주는 것 말고 **바깥 상태를 바꾸는 일**(저장, 삭제, 전송 등)을 말한다.

```kotlin
// 나쁨 — get인데 몰래 저장까지 함
fun getUser(id: Long): User {
    val user = repository.find(id)
    user.lastAccessedAt = now()
    repository.save(user)   // 이름에 없는 동작
    return user
}

// 좋음 — 하는 일이 이름에 다 있음
fun findUser(id: Long): User
fun touchLastAccessedAt(user: User)
```

자주 쓰는 동사는 **뜻을 팀에서 고정**해두면 이름만 보고 동작을 예측할 수 있다.

| 동사 | 의미 |
|---|---|
| `get` | 반드시 있음. 없으면 예외 |
| `find` | 없을 수 있음. `null` 반환 |
| `create` | 새로 만들어 반환 |
| `save` | 저장(신규 + 수정 모두) |
| `is` / `has` | boolean 반환 |
| `to` | 다른 타입으로 변환 |

```kotlin
fun getUser(id: Long): User          // 없으면 throw
fun findUser(id: Long): User?        // 없으면 null
fun toResponse(): UserResponse       // 변환
```

### 인수 이름

인수(파라미터) 이름은 **호출하는 쪽에서 읽힐 것**을 생각해서 짓는다.

```kotlin
// 나쁨 — 호출부에서 뭐가 뭔지 모름
fun transfer(a: Long, b: Long, c: Int)
transfer(1L, 2L, 5000)

// 좋음 — 이름만 봐도 순서가 보임
fun transfer(fromUserId: Long, toUserId: Long, amount: Int)
transfer(fromUserId = 1L, toUserId = 2L, amount = 5000)
```

타입만 반복하는 이름, 의미 없는 축약은 피한다.

```kotlin
// 나쁨
fun register(str: String, num: Int, flag: Boolean)

// 좋음
fun register(nickname: String, age: Int, isAgreedToTerms: Boolean)
```

> **중요한 점** boolean 인수가 2개 이상이면 이름을 아무리 잘 지어도 호출부가 안 읽힌다. 이럴 땐 **enum이나 객체로 묶는 게** 네이밍보다 나은 해결책이다.

```kotlin
// 나쁨
createUser(true, false)

// 좋음
createUser(NotificationSetting(email = true, sms = false))
```

### 예외: 추상화된 메서드

인터페이스나 추상 클래스처럼 **여러 구현을 아우르는 자리**에서는 이름을 일부러 **한 단계 더 추상적으로** 짓는다. 구체적으로 지으면 다른 구현체에서 거짓말이 되기 때문이다.

```kotlin
// 나쁨 — 인터페이스인데 이름이 특정 구현에 묶임
interface MessageSender {
    fun sendEmail(to: String, body: String)   // SMS 구현체는 어떡하지?
}

// 좋음 — 어떤 구현이 와도 성립하는 이름
interface MessageSender {
    fun send(to: String, body: String)
}

class EmailSender : MessageSender { ... }
class SmsSender : MessageSender { ... }
```

반대로 **구현 클래스는 구체적으로** 짓는다.

```kotlin
interface PaymentClient { fun pay(amount: Int) }

class TossPaymentClient : PaymentClient   // 무엇으로 결제하는지 명확
class MockPaymentClient : PaymentClient   // 테스트용임이 명확
```

## 단어 선택

같은 개념에는 **항상 같은 단어**를 쓴다. 단어가 섞이면 읽는 사람은 "뭔가 다른 건가?" 하고 의심하게 된다.

```kotlin
// 나쁨 — 같은 조회인데 단어가 제각각
fun getUser(id: Long): User
fun fetchOrder(id: Long): Order
fun retrieveProduct(id: Long): Product
fun loadCoupon(id: Long): Coupon

// 좋음 — 한 가지로 통일
fun getUser(id: Long): User
fun getOrder(id: Long): Order
fun getProduct(id: Long): Product
```

반대로 **다른 개념에 같은 단어**를 쓰는 것도 문제다.

```kotlin
// 나쁨 — add가 서로 다른 뜻
fun addUser(user: User)            // DB에 저장
fun addPoint(point: Int)           // 기존 값에 더함

// 좋음
fun saveUser(user: User)
fun increasePoint(point: Int)
```

축약어는 **모두가 아는 것만** 쓴다.

```kotlin
// 괜찮음 — 통용되는 축약
val id, url, http, api, db

// 나쁨 — 나만 아는 축약
val usrCnt, ordRsp, tmpPrcCalc

// 좋음
val userCount, orderResponse, temporaryPriceCalculator
```

### 긍정적 단어 사용

boolean은 **부정형으로 짓지 않는다.** 부정을 부정하면(`!isNotXxx`) 머릿속에서 두 번 뒤집어야 한다.

```kotlin
// 나쁨 — 이중 부정
val isNotAvailable: Boolean
if (!isNotAvailable) { ... }        // 읽는 순간 멈칫

val isDisabled: Boolean
if (!isDisabled) { ... }

// 좋음 — 긍정형
val isAvailable: Boolean
if (isAvailable) { ... }

val isEnabled: Boolean
if (isEnabled) { ... }
```

조건문도 가능하면 긍정이 먼저 오게 배치한다.

```kotlin
// 나쁨
if (!user.isBanned && !order.isCanceled) { proceed() }

// 좋음
if (user.isActive && order.isValid) { proceed() }
```

## 언어, 플랫폼, 코딩 규약

같은 개념이라도 **언어마다 관례가 다르다.** 문법적으로 옳은지보다 **그 언어에서 통하는 방식**을 따르는 게 우선이다.

Kotlin 기본 규약은 이렇다.

```kotlin
// 클래스, 인터페이스, 객체 → PascalCase
class OrderService
interface PaymentClient

// 함수, 변수, 프로퍼티 → camelCase
fun calculateTotalPrice()
val loggedInUser: User

// 상수(compile-time) → UPPER_SNAKE_CASE
const val MAX_RETRY_COUNT = 3

// 패키지 → 전부 소문자, 언더스코어 X
package com.example.order.payment

// 테스트 함수 → 백틱으로 한글/공백 허용
@Test
fun `주문 금액이 5만원 이상이면 무료 배송이 적용된다`() { ... }
```

Kotlin에서는 **Java 스타일을 그대로 옮기지 않는 것**도 규약의 일부다.

```kotlin
// 나쁨 — Java 습관
class User(private val name: String) {
    fun getName(): String = name       // Kotlin은 프로퍼티가 있음
}

// 좋음
class User(val name: String)           // user.name 으로 접근
```

```kotlin
// 나쁨 — boolean 프로퍼티에 get 붙이기
val getIsActive: Boolean

// 좋음
val isActive: Boolean
```

플랫폼/프레임워크가 정한 이름은 그 규칙이 곧 정답이다.

```kotlin
// Spring — 계층 접미사 관례
class OrderController
class OrderService
interface OrderRepository : JpaRepository<Order, Long>

// JPA — 메서드 이름이 곧 쿼리이므로 마음대로 못 바꿈
fun findAllByStatusOrderByCreatedAtDesc(status: Status): List<Order>
```
