# 함수

## 함수의 책임

함수는 **"하나의 일"** 을 해야 한다. 여기서 "하나"의 기준은 코드 줄 수가 아니라 **한 문장으로 설명되는가**이다.

```kotlin
// 이름에 "그리고"가 들어가면 대부분 책임이 둘 이상
fun validateAndSaveAndNotify(order: Order)   // 신호
```

### 명령과 쿼리의 분리

**CQS(Command Query Separation)** 라고 부른다. 함수를 두 종류로만 나눈다.

| 종류 | 하는 일 | 반환값 | 상태 변경 |
|---|---|---|---|
| **명령(Command)** | 상태를 바꾼다 | 없음(`Unit`) | O |
| **쿼리(Query)** | 값을 알려준다 | 있음 | X |

핵심 규칙은 **"둘을 한 함수에서 동시에 하지 않는다"** 이다. 질문했는데 대상이 바뀌어 있으면 곤란하다. 온도계를 봤더니 온도가 바뀌는 셈이다.

```kotlin
// 나쁨 — 조회인 척하면서 상태를 바꿈
fun getUser(id: Long): User {
    val user = repository.find(id)
    user.viewCount++                 // 몰래 변경
    repository.save(user)
    return user
}

// 호출부에서 이런 사고가 남
val a = getUser(1L)
val b = getUser(1L)   // 부른 것뿐인데 viewCount가 2 올라감
```

```kotlin
// 좋음 — 명령과 쿼리를 분리
fun findUser(id: Long): User = repository.find(id)        // 쿼리: 안 바꿈
fun increaseViewCount(id: Long) { ... }                    // 명령: 안 돌려줌
```

CQS를 지키면 **쿼리는 몇 번을 불러도 안전해진다.** 조건문 안에서, 로그에서, 테스트에서 마음껏 부를 수 있다.

```kotlin
// 쿼리라서 안심하고 여러 번 호출 가능
if (order.calculateTotal() > 50_000 && order.calculateTotal() < 100_000) { ... }
log.info("총액: ${order.calculateTotal()}")
```

**현실적인 예외**도 있다. 무조건 지키면 오히려 불편한 경우다.

```kotlin
// 관용적으로 허용되는 것들 — 명령이지만 결과를 돌려줌
val removed = list.removeAt(0)          // 지우고 지운 값 반환
val previous = map.put(key, value)      // 넣고 이전 값 반환
val saved = repository.save(order)      // 저장하고 저장된 엔티티 반환
```

> **중요한 점** 예외를 쓰더라도 기준은 같다. **이름이 명령임을 분명히 말하고 있는가.** `save`, `remove`, `put`은 누가 봐도 상태를 바꾸는 이름이라 반환값이 있어도 헷갈리지 않는다. `get`, `find`, `is`가 상태를 바꾸는 게 문제다.

### 조작 대상에 따른 분할

함수가 커졌을 때 **어디서 잘라야 하나?** 기준은 "줄 수"가 아니라 **다루는 대상(데이터)이 바뀌는 지점**이다.

```kotlin
// 나쁨 — 한 함수에서 request, item, order, mail 을 전부 만짐
fun processOrder(request: OrderRequest) {
    if (request.items.isEmpty()) throw IllegalArgumentException("상품이 없습니다")
    if (request.address.isBlank()) throw IllegalArgumentException("주소가 없습니다")

    var total = 0
    for (item in request.items) {
        total += item.price * item.count
    }
    if (total > 50_000) total -= 3_000

    val order = Order(request.userId, total, request.address)
    orderRepository.save(order)

    val body = "주문번호 ${order.id}, 금액 ${order.total}원"
    mailSender.send(request.email, "주문 완료", body)
}
```

대상별로 자르면 이렇게 된다.

```kotlin
// 좋음 — 각 함수가 자기 대상 하나만 만짐
fun processOrder(request: OrderRequest) {
    validate(request)                                   // 대상: request
    val total = calculateTotal(request.items)           // 대상: items
    val order = saveOrder(request, total)               // 대상: order
    sendConfirmationMail(request.email, order)          // 대상: mail
}

private fun validate(request: OrderRequest) {
    require(request.items.isNotEmpty()) { "상품이 없습니다" }
    require(request.address.isNotBlank()) { "주소가 없습니다" }
}

private fun calculateTotal(items: List<OrderItem>): Int {
    val subtotal = items.sumOf { it.price * it.count }
    return if (subtotal > FREE_SHIPPING_THRESHOLD) subtotal - SHIPPING_FEE else subtotal
}
```

분할 지점을 찾는 실전 신호들이다.

- **주석으로 구역을 나누고 있다** → 그 주석이 곧 함수 이름
- **같은 변수만 붙어 다니는 덩어리가 있다** → 그 덩어리가 한 함수
- **중간에 임시 변수(`total`, `body`)가 생긴다** → 그 변수를 만드는 부분이 한 함수
- **들여쓰기가 3단계 넘는다** → 안쪽을 떼어낸다

한 걸음 더 나아가면, 다루는 대상이 **자기 데이터**라면 아예 그 데이터 쪽으로 함수를 옮긴다.

```kotlin
// 나쁨 — 서비스가 Order의 내부 값을 꺼내서 계산
class OrderService {
    fun isCancelable(order: Order): Boolean =
        order.status == OrderStatus.PENDING && order.createdAt.isAfter(now().minusDays(1))
}

// 좋음 — 자기 데이터를 아는 쪽이 판단
class Order(...) {
    fun isCancelable(): Boolean =
        status == OrderStatus.PENDING && createdAt.isAfter(now().minusDays(1))
}
```

## 함수의 흐름

책임을 나눴다면, 다음은 **함수 안이 어떤 순서로 읽히는가**이다.

### 조기 반환

**예외적인 경우를 위에서 먼저 걷어내고, 정상 흐름을 아래에 남기는 방식.** 가드 절(guard clause)이라고도 한다.

```kotlin
// 나쁨 — 정상 로직이 가장 안쪽에 파묻힘
fun createOrder(user: User?, items: List<Item>): Order {
    if (user != null) {
        if (!user.isBanned) {
            if (items.isNotEmpty()) {
                if (user.point >= calculateTotal(items)) {
                    return Order(user.id, items)      // ← 진짜 하고 싶은 일
                } else {
                    throw NotEnoughPointException()
                }
            } else {
                throw EmptyItemException()
            }
        } else {
            throw BannedUserException()
        }
    } else {
        throw UserNotFoundException()
    }
}

// 좋음 — 조건과 그 결과가 붙어 있고, 정상 흐름이 맨 아래에 평평하게 남음
fun createOrder(user: User?, items: List<Item>): Order {
    if (user == null) throw UserNotFoundException()
    if (user.isBanned) throw BannedUserException()
    if (items.isEmpty()) throw EmptyItemException()
    if (user.point < calculateTotal(items)) throw NotEnoughPointException()

    return Order(user.id, items)
}
```

조기 반환이 좋은 이유는 **머릿속에 담을 조건이 줄어들기** 때문이다. 중첩 방식에서는 마지막 줄까지 조건 4개를 동시에 기억해야 하지만, 조기 반환에서는 통과한 조건을 바로 잊어도 된다.

Kotlin에서 자주 쓰는 형태들이다.

```kotlin
// require / check — 조건 위반 시 예외 (조기 반환의 축약형)
fun withdraw(amount: Int) {
    require(amount > 0) { "출금액은 0보다 커야 합니다" }
    check(!isLocked) { "잠긴 계좌입니다" }
    balance -= amount
}

// ?: return — null이면 즉시 탈출
fun sendMail(userId: Long) {
    val user = userRepository.findById(userId) ?: return
    val email = user.email ?: return
    mailSender.send(email)
}

// 스마트 캐스트 — 조기 반환 후에는 타입이 자동으로 좁혀짐
fun describe(value: Any?): String {
    if (value !is String) return "문자열이 아님"
    return value.uppercase()      // 여기서 value는 이미 String
}
```

### 정의 기반 프로그래밍

절차를 하나씩 지시하는 대신, **"이건 무엇이다"라는 정의를 쌓아 올려** 마지막에 답이 나오게 하는 방식이다. 요리로 치면 "냄비에 넣어라, 저어라, 5분 뒤에 꺼내라"가 아니라 **"소스 = 양파 + 토마토, 파스타 = 면 + 소스"** 처럼 재료를 정의해 나가는 것이다.

```kotlin
// 흐름 기반 — var를 계속 고쳐 나감. 마지막 값이 뭔지 위에서부터 따라가야 함
fun calculatePrice(order: Order, user: User): Int {
    var price = 0
    for (item in order.items) {
        price += item.price * item.count
    }
    if (user.isVip) {
        price = price - price * 10 / 100
    }
    if (price > 50_000) {
        price -= 3_000
    }
    if (price < 0) {
        price = 0
    }
    return price
}

// 정의 기반 — 각 단계가 이름을 갖고, 한 번 정해진 값은 안 바뀜
fun calculatePrice(order: Order, user: User): Int {
    val subtotal = order.items.sumOf { it.price * it.count }
    val afterVipDiscount = if (user.isVip) subtotal * 90 / 100 else subtotal
    val afterShipping = if (afterVipDiscount > FREE_SHIPPING_THRESHOLD)
        afterVipDiscount - SHIPPING_FEE else afterVipDiscount

    return afterShipping.coerceAtLeast(0)
}
```

정의 기반이 주는 이점이다.

- **중간 상태가 이름을 가진다** → `afterVipDiscount`만 봐도 그 시점의 의미를 안다
- **디버깅할 때 어느 단계가 틀렸는지 바로 보인다**
- **`var`가 없으니 "지금 값이 뭐지"를 추적할 필요가 없다**

Kotlin은 정의 기반으로 쓰기 좋은 문법을 갖고 있다. `if`, `when`, `try`가 **값을 반환하는 식(expression)** 이기 때문이다.

```kotlin
// 나쁨 — var를 선언해 두고 나중에 채움
fun gradeOf(score: Int): String {
    var grade: String
    if (score >= 90) grade = "A"
    else if (score >= 80) grade = "B"
    else grade = "C"
    return grade
}

// 좋음 — when 자체가 값
fun gradeOf(score: Int): String = when {
    score >= 90 -> "A"
    score >= 80 -> "B"
    else -> "C"
}
```

```kotlin
// 식 본문(expression body) — "이 함수는 곧 이 값이다"
fun isAdult(user: User): Boolean = user.age >= ADULT_AGE
fun fullName(user: User): String = "${user.lastName}${user.firstName}"
```

```kotlin
// 컬렉션도 절차 대신 정의로
// 나쁨
val result = mutableListOf<String>()
for (user in users) {
    if (user.isActive) {
        result.add(user.name.uppercase())
    }
}

// 좋음 — "결과 = 활성 유저의 대문자 이름들"
val result = users.filter { it.isActive }.map { it.name.uppercase() }
```

```kotlin
// 나쁨 — 정의 기반이지만 한 덩어리라 안 읽힘
val top3 = orders.filter { it.status == PAID }.groupBy { it.type }
    .mapValues { (_, v) -> v.sumOf { it.price } }.entries
    .sortedByDescending { it.value }.take(3).associate { it.key to it.value }

// 좋음 — 단계마다 이름
val paidOrders = orders.filter { it.status == PAID }
val salesByType = paidOrders.groupBy { it.type }.mapValues { (_, v) -> v.sumOf { it.price } }
val top3 = salesByType.entries.sortedByDescending { it.value }.take(3).associate { it.key to it.value }
```

### 추상화 수준 맞추기

한 함수 안의 문장들은 **같은 눈높이**여야 한다. "비행기를 탄다, 짐을 부친다, 지퍼를 올린다"처럼 크기가 다른 일이 섞이면 읽는 사람이 계속 줌인/줌아웃을 해야 한다.

```kotlin
// 나쁨 — 큰 단계와 세부 구현이 섞임
fun processOrder(request: OrderRequest) {
    validate(request)                                  // 큰 단계
    var total = 0                                      // 갑자기 세부 구현
    for (item in request.items) total += item.price
    saveOrder(request, total)                          // 다시 큰 단계
}

// 좋음 — 전부 같은 눈높이. 목차처럼 읽힘
fun processOrder(request: OrderRequest) {
    validate(request)
    val total = calculateTotal(request.items)
    val order = saveOrder(request, total)
    sendConfirmationMail(order)
}
```
