# 실행 계획 2 - ANALYZE 완전 정복

## EXPLAIN ANALYZE

> **EXPLAIN ANALYZE** = 쿼리를 **실제로 실행**하고, **예상값과 실제값**을 함께 보여주는 명령어

```sql
EXPLAIN ANALYZE SELECT * FROM member WHERE member_id = 1;
```

| 항목 | EXPLAIN | EXPLAIN ANALYZE |
|---|---|---|
| 쿼리 실행 | X | **O** |
| 보여주는 값 | 예상값 | 예상값 + **실제값** |
| 출력 형태 | 표 | 트리 |

**중요한 점:** EXPLAIN은 **계획**, EXPLAIN ANALYZE는 **계획 + 실제 결과**다.

---

## 주의 사항

> EXPLAIN ANALYZE는 쿼리를 **진짜로 실행**한다.

- 5억 건 테이블을 풀스캔하는 쿼리라면 **실제로 5억 건을 다 읽는다.**
- 운영 DB에서 쓰면 서비스가 느려질 수 있다.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE created_at >= '2020-01-01';  -- 사실상 전체 스캔 → 위험
```

### 운영 환경 대안

> **EXPLAIN FORMAT=TREE** = 실행하지 않고 **예상 계획만** 트리 형태로 보여준다.

```sql
EXPLAIN FORMAT=TREE SELECT * FROM member WHERE member_id = 1;
```

**중요한 점:** 운영 DB에서는 **FORMAT=TREE**, 개발·테스트 DB에서는 **ANALYZE**를 쓴다.

---

## 사용 순서

1. **EXPLAIN**으로 계획을 먼저 확인한다.
2. 문제가 의심되면 **EXPLAIN ANALYZE**로 실제 값을 확인한다.

```sql
EXPLAIN SELECT * FROM product WHERE category_id = 11;
EXPLAIN ANALYZE SELECT * FROM product WHERE category_id = 11;
```

---

## 출력 읽는 법

출력 한 줄의 모양

```
-> Index lookup on product using idx_product_category_id (category_id=11)
   (cost=... rows=예상) (actual time=A..B rows=실제 loops=N)
```

| 항목 | 뜻 |
|---|---|
| cost | 옵티마이저가 계산한 **예상 비용** |
| rows (앞) | **예상** 행 수 |
| actual time=A..B | A = **첫 행**까지 걸린 시간, B = **마지막 행**까지 걸린 시간 (ms) |
| rows (뒤) | **실제** 행 수 |
| loops | 이 단계가 **반복된 횟수** |

> **실제 전체 행 수 = rows × loops**

### 트리 읽는 순서

- **들여쓰기가 깊은 줄부터** 실행된다.
- 안쪽 결과가 바깥 줄로 넘어간다.

**중요한 점:** 트리는 **안쪽 → 바깥** 순서로 읽는다.

---

## 실행 단계

쿼리에 조건을 하나씩 추가하면 트리에 단계가 하나씩 늘어난다.

| 단계 | 쿼리에 추가한 것 | 트리에 나오는 것 |
|---|---|---|
| 1 | 조건 없음 | `Table scan` (전체 스캔) |
| 2 | `member_id BETWEEN ...` | `Index range scan` (인덱스 범위 스캔) |
| 3 | `+ order_status = 'DELIVERED'` | `Filter` (인덱스 없는 조건 거르기) |
| 4 | `+ ORDER BY total_price DESC` | `Sort` (정렬) |
| 5 | `JOIN member` | `Nested loop inner join` (조인) |
| 6 | `+ LIMIT 10` | `Limit` (개수 제한) |

> **Nested loop join** = 바깥 테이블의 **행 하나마다** 안쪽 테이블을 찾는 조인 방식 → 안쪽 단계의 **loops가 커진다.**

6단계 전체 쿼리

```sql
EXPLAIN ANALYZE
SELECT m.member_name, o.total_price
FROM orders o
JOIN member m ON m.member_id = o.member_id
WHERE m.member_id BETWEEN 2940001 AND 2950000
  AND o.order_status = 'DELIVERED'
ORDER BY o.total_price DESC
LIMIT 10;
```

트리 모양 (간략화)

```
-> Limit: 10 row(s)
    -> Sort: o.total_price DESC
        -> Nested loop inner join
            -> Filter: o.order_status = 'DELIVERED'
                -> Index range scan on o
            -> Single-row index lookup on m (PK)
```

**중요한 점:** 트리에서 **actual time이 갑자기 커지는 단계**가 병목이다.

## 예상 vs 실제

> **통계 정보** = 옵티마이저가 판단에 쓰는 테이블 **요약 정보** (행 수, 값 분포 등)

- 예상 rows와 실제 rows가 **크게 다르면** → 통계 정보가 틀린 것
- 통계가 틀리면 옵티마이저가 **잘못된 계획**을 고를 수 있다.

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE member_id BETWEEN 2940001 AND 2950000;
```

| 예상 rows vs 실제 rows | 판단 |
|---|---|
| 비슷함 | 정상 |
| 크게 다름 | 통계 갱신 필요 |

해결: 통계 정보를 다시 계산한다.

```sql
ANALYZE TABLE orders;
```

**중요한 점:** 예상과 실제가 크게 다르면 **ANALYZE TABLE**로 통계를 갱신한다.
