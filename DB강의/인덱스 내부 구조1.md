# 인덱스 내부 구조 1 - B+Tree

## B-Tree

> **B-Tree** = 값을 정렬해서 저장하는 트리. **모든 노드에 데이터**가 들어 있다.

```
         [30|데이터]
         /         \
 [10|데이터]     [50|데이터]
```

- 위쪽 노드에서 바로 찾을 수도 있다.
- 범위 검색은 트리를 **위아래로 왔다 갔다** 해야 해서 느리다.

---

## B+Tree

> **B+Tree** = B-Tree를 개선한 트리. **데이터는 맨 아래(리프)에만** 있고, **리프끼리 옆으로 연결**되어 있다.

```
              [30]              ← 루트: 길 안내만
            /      \
        [10]        [50]        ← 브랜치: 길 안내만
       /    \      /    \
    [리프] ↔ [리프] ↔ [리프] ↔ [리프]   ← 데이터 + 옆으로 연결
```

| 노드 | 역할 |
|---|---|
| 루트 | 맨 위 시작점 |
| 브랜치 | 어느 쪽으로 내려갈지 알려주는 **이정표** |
| 리프 | **실제 데이터**가 있는 곳. 옆 리프와 연결 |

MySQL(InnoDB) 인덱스는 **B+Tree**를 쓴다. (`BTREE`라고 표시돼도 실제는 B+Tree)

---

## B-Tree vs B+Tree

| 항목 | B-Tree | B+Tree |
|---|---|---|
| 데이터 위치 | 모든 노드 | **리프에만** |
| 리프 연결 | X | **O** |
| 범위 검색 | 느림 | **빠름** (리프를 옆으로 쭉 읽음) |
| 노드 하나에 담는 키 | 적음 | **많음** (데이터가 없어서) |
| 트리 높이 | 높음 | **낮음** |

**중요한 점:** B+Tree는 **범위 검색이 빠르고, 트리가 낮아서** DB 인덱스에 적합하다.

---

## 노드와 트리 높이

> **노드 하나 = 페이지 하나(16KB)**
> **트리 높이 = 디스크 읽기 횟수**

- 한 페이지에 키가 **수백~수천 개** 들어간다.
- 그래서 트리가 옆으로 넓고 **높이는 3~4** 정도다.

| 트리 높이 | 찾을 수 있는 양 |
|---|---|
| 3 | 수천만 건 |
| 4 | 수십억 건 |

**중요한 점:** 수천만 건이어도 **페이지 3~4번**만 읽으면 찾는다.

---

## 클러스터드 vs 세컨더리 인덱스

| 인덱스 | 리프에 들어 있는 것 | 찾는 과정 |
|---|---|---|
| **클러스터드** (PK) | **행 데이터 전체** | PK 탐색 → 끝 |
| **세컨더리** (나머지) | **PK 값** | 인덱스 탐색 → PK 획득 → **PK 한 번 더 탐색** |

- 세컨더리 인덱스로 **너무 많은 행**을 찾으면 PK 재탐색이 반복돼 느려진다.
- 그래서 옵티마이저가 인덱스 대신 **풀스캔**을 고르기도 한다.

**중요한 점:** 같은 1건이라도 **PK 조회가 가장 빠르다.**

---

## 페이지 분할과 병합

| 작업 | 언제 | 하는 일 |
|---|---|---|
| **분할** | 페이지가 꽉 찼을 때 | 페이지를 **둘로 나눔** |
| **병합** | 삭제로 페이지가 많이 비었을 때 | 옆 페이지와 **합침** |

> **MERGE_THRESHOLD** = 병합 기준. 기본값 **50%**

**중요한 점:** 분할·병합이 자주 일어나면 **쓰기 성능이 떨어진다.**
