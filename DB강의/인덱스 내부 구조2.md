# 인덱스 내부 구조 2 - 클러스터드, 세컨더리 인덱스

## 클러스터드 인덱스

> **클러스터드 인덱스** = PK 인덱스. 리프에 **행 데이터 전체**가 있고, 테이블 데이터가 **PK 순서대로** 저장된다.

PK로 찾으면 인덱스 탐색 한 번으로 끝난다.

### 선택 규칙

| 순서 | 클러스터드 인덱스가 되는 것 |
|---|---|
| 1 | PK |
| 2 | PK가 없으면 → 첫 번째 **UNIQUE + NOT NULL** 인덱스 |
| 3 | 그것도 없으면 → MySQL이 만든 **숨은 행 ID** |

---

## 순차 PK vs 랜덤 PK

| PK 방식 | 삽입 위치 | 결과 |
|---|---|---|
| AUTO_INCREMENT (순차) | 항상 **맨 끝** | 페이지 분할 거의 없음 → **빠름** |
| 랜덤 값 (UUID 등) | **중간 아무 곳** | 페이지 분할 자주 발생 → **느림 + 페이지 수 증가** |

같은 BIGINT(8바이트)여도 **값이 랜덤이라는 이유만으로** 삽입이 느려지고 용량도 커진다.

**중요한 점:** PK는 **순차적으로 증가하는 값**을 쓴다.

---

## 세컨더리 인덱스

> **세컨더리 인덱스** = PK 외의 인덱스. 리프에 **인덱스 값 + PK**가 들어 있다.

### 2단 점프

```
category_id 인덱스 → PK 획득 → 클러스터드 인덱스 → 행 데이터
```

| 조회량 | 결과 |
|---|---|
| 적음 (10건) | 점프 10번 → 빠름 |
| 많음 (25만 건) | 점프 25만 번 → **느림** |

**중요한 점:** 세컨더리 인덱스는 **조회 건수가 많을수록** 불리하다.

---

## 커버링 인덱스

> **커버링 인덱스** = 필요한 컬럼이 **인덱스 안에 다 있어서** 2단 점프가 없는 상태. Extra에 `Using index`

세컨더리 인덱스 `(category_id)` 안에는 **PK(product_id)도 자동으로** 들어 있다.

| 쿼리 | 2단 점프 | 이유 |
|---|---|---|
| `SELECT *` | O | 인덱스에 없는 컬럼 필요 |
| `SELECT category_id` | **X** | 인덱스에 있음 |
| `SELECT product_id, category_id` | **X** | PK도 인덱스에 있음 |
| `SELECT product_id, price` | O | price가 인덱스에 없음 |

**중요한 점:** 필요한 컬럼만 SELECT하면 **테이블을 안 읽고** 끝낼 수 있다.

---

## 세컨더리 인덱스 안의 PK 정렬

세컨더리 인덱스는 **인덱스 값 → PK 순서**로 정렬돼 있다.

| category_id | product_id |
|---|---|
| 11 | 3 |
| 11 | 8 |
| 11 | 15 |
| 12 | 2 |

```sql
SELECT product_id, category_id FROM product
WHERE category_id = 11
ORDER BY product_id;   -- 이미 정렬돼 있어서 filesort 없음
```

## 랜덤 I/O vs 순차 I/O

| 방식 | 읽는 모양 | 예 |
|---|---|---|
| **랜덤 I/O** | 페이지를 **여기저기** 읽음 | 세컨더리 인덱스 → PK 점프 |
| **순차 I/O** | 페이지를 **순서대로** 읽음 | 풀 테이블 스캔 |

> **Read-Ahead(미리 읽기)** = 순서대로 읽는 중이면 **다음 페이지를 미리** 버퍼 풀에 올려두는 기능

순차 I/O는 미리 읽기 덕분에 **1건당 비용이 훨씬 싸다.**

---

## 손익분기점

> 조회 비율이 **일정 수준(대략 20~25%)을 넘으면** 인덱스보다 **풀스캔이 더 빠르다.**

| 조회 비율 | 더 빠른 쪽 |
|---|---|
| 적음 | 인덱스 (랜덤 I/O 조금) |
| 많음 | 풀스캔 (순차 I/O + 미리 읽기) |

### FORCE INDEX 역효과

```sql
-- 약 40% 데이터를 인덱스로 강제 → 풀스캔보다 느려짐
SELECT * FROM product FORCE INDEX (idx_product_category_id)
WHERE category_id BETWEEN 11 AND 19;
```

**중요한 점:** 인덱스가 **항상 빠른 건 아니다.** 옵티마이저가 풀스캔을 고르면 이유가 있다.
