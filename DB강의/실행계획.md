# 실행 계획 1 - EXPLAIN 완전 정복

## 실행 계획의 필요성

> **실행 계획** = 옵티마이저가 정한 **쿼리 처리 방법** (어떤 인덱스를 쓸지, 몇 줄을 읽을지 등)

"가격으로 검색하니까 가격에 인덱스를 걸자"처럼 **감으로** 인덱스를 추가하면 문제가 생긴다.

```sql
CREATE INDEX idx_product_price ON product (price);
```

- 인덱스 용량만 늘어난다.
- 옵티마이저가 그 인덱스를 **안 쓰면** 쿼리 속도는 그대로다.

**중요한 점:** 인덱스는 감이 아니라 **EXPLAIN으로 확인하고** 판단한다.

---

## EXPLAIN 사용법

> **EXPLAIN** = 쿼리 앞에 붙여 **실행 계획을 보는** 명령어. 쿼리를 실제로 실행하지는 않는다.

```sql
EXPLAIN SELECT * FROM member WHERE member_id = 1;
```

### 출력 형식

| 형식 | 특징 |
|---|---|
| 기본 (TRADITIONAL) | 표 형태, 가장 많이 씀 |
| `FORMAT=JSON` | 비용 등 상세 정보 |
| `FORMAT=TREE` | 실행 순서를 트리로 표시 |

### 읽는 법

- **한 줄 = 테이블 하나**. 조인하면 테이블 수만큼 줄이 나온다.
- 기본적으로 **위에서 아래 순서**로 실행된다.

| select_type | 뜻 |
|---|---|
| SIMPLE | 조인·서브쿼리 없는 단순 SELECT |
| PRIMARY | 서브쿼리가 있을 때 바깥 쿼리 |
| SUBQUERY | 안쪽 서브쿼리 |

### SHOW WARNINGS

> EXPLAIN 직후 실행하면 **옵티마이저가 고쳐 쓴 쿼리**를 보여준다.

```sql
EXPLAIN SELECT * FROM member WHERE member_id = 1;
SHOW WARNINGS;
```

PK로 1건 조회하면 값이 **상수로 바뀌고** 조건은 `where true`가 된다. → 이미 값을 다 찾아놨다는 뜻

---

## type

> **type** = 테이블에 **접근하는 방식**. 성능을 판단하는 **가장 중요한 컬럼**

위로 갈수록 빠르다.

| type | 뜻 | 예시 |
|---|---|---|
| system | 행이 1개뿐인 테이블 | `FROM (SELECT 1) AS t` |
| const | PK·유니크 인덱스로 **딱 1건** | `WHERE member_id = 1` |
| eq_ref | 조인에서 PK·유니크로 **1건씩** | `JOIN member m ON o.member_id = m.member_id` |
| ref | 일반 인덱스로 **같은 값 여러 건** | `WHERE category_id = 11` |
| range | 인덱스로 **범위** 조회 | `BETWEEN`, `IN`, `>`, `<` |
| index | **인덱스 전체**를 읽음 | `SELECT member_id FROM orders` |
| ALL | **테이블 전체**를 읽음 | 인덱스 없는 컬럼 조건 |

### index vs ALL

| type | 읽는 것 | 속도 |
|---|---|---|
| index | 인덱스 전체 (필요한 컬럼만) | ALL보다 빠를 수 있음 |
| ALL | 테이블 전체 (모든 컬럼) | 가장 느림 |

> **커버링 인덱스** = 필요한 컬럼이 **전부 인덱스 안에 있어서** 테이블을 안 읽어도 되는 상태

**중요한 점:** **range까지는 양호**, **index·ALL이 나오면 개선을 검토**한다.

## possible_keys, key

> **possible_keys** = 쓸 수 있는 **후보** 인덱스
> **key** = 실제로 **사용한** 인덱스

| 상황 | 이유 |
|---|---|
| 후보 여러 개 → 하나만 사용 | 옵티마이저가 더 빠른 쪽을 고름 |
| 후보는 있는데 key = NULL | 거의 전부 읽어야 해서 **풀스캔이 더 빠르다고** 판단 (`category_id > 0`) |
| 후보는 NULL인데 key 있음 | 조건 없이 인덱스 컬럼만 조회 → **커버링**으로 인덱스만 읽음 |

**중요한 점:** 인덱스가 있어도 **옵티마이저가 안 쓸 수 있다.** 꼭 key를 확인한다.

---

## key_len

> **key_len** = 사용한 인덱스의 **바이트 길이** → 복합 인덱스에서 **몇 번째 컬럼까지 썼는지** 알 수 있다.

### 계산법

| 타입 | 크기 |
|---|---|
| BIGINT | 8 |
| INT | 4 |
| VARCHAR(n), utf8mb4 | n × 4 + 2 |
| NULL 허용 | +1 |

예: `email VARCHAR(100) NOT NULL` → 100 × 4 + 2 = **402**

### 복합 인덱스

인덱스: `(category_id BIGINT, product_status VARCHAR(20), price INT)`

| 조건 | 사용한 컬럼 | key_len |
|---|---|---|
| `category_id = 11` | 1개 | 8 |
| + `product_status = 'ACTIVE'` | 2개 | 8 + 82 = **90** |
| + `price = 25000` | 3개 | 90 + 4 = **94** |

**중요한 점:** key_len이 클수록 복합 인덱스를 **더 많이 활용**한 것이다.

---

## ref

> **ref** = 인덱스와 **비교한 값**

| ref 값 | 뜻 |
|---|---|
| const | 상수와 비교 (`member_id = 1`) |
| 테이블.컬럼 | 조인한 다른 테이블 컬럼과 비교 (`shop.o.member_id`) |

---

## rows, filtered

> **rows** = 읽을 것으로 **예상되는 행 수** (추정치)
> **filtered** = 읽은 행 중 **조건을 통과할 예상 비율(%)**

- rows는 통계 기반 추정이라 **실제와 다를 수 있다.** → `COUNT(*)`로 비교해 본다.
- 조인이면 각 줄의 rows를 **곱한 만큼** 읽는다고 보면 된다.
- **최종 예상 행 수 = rows × filtered ÷ 100**

| 조건 | filtered |
|---|---|
| `member_id = 2940001` (인덱스로 다 걸러짐) | 100 |
| + `order_status = 'DELIVERED'` (인덱스 없음) | 낮아짐 |

**중요한 점:** rows는 **작을수록**, filtered는 **100에 가까울수록** 좋다.

## Extra

> **Extra** = 실행에 대한 **추가 정보**

| Extra | 신호 | 뜻 |
|---|---|---|
| Using index | 긍정 | 커버링 인덱스. 테이블을 안 읽음 |
| Using where | 중립 | 인덱스로 찾은 뒤 서버에서 **추가로 거름** |
| Using filesort | 경고 | 인덱스로 정렬 못 해서 **따로 정렬** |
| Using temporary | 위험 | **임시 테이블**을 만들어 처리 |

```sql
-- Using index
SELECT category_id FROM product WHERE category_id = 11;

-- Using where
SELECT * FROM product WHERE category_id = 11 AND product_status = 'ACTIVE';

-- Using filesort
SELECT * FROM product WHERE category_id = 11 ORDER BY price;

-- Using temporary
SELECT category_id, COUNT(*) AS cnt FROM product GROUP BY category_id ORDER BY cnt DESC;
```

**중요한 점:** **filesort·temporary**가 보이면 튜닝 대상이다.
