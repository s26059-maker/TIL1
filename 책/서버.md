# 서버 지식 정리

## OS 계정과 권한

서버에 처음 접속하면 보통 `root`나 관리자 계정이다. 그런데 **애플리케이션을 root로 띄우면 안 된다.** 그 프로세스가 뚫리는 순간 공격자가 서버 전체를 얻기 때문이다. 그래서 서비스마다 전용 계정을 만든다.

```bash
sudo useradd -r -s /sbin/nologin appuser   # -r 시스템 계정, 로그인 불가
sudo chown -R appuser:appuser /opt/myapp
```

`-s /sbin/nologin`이 포인트다. 이 계정으로는 **셸 로그인 자체가 안 된다.** 앱을 실행하는 용도로만 존재하니 로그인할 이유가 없고, 로그인이 안 되면 공격 경로 하나가 줄어든다.

권한은 세 자리 숫자로 본다.

```bash
$ ls -l
-rw-r--r--  1 appuser appuser  1024 app.log      # 644
-rwxr-x---  1 appuser appuser  8192 start.sh     # 750
drwxr-xr-x  2 appuser appuser  4096 logs/        # 755
```

`읽기 4 + 쓰기 2 + 실행 1`을 소유자/그룹/기타 순으로 더한 것이다. 644면 소유자는 읽고 쓰고(6), 나머지는 읽기만(4).

```bash
chmod 600 application-prod.yml   # 소유자만 읽고 쓰기 — 설정 파일은 이렇게
chmod 755 deploy.sh              # 실행 권한 필요한 스크립트
```

**중요한 점**: 디렉터리에서 `x`는 실행이 아니라 **"안으로 들어갈 수 있다"** 는 뜻이다. 읽기 권한만 있고 실행 권한이 없으면 목록은 보여도 그 안의 파일에 접근이 안 된다. 디렉터리에 644를 주고 왜 안 되는지 헤매는 경우가 흔하다.

DB 비밀번호가 든 설정 파일이 644면 서버에 접속한 **모든 계정이 읽을 수 있다.** 600으로 잠그는 게 기본이다.

권한 문제를 만나면 `chmod 777`로 해결하고 싶어지는데, 이건 "아무나 수정하고 실행해도 된다"는 선언이라 문제를 감추는 것뿐이다. 대부분은 소유자를 `chown`으로 바꾸는 게 정답이다.

## 프로세스

서버가 이상하면 제일 먼저 보는 게 프로세스다.

```bash
ps -ef | grep java              # 실행 중인지, PID가 뭔지
top                             # 실시간 CPU/메모리 (htop이 더 보기 편함)
```

`top`에서 봐야 할 건 몇 개 안 된다.

```
%Cpu(s):  12.3 us,  2.1 sy,  0.0 ni, 84.2 id,  1.4 wa
          └ 사용자 프로세스        └ 놀고 있음  └ IO 대기
```

**중요한 점**: `id`(idle)가 높은데 서버가 느리면 CPU 문제가 아니다. 특히 `wa`가 높으면 디스크나 네트워크를 기다리는 중이라는 뜻이다. 앞에서 정리한 IO 병목이 여기서 숫자로 보인다.

`load average`는 헷갈리기 쉬운 지표인데, **CPU 사용률이 아니라 "실행 중이거나 대기 중인 프로세스 수"** 다. 코어가 4개인 서버에서 4.0이면 딱 포화 상태고, 8.0이면 절반은 줄 서 있다는 뜻이다. 코어 수를 모르면 해석이 안 되는 숫자다.

```bash
nproc                           # 코어 수 확인
```

프로세스를 죽일 때도 순서가 있다.

```bash
kill <PID>       # SIGTERM — "정리하고 끝내라". 앱이 종료 훅을 실행할 수 있음
kill -9 <PID>    # SIGKILL — 즉시 강제 종료. 정리 못 함
```

**중요한 점**: `-9`를 먼저 쓰면 안 된다. 처리 중이던 요청이 잘리고, 커넥션이 정리되지 않고, 버퍼에 있던 로그가 사라진다. 일반 `kill`을 먼저 주고 몇 초 기다린 뒤에도 안 죽으면 그때 `-9`다.

애플리케이션은 `nohup`이나 `&`로 띄우지 말고 **systemd에 등록**하는 게 좋다. 서버가 재부팅돼도 자동으로 뜨고, 죽으면 다시 살아나고, 로그도 한 곳으로 모인다.

```bash
sudo systemctl status myapp
sudo systemctl restart myapp
sudo journalctl -u myapp -f     # 로그 실시간 확인
```

## 디스크 용량

서버 장애의 은근히 큰 비중이 디스크 꽉 참이다. 이게 무서운 이유는 **증상이 엉뚱하게 나타나기** 때문이다. DB가 쓰기를 못 하고, 로그가 안 남고, 세션 파일이 안 만들어지는데 원인은 그냥 용량이다.

```bash
df -h                           # 전체 사용량 (제일 먼저)
du -sh /var/log/*               # 어느 디렉터리가 큰지
du -sh * | sort -rh | head -10  # 현재 위치에서 큰 것 10개
```

**중요한 점**: `df`에 여유가 있는데도 "No space left"가 뜨면 **inode**를 봐야 한다. inode는 파일 하나당 하나씩 쓰는 관리 정보인데, 개수 자체에 한계가 있다. 아주 작은 파일이 수백만 개 쌓이면 용량은 남았는데 파일을 못 만든다.

```bash
df -i                           # inode 사용량
```

**중요한 점**: 더 헷갈리는 함정이 있다. **로그 파일을 `rm`으로 지웠는데 용량이 안 줄어드는 경우다.** 애플리케이션이 그 파일을 열어둔 상태면 OS는 공간을 회수하지 않는다. 프로세스를 재시작하거나 이렇게 비워야 한다.

```bash
> /var/log/myapp.log            # 파일은 두고 내용만 비움
lsof | grep deleted             # 지워졌는데 아직 잡고 있는 파일 확인
```

애초에 이런 일이 없게 로그 로테이션을 걸어둔다.

```bash
# /etc/logrotate.d/myapp
/opt/myapp/logs/*.log {
    daily
    rotate 14        # 14일치 보관
    compress
    missingok
}
```

## 파일 디스크립터 제한

리눅스는 **열려 있는 모든 것을 파일로 다룬다.** 진짜 파일뿐 아니라 소켓, 파이프까지 전부 파일 디스크립터(fd) 하나를 차지한다. 그래서 **네트워크 연결 하나 = fd 하나**다.

문제는 기본 제한이 1024인 경우가 많다는 것이다. 동시 접속이 조금만 늘어도 이 한도에 걸린다.

```
java.net.SocketException: Too many open files
```

이 에러가 보이면 십중팔구 fd 부족이다. 코드 문제로 보이지만 OS 설정 문제다.

```bash
ulimit -n                       # 현재 셸의 제한
cat /proc/<PID>/limits          # 실행 중인 프로세스의 실제 제한
ls /proc/<PID>/fd | wc -l       # 지금 몇 개 쓰고 있는지
```

**중요한 점**: `ulimit -n 65535`로 바꿔도 **그 셸에서만 적용된다.** 재부팅하거나 다른 방식으로 띄우면 원래대로다. 영구 설정은 따로 해야 하고, systemd로 띄운다면 `ulimit`이 아니라 서비스 파일에 넣어야 먹는다.

```ini
[Service]
LimitNOFILE=65535
```

**중요한 점**: 한도를 올려도 계속 터지면 **fd가 새고 있는 것**이다. 커넥션이나 스트림을 닫지 않는 코드가 어딘가 있다는 뜻이라, 숫자만 올리면 터지는 시점이 미뤄질 뿐이다. `ls /proc/<PID>/fd`로 뭐가 쌓이는지 보면 원인이 드러난다.

## 시간 동기화

서버 시계는 그냥 두면 조금씩 어긋난다. 하루에 몇 초씩 밀리는 건 정상이고, 그게 쌓이면 문제가 된다.

- 로그 타임스탬프가 서버마다 달라서 **장애 원인 추적이 불가능**해진다
- JWT 만료 검증이 어긋난다 (시계가 앞선 서버에서는 멀쩡한 토큰이 만료로 나온다)
- TLS 인증서 검증이 실패한다
- 배치가 중복 실행되거나 건너뛴다

```bash
timedatectl                     # 현재 시간, 타임존, 동기화 상태
timedatectl set-timezone Asia/Seoul
```

`System clock synchronized: yes`가 떠 있어야 정상이다. 아니라면 NTP 데몬이 안 돌고 있는 것이다.

**중요한 점**: 서버 타임존은 **UTC로 두고 애플리케이션에서 변환**하는 게 표준이다. 서버마다 타임존이 다르면 로그를 맞춰 보는 게 지옥이 된다. 특히 여러 지역에 서버가 있으면 더 그렇다.

애플리케이션, DB, 서버 OS의 타임존이 제각각인 경우가 정말 흔하다. 데이터가 9시간씩 밀려서 저장되는 사고가 여기서 나온다. 셋 다 확인해야 한다.

```sql
SELECT @@global.time_zone, @@session.time_zone, NOW();
```

## 크론을 이용한 스케줄링

정해진 시간에 명령을 실행시키는 기능이다.

```bash
crontab -e      # 편집
crontab -l      # 확인
```

형식은 다섯 자리다.

```
분  시  일  월  요일   명령
0   3   *   *   *     /opt/myapp/backup.sh        # 매일 새벽 3시
*/10 *  *   *   *     /opt/myapp/health.sh        # 10분마다
0   0   1   *   *     /opt/myapp/monthly.sh       # 매월 1일 자정
0   9   *   *   1-5   /opt/myapp/report.sh        # 평일 오전 9시
```

**중요한 점**: 크론 실패의 90%는 **환경 변수 때문**이다. 크론은 로그인 셸이 아니라서 `PATH`가 최소한만 잡혀 있고, `.bashrc`도 읽지 않는다. 터미널에서는 잘 되던 스크립트가 크론에서만 조용히 실패한다. **절대 경로를 쓰는 게 답이다.**

```bash
# 안 됨
0 3 * * * java -jar /opt/myapp/batch.jar

# 됨
0 3 * * * /usr/bin/java -jar /opt/myapp/batch.jar
```

**중요한 점**: 출력을 반드시 파일로 남긴다. 안 그러면 실패해도 알 수가 없다.

```bash
0 3 * * * /opt/myapp/backup.sh >> /var/log/backup.log 2>&1
```

`2>&1`이 핵심인데, **에러 출력까지 같이 남기라는 뜻**이다. 이게 없으면 정상 메시지만 쌓이고 정작 실패 원인은 사라진다.

**중요한 점**: 서버가 여러 대인데 같은 크론이 걸려 있으면 **배치가 대수만큼 중복 실행된다.** 서버 한 대만 지정하거나, 앞에서 다룬 잠금으로 한 대만 실행되게 해야 한다.

## 별칭

`alias`는 긴 명령을 짧은 이름으로 바꿔두는 것이다. 서버에 자주 들어가면 체감 효율이 크다.

```bash
alias ll='ls -alh'
alias logs='tail -f /opt/myapp/logs/app.log'
alias appstatus='sudo systemctl status myapp'
alias ports='sudo ss -tulpn'
```

터미널에서 그냥 치면 그 세션에서만 살아 있다. 영구로 쓰려면 `~/.bashrc`에 넣고 다시 읽는다.

```bash
echo "alias ll='ls -alh'" >> ~/.bashrc
source ~/.bashrc
```

**중요한 점**: 위험한 명령에 안전장치를 거는 용도가 특히 유용하다.

```bash
alias rm='rm -i'                # 지울 때 물어보게
alias cp='cp -i'
```

**중요한 점**: 반대로 **alias가 사고를 만들기도 한다.** 스크립트 안에서는 alias가 적용되지 않으므로, alias에 익숙해진 상태로 스크립트를 짜면 의도와 다르게 동작한다. 그리고 남의 서버에서 내 alias가 없다고 당황하지 않으려면 원래 명령도 알고 있어야 한다.

## 네트워크 정보 확인

"서버는 떴는데 접속이 안 된다"를 풀 때 쓰는 도구들이다. 확인 순서가 중요하다.

### 1. 프로세스가 포트를 잡고 있나

```bash
sudo ss -tulpn                  # 열려 있는 포트 + 프로세스 (netstat 후속)
sudo ss -tulpn | grep 8080
```

```
LISTEN  0  100  127.0.0.1:8080   users:(("java",pid=1234,fd=45))
              └──────────┘
```

**중요한 점**: 여기서 `127.0.0.1:8080`과 `0.0.0.0:8080`은 완전히 다르다. **127.0.0.1은 서버 자신만 접속 가능**하다는 뜻이라, 외부에서는 절대 안 들어온다. 서버 안에서 `curl`은 되는데 밖에서는 안 될 때 원인이 대부분 이거다.

### 2. 포트 충돌

배포할 때 자주 만난다.

```
Web server failed to start. Port 8080 was already in use.
```

이전 프로세스가 안 죽고 남아 있는 것이다.

```bash
sudo lsof -i :8080              # 누가 쓰는지
sudo kill <PID>
```

**중요한 점**: 프로세스를 분명히 죽였는데도 포트가 안 열리는 경우가 있다. `ss`로 보면 상태가 `TIME_WAIT`인데, 이건 정상적인 TCP 동작이다. 연결을 닫은 뒤에도 뒤늦게 오는 패킷을 처리하려고 잠시(보통 1분 내외) 남겨두는 것이라, **기다리면 풀린다.**

### 3. 방화벽

프로세스는 잘 떠 있는데 밖에서 안 들어오면 그다음은 방화벽이다.

```bash
sudo ufw status                 # Ubuntu
sudo firewall-cmd --list-all    # CentOS/RHEL
```

클라우드라면 여기에 더해 **보안 그룹**도 봐야 한다. OS 방화벽과 클라우드 보안 그룹은 별개라, 둘 다 열려 있어야 통한다.

### 4. 상대편까지 닿나

```bash
ping db-server                  # 서버 자체가 살아있나 (ICMP)
curl -v telnet://db-server:3306 # 그 포트까지 닿나
dig api.example.com             # DNS가 제대로 풀리나
```

**중요한 점**: `ping`이 되는데 접속이 안 되는 건 흔한 상황이다. **ping은 서버가 켜져 있는지만 확인**할 뿐 특정 포트가 열렸는지는 알려주지 않는다. 포트 확인은 `curl`이나 `telnet`으로 해야 한다. 반대로 ping은 막아두고 서비스 포트만 여는 서버도 많아서, ping이 안 된다고 서버가 죽은 것도 아니다.

문제를 만나면 항상 **가까운 곳부터 바깥으로** 확인한다. 프로세스가 떴나 → 포트를 잡았나 → 어느 주소로 잡았나 → 방화벽이 열렸나 → DNS가 맞나. 순서를 지키면 대부분 몇 분 안에 원인이 나온다.
