# 네트워크 정리

## 네트워크와 라우터

데이터는 통째로 가지 않는다. 작은 조각으로 잘려서 각각 따로 출발하는데, 이 조각을 **패킷**이라고 한다.

패킷 하나에는 실제 데이터 앞에 주소 정보가 붙는다. 택배 상자에 송장이 붙는 것과 같고, 계층마다 자기 송장을 하나씩 더 붙인다.

```
[ 이더넷 헤더 ][ IP 헤더 ][ TCP 헤더 ][ 실제 데이터 ]
  MAC 주소       IP 주소     포트 번호
  (옆 장비까지)  (최종 목적지) (어느 프로그램에게)
```

여기서 헷갈리기 쉬운 게 **MAC 주소와 IP 주소가 둘 다 있는 이유**다. IP는 최종 목적지고, MAC은 **바로 다음 장비**의 주소다. 패킷이 라우터를 하나 지날 때마다 IP는 그대로인데 MAC은 계속 바뀐다. 최종 목적지는 그대로지만 다음에 넘길 상대는 매번 달라지기 때문이다.

**중요한 점**: 이 구조 때문에 라우터는 **자기 다음 한 칸만 안다.** 전체 경로를 아는 장비는 아무 데도 없다. 각 라우터가 "이 목적지면 저쪽으로"라는 판단만 반복해서 결과적으로 도착하는 방식이라, 중간에 한 곳이 죽어도 다른 길로 돌아갈 수 있다.

경로는 직접 볼 수 있다.

```bash
traceroute google.com     # 거쳐가는 라우터들이 순서대로 나옴
mtr google.com            # traceroute + ping을 계속 돌려줌 (실무에서 더 유용)
```

한 칸 건너가는 걸 **홉(hop)** 이라고 한다. 목적지까지 보통 10~20홉 정도 나온다.

**중요한 점**: 패킷은 순서가 뒤바뀌거나 유실될 수 있다. 각자 다른 길로 가기 때문이다. 그걸 다시 맞추고 재전송하는 건 아래에서 볼 TCP의 일이지 네트워크 자체가 해주는 게 아니다.

스위치와 라우터를 구분하면 좋다. **스위치는 같은 네트워크 안에서** MAC 주소로 전달하고, **라우터는 다른 네트워크로** IP를 보고 넘긴다. 집 공유기는 사실 이 둘에 아래의 NAT까지 합쳐진 장비다.

## IP 주소와 도메인

IP는 네트워크상의 주소다. IPv4는 점으로 나뉜 네 자리이고 각 칸은 0~255다.

```
192.168.0.15
└─────┘└──┘
 네트워크  호스트
 (어느 동네)  (그 동네 몇 호)
```

어디까지가 동네이고 어디부터가 호수인지를 정하는 게 **서브넷 마스크**다. 요즘은 `/24` 같은 CIDR 표기를 쓴다.

```
192.168.0.0/24    → 앞 24비트가 네트워크. 192.168.0.1 ~ 192.168.0.254 사용 가능
10.0.0.0/16       → 앞 16비트가 네트워크. 훨씬 넓은 대역
```

**중요한 점**: 같은 네트워크 안에 있으면 라우터를 거치지 않고 직접 통신한다. 그래서 클라우드에서 서버끼리 통신이 안 될 때 **서브넷이 다른데 라우팅이 없는 경우**를 먼저 의심하면 된다.

### 공인 IP와 사설 IP

IP는 크게 두 종류로 나뉜다.

- **공인 IP** — 인터넷 전체에서 유일한 주소. 국제기구가 관리하고, 통신사나 클라우드에서 할당받아 쓴다. 밖에서 찾아올 수 있는 주소다.
- **사설 IP** — 내부에서만 쓰는 주소. 아무나 마음대로 써도 되고, 그래서 **전 세계에서 중복된다.**

사설용으로 예약된 대역은 정해져 있다.

```
10.0.0.0    ~ 10.255.255.255     (/8)     클라우드 VPC에서 주로 사용
172.16.0.0  ~ 172.31.255.255     (/12)    도커 기본 대역이 여기 있음
192.168.0.0 ~ 192.168.255.255    (/16)    가정용 공유기 기본값
```

**중요한 점**: 라우터는 이 대역을 인터넷으로 넘기지 않는다. 넘겨봐야 전 세계에 같은 주소가 수억 개라 어디로 보낼지 결정할 수 없기 때문이다. 그래서 사설 IP끼리는 같은 내부망 안에서만 통한다.

```bash
ip addr          # 내 IP 확인 (ifconfig 후속) — 보통 사설 IP가 나옴
curl ifconfig.me # 밖에서 보이는 내 공인 IP
```

**중요한 점**: 이 둘의 값이 다른 게 정상이다. 서버 안에서 `ip addr`을 쳤을 때 `10.0.x.x`가 나오고 `curl ifconfig.me`는 전혀 다른 주소가 나오는 건 고장이 아니라, 아래에서 볼 NAT가 중간에서 바꿔주고 있다는 뜻이다.

사설 IP는 그 자체로 보안 수단이 된다. DB 서버에 공인 IP를 아예 주지 않으면 인터넷에서는 존재조차 알 수 없다. 방화벽을 잘못 설정할 여지도 없어진다.

### 고정 IP와 동적 IP

주소를 계속 유지하느냐에 따라 나뉜다.

**동적 IP**는 접속할 때마다 그때그때 빌려 쓰는 방식이고, 이걸 자동으로 나눠주는 게 **DHCP**다. 집 인터넷이나 사내망 노트북이 여기 해당한다. 주소가 남아돌지 않아도 되고 설정할 게 없다는 게 장점이다.

```
1. 새 기기: "IP 좀 주세요" (브로드캐스트)
2. DHCP 서버: "192.168.0.15 쓰세요, 유효기간 24시간"
3. 기기가 그 주소를 사용, 만료 전에 연장 요청
```

**고정 IP**는 주소를 못 박아 두는 것이다. 주소가 바뀌면 안 되는 대상에 쓴다.

**중요한 점**: 서버는 원칙적으로 고정 IP다. DNS가 특정 IP를 가리키고 있는데 그 IP가 바뀌면 도메인이 엉뚱한 곳을 가리키게 되고, 방화벽 허용 목록에 등록해둔 주소도 전부 무의미해진다.

클라우드에서 자주 겪는 함정이 하나 있다. **인스턴스를 껐다 켜면 공인 IP가 바뀌는 경우가 많다.** 그래서 고정이 필요하면 별도로 발급받아 붙여야 한다(AWS의 탄력적 IP, GCP의 고정 외부 IP). 개발 서버를 재부팅했더니 접속이 안 되고 방화벽 등록도 다 풀린 상황이 여기서 나온다.

반대로 **내부 통신은 IP가 아니라 DNS 이름으로 하는 게 좋다.** 클라우드는 내부 DNS를 제공하므로 `db.internal` 같은 이름을 쓰면 서버를 교체해도 설정을 안 고쳐도 된다. IP를 설정 파일에 직접 박아두면 인스턴스를 바꿀 때마다 배포가 따라온다.

`127.0.0.1`은 특별하다. **자기 자신**을 가리키는 주소라 패킷이 랜카드로 나가지도 않는다. 앞에서 본 "서버 안에서 curl은 되는데 밖에서는 안 되는" 문제가 여기서 나온다.

### 도메인과 DNS

사람은 IP를 못 외우니 이름을 붙이고, 그 이름을 IP로 바꿔주는 게 **DNS**다.

```bash
dig api.example.com       # 어떤 IP로 풀리는지 + 응답 시간
dig api.example.com +short
```

주요 레코드는 몇 개만 알면 된다.

```
A      도메인 → IPv4 주소
AAAA   도메인 → IPv6 주소
CNAME  도메인 → 다른 도메인 (별칭)
MX     메일 서버
TXT    검증용 문자열 (도메인 소유 확인 등)
```

**중요한 점**: DNS 응답에는 **TTL**(캐시 유효 시간)이 붙는다. 그래서 IP를 바꿔도 즉시 반영되지 않는다. 서버 이전을 계획한다면 **미리 TTL을 짧게 줄여놓고** 옮겨야 한다. TTL이 86400(하루)인 상태로 옮기면 하루 동안 절반은 옛날 서버로 간다.

**중요한 점**: "배포했는데 옛날 페이지가 보여요"의 원인이 DNS 캐시인 경우가 많다. 캐시는 브라우저, OS, 회사 DNS 서버, ISP 등 여러 층에 있어서 한 곳만 비워서는 안 된다.

**중요한 점**: 도메인은 IP 하나에만 묶이지 않는다. 여러 IP를 응답해서 부하를 나누기도 하고, 접속 지역에 따라 다른 IP를 주기도 한다. 그래서 `ping`으로 나온 IP가 항상 같은 서버라는 보장이 없다.

## NAT

집에 기기가 10대인데 인터넷에 나가는 공인 IP는 하나다. 이걸 가능하게 해주는 게 **NAT(주소 변환)** 다.

원리는 **포트 번호로 구분하는 것**이다. 공유기가 나가는 패킷마다 출발지를 자기 공인 IP로 바꾸면서, 포트 번호를 하나씩 배정해 표로 기억해둔다.

```
내부                          공유기 변환표
192.168.0.10:52341   ←→   1.2.3.4:40001
192.168.0.11:49820   ←→   1.2.3.4:40002
```

응답이 `1.2.3.4:40001`로 돌아오면 표를 보고 원래 기기에게 전달한다.

**중요한 점**: 여기서 중요한 성질이 나온다. **NAT는 나갈 때만 표가 만들어진다.** 그래서 밖에서 먼저 들어오는 연결은 누구에게 줘야 할지 알 수가 없어서 그냥 버려진다. 집에서 서버를 돌려도 외부에서 접속이 안 되는 이유가 이것이고, 동시에 **NAT가 방화벽 비슷한 효과를 내는** 이유이기도 하다.

밖에서 들어오게 하려면 "이 포트로 오면 이 기기로 보내라"고 미리 등록해야 하는데, 이게 **포트 포워딩**이다.

```
공유기 8080  →  192.168.0.10:8080
```

**중요한 점**: 클라우드에서도 같은 일이 일어난다. EC2 인스턴스가 갖는 사설 IP와 붙어 있는 공인 IP는 별개이고, 그 사이를 NAT가 이어준다. 그래서 서버 안에서 `ip addr`을 쳐도 **공인 IP는 안 보인다.** 이걸 모르면 설정에서 한참 헤맨다.

**중요한 점**: 사설 서브넷에 있는 서버가 외부로 나가기만 해야 할 때(패키지 설치 등) NAT 게이트웨이를 둔다. 나가는 건 되고 들어오는 건 안 되는 구조라, DB 서버를 여기 두는 게 기본 구성이다.

## VPN

인터넷은 기본적으로 공개된 길이다. VPN은 그 위에 **암호화된 터널**을 만들어서, 물리적으로 떨어진 곳을 마치 같은 사설망에 있는 것처럼 연결한다.

동작은 이렇다. 내 패킷을 통째로 암호화해서 **또 다른 패킷 안에 넣어** 보낸다. 중간에서 보면 VPN 서버로 가는 알 수 없는 데이터 덩어리일 뿐이고, 실제 목적지와 내용은 안 보인다. 이걸 **터널링**이라고 한다.

```
[ 새 IP 헤더 ][ 암호화된 { 원래 IP 헤더 + 데이터 } ]
   VPN 서버로            여기는 안 보임
```

VPN에 붙으면 사설망 주소를 하나 받는다.

```bash
ip addr            # tun0 같은 가상 인터페이스가 생김
ping 10.0.1.50     # 회사 내부 DB에 직접 접근 가능
```

**중요한 점**: 실무에서 VPN을 쓰는 이유는 대부분 하나다. **DB나 관리 서버를 인터넷에 안 열기 위해서.** DB 포트를 전 세계에 열어두고 비밀번호로 지키는 것보다, 아예 인터넷에서 안 보이게 하고 VPN을 통과한 사람만 접근하게 하는 게 훨씬 안전하다. 앞에서 본 심층 방어의 전형적인 예다.

**중요한 점**: 비슷한 목적으로 더 가볍게 쓰는 게 **SSH 터널**이다. 서버 하나에만 접근하면 될 때는 VPN을 구축할 것 없이 이걸 쓴다.

```bash
ssh -L 3306:db-server:3306 user@bastion
# 이제 내 컴퓨터의 localhost:3306 이 원격 DB로 연결됨
```

중간의 `bastion`은 **외부에서 접속 가능한 유일한 서버**를 말한다. 여기만 잘 지키면 나머지 서버는 인터넷에 노출할 필요가 없다.

## 프로토콜

프로토콜은 "이런 형식으로 주고받자"는 약속이다. 계층별로 역할이 나뉘어 있다.

```
응용 계층    HTTP, DNS, SSH        무슨 내용을 주고받나
전송 계층    TCP, UDP              어느 프로그램에게, 제대로 갔나
인터넷 계층  IP                    어디로 보내나
링크 계층    이더넷, Wi-Fi         옆 장비까지 어떻게 넘기나
```

**중요한 점**: 계층이 나뉜 덕분에 위층은 아래를 몰라도 된다. HTTP는 Wi-Fi인지 유선인지 신경 쓰지 않고, IP는 그 안의 내용이 HTTP인지 모른다. 그래서 장애를 볼 때도 층별로 나눠서 확인하면 범위가 빠르게 좁혀진다.

### TCP와 UDP

같은 전송 계층인데 성격이 정반대다.

**TCP**는 연결을 맺고 시작한다. 이게 **3-way handshake**다.

```
클라이언트 → SYN     → 서버      "연결할래?"
클라이언트 ← SYN+ACK ← 서버      "그래, 나도 할래"
클라이언트 → ACK     → 서버      "확인"
```

이 왕복 때문에 **연결 하나 맺는 데만 1RTT가 든다.** 앞에서 HTTP 커넥션 풀로 연결을 재사용해야 한다고 한 이유가 이 비용이다. HTTPS라면 여기에 TLS 협상이 더 붙는다.

연결 후에는 순서 번호와 확인 응답으로 **유실된 패킷을 재전송하고 순서를 맞춰준다.** 대신 그만큼 느리고 오버헤드가 있다.

**UDP**는 이 모든 걸 안 한다. 그냥 보낸다. 도착 여부도 순서도 보장하지 않는 대신 빠르다. DNS 조회, 실시간 스트리밍, 게임처럼 **한 조각 놓쳐도 다음 걸 받는 게 나은** 경우에 쓴다.

**중요한 점**: TCP가 "안전"하고 UDP가 "불안정"한 게 아니라, **보장을 어디서 할 것인가의 선택**이다. UDP를 쓰면서 필요한 보장만 애플리케이션에서 직접 구현하는 방식도 흔하다. HTTP/3가 정확히 그렇게 만들어졌다.

### HTTP

HTTP는 요청과 응답이 텍스트로 오가는 단순한 프로토콜이다.

```bash
curl -v https://api.example.com/users/1
```

```
> GET /users/1 HTTP/1.1        요청 라인
> Host: api.example.com        헤더
>
< HTTP/1.1 200 OK              상태 코드
< Content-Type: application/json
<
< {"id":1,"name":"..."}        본문
```

버전별 차이는 결국 **연결을 얼마나 아끼느냐**의 이야기다.

- **HTTP/1.1** — 연결을 재사용하지만, 한 연결에서 요청을 하나씩 순서대로 처리한다. 앞 요청이 느리면 뒤가 막힌다.
- **HTTP/2** — 한 연결에서 여러 요청을 동시에 주고받는다. 헤더도 압축한다.
- **HTTP/3** — TCP를 버리고 UDP 위에서 동작한다. 그 기반이 QUIC이다.

### QUIC

HTTP/2가 한 연결에서 요청을 동시에 보내도록 만들었는데, 문제가 하나 남았다. **TCP가 순서를 보장해주는 게 오히려 발목을 잡는다는 것이다.**

TCP는 패킷 하나가 유실되면 그게 재전송돼서 도착할 때까지 뒤에 온 패킷들을 애플리케이션에 넘기지 않는다. 순서를 지켜야 하기 때문이다. 그래서 이미지 요청 하나의 패킷이 빠졌을 뿐인데, 같은 연결로 오던 CSS와 JS까지 전부 대기한다. 이걸 **HOL 블로킹**이라고 한다. HTTP/2가 위층에서 요청을 나눠놨는데, 아래층인 TCP가 다시 하나로 묶어버리는 셈이다.

TCP는 OS 커널에 박혀 있어서 고칠 수가 없다. 그래서 QUIC은 **아무것도 보장하지 않는 UDP를 깔고, 필요한 기능을 그 위에 다시 만드는** 쪽을 택했다.

```
HTTP/2                        HTTP/3
┌──────────┐                  ┌──────────┐
│  HTTP/2  │                  │  HTTP/3  │
├──────────┤                  ├──────────┤
│   TLS    │                  │   QUIC   │ ← 재전송·순서·암호화를 여기서
├──────────┤                  ├──────────┤
│   TCP    │ ← 커널, 못 고침   │   UDP    │ ← 그냥 통로 역할만
└──────────┘                  └──────────┘
```

얻는 게 세 가지다.

**스트림별 독립** — 요청마다 스트림을 나누고 각각 따로 순서를 관리한다. 이미지 패킷이 빠져도 CSS는 그대로 처리된다. HOL 블로킹이 사라진다.

**연결이 빨라진다** — TCP는 3-way handshake 후에 TLS 협상을 또 해서 보통 2~3RTT가 든다. QUIC은 연결 수립과 암호화 협상을 **하나로 합쳐서 1RTT**에 끝낸다. 한 번 접속했던 서버라면 0-RTT로 바로 데이터를 보내기도 한다.

**연결 마이그레이션** — TCP 연결은 출발지 IP와 포트로 식별되기 때문에, Wi-Fi에서 LTE로 바뀌면 IP가 바뀌어 연결이 끊긴다. QUIC은 연결에 별도 ID를 붙여서 식별하므로 **IP가 바뀌어도 연결이 유지된다.** 모바일에서 체감이 가장 큰 부분이다.

**중요한 점**: 암호화가 선택이 아니라 QUIC에 내장돼 있다. 그래서 HTTP/3에는 평문 버전이 없다.

단점도 있다. UDP를 막아두는 방화벽이 아직 있어서, 브라우저는 QUIC이 안 되면 조용히 TCP로 되돌아간다(폴백). 그리고 TCP는 커널이 처리하는데 QUIC은 사용자 영역에서 돌아가서 **CPU를 더 쓴다.** 트래픽이 아주 많은 서버에서는 이게 실제 비용이 된다.

서버에서 직접 켜기보다 CDN이나 로드밸런서 단에서 처리하는 경우가 대부분이다. 사용자와 가까운 앞단에서만 QUIC을 쓰고, 그 뒤 내부 통신은 그냥 TCP로 하는 구성이 흔하다.

HTTPS는 별개의 프로토콜이 아니라 **HTTP를 TLS로 감싼 것**이다. 그래서 서버 입장에서 다루는 내용은 똑같고, 암호화는 그 아래 층에서 알아서 처리된다.

상태 코드는 의미대로 써야 한다. 특히 **401은 인증 실패(누군지 모름), 403은 인가 실패(누군지는 알지만 권한 없음)** 이다. 앞에서 정리한 인증과 인가의 구분이 그대로 코드로 나타난다. 에러가 났는데 200을 주고 본문에 실패를 담는 API는 클라이언트와 중간 장비 모두를 혼란스럽게 만든다.
