## 비동기 연동

동기 호출은 상대가 답할 때까지 내 스레드가 멈춰 서 있다. 그래서 내 응답 시간은 항상 "내 처리 시간 + 외부 응답 시간"이 되고, 외부가 느려지면 나도 같이 느려진다.

비동기 연동은 이 연결을 끊는다. 할 일을 어딘가에 맡겨두고 사용자에게는 먼저 응답한다. 실제 처리는 뒤에서 일어난다.

판단 기준은 하나다. **지금 이 결과가 있어야 사용자에게 응답할 수 있는가?**

- 결제 승인 → 결과가 있어야 주문이 성립한다. 동기.
- 주문 완료 알림톡, 통계 집계, 검색 인덱스 갱신 → 없어도 응답할 수 있다. 비동기.

**중요한 점**: 비동기로 바꿔도 전체 작업이 빨라지는 건 아니다. 사용자가 기다리는 구간에서 빼낸 것뿐이다. 대신 대가를 치른다. 처리 시점을 알 수 없고, 실패해도 사용자는 모른다. 그래서 비동기 연동 설계의 절반은 "실패했을 때 어떻게 알아채고 되살리나"다.

## 별도 스레드를 이용한 비동기 연동

가장 간단한 방법. 다른 스레드에 던져놓고 요청 스레드는 바로 돌아간다.

```java
@Service
public class OrderService {
    @Transactional
    public void order(Order order) {
        orderRepository.save(order);
        eventPublisher.publishEvent(new OrderPlaced(order.getId()));
    }
}

@Component
public class NotificationHandler {
    @Async("notificationExecutor")
    @TransactionalEventListener(phase = AFTER_COMMIT)
    public void handle(OrderPlaced event) {
        notificationClient.send(event.orderId());
    }
}
```

**중요한 점**: `AFTER_COMMIT`이 핵심이다. 커밋 전에 발행하면, 알림은 나갔는데 주문 저장은 롤백되는 상황이 생긴다. 존재하지 않는 주문에 대한 알림이 날아간다.

스레드 풀은 반드시 따로 만든다. 기본 설정을 쓰면 요청마다 스레드를 새로 만들거나 톰캣 스레드를 공유해서, 비동기로 뺀 작업이 오히려 서버 전체를 잡아먹는다. 풀 크기와 큐 크기, 큐가 찼을 때 어떻게 할지(버릴지, 호출한 쪽에서 직접 처리할지)까지 정해야 한다.

결정적인 한계는 **서버가 죽으면 메모리에 있던 작업이 통째로 사라진다**는 것이다. 재배포 한 번에 처리 중이던 작업이 증발하고, 아무 기록도 남지 않는다. 그래서 이 방식은 잃어도 되는 작업에만 쓴다. 돈이나 상태가 걸린 건 아래 방법으로 가야 한다.

## 메시징을 이용한 비동기 연동

중간에 메시지 브로커(Kafka, RabbitMQ, SQS)를 둔다. 보내는 쪽은 브로커에 넣고 끝내고, 받는 쪽은 자기 속도로 꺼내 쓴다.

메모리 스레드 방식과 결정적으로 다른 점은 **메시지가 브로커에 저장된다**는 것이다. 소비자가 죽어 있어도 메시지는 남아 있고, 살아나면 밀린 걸 처리한다. 트래픽이 몰려도 브로커가 완충해주니 소비자가 감당 못 할 속도로 밀려들지 않는다.

### 이벤트와 커맨드

같은 메시지지만 의미가 다르다.

**커맨드는 "이걸 해줘"다.** 수신자가 정해져 있고, 보내는 쪽이 결과에 관심이 있다. 이름은 명령형이다.

```java
record SendEmailCommand(String to, String template, Map<String, String> params) {}
```

**이벤트는 "이런 일이 일어났다"다.** 이미 벌어진 사실을 알릴 뿐이라 이름은 과거형이고, 누가 받아서 뭘 하는지 보내는 쪽은 모른다.

```java
record OrderPlaced(Long orderId, Long userId, int amount, Instant occurredAt) {}
```

**중요한 점**: 차이는 결합도다. 이벤트를 쓰면 나중에 "주문 시 포인트 적립"이 추가돼도 주문 서비스 코드는 그대로다. 새 소비자가 같은 이벤트를 하나 더 구독하면 끝. 반면 커맨드는 흐름이 명확해서 추적과 디버깅이 쉽다.

흔한 실수는 이름만 이벤트인 커맨드를 만드는 것이다. `OrderPlaced` 안에 "재고를 차감하라"는 지시나 재고 서비스 전용 필드가 들어가면, 겉모습만 이벤트고 실제로는 커맨드다. 이벤트는 **일어난 사실만** 담아야 한다.

### 메시징에서 고려할 것

**전달 보장** — 이론상 세 가지지만 현실적으로 쓰이는 건 at-least-once(최소 한 번)다. 즉 **같은 메시지가 두 번 올 수 있다.** 브로커가 확인 응답을 못 받으면 다시 보내기 때문이다. 그래서 소비자는 반드시 멱등해야 한다. 메시지 ID를 저장해두고 이미 처리한 건 건너뛰는 식이다.

**순서** — 전체 순서는 보장되지 않는다. Kafka라면 같은 파티션 안에서만 순서가 지켜지므로, 순서가 중요한 것끼리는 같은 키를 쓴다. 주문 ID를 키로 쓰면 그 주문의 생성/수정/취소는 순서대로 처리된다.

**메시지에 뭘 담을까** — ID만 담고 소비자가 API로 조회하게 할 수도 있고, 필요한 데이터를 다 담을 수도 있다. ID만 담으면 메시지는 가볍지만 소비자가 조회하는 시점의 데이터를 보게 되어, 이미 바뀐 뒤의 값을 읽는 문제가 생긴다. 다 담으면 그 시점의 사실이 그대로 보존되지만 스키마가 커지고 생산자-소비자 결합이 생긴다. 보통은 **소비자가 판단하는 데 필요한 최소한**을 담는 쪽으로 간다.

**실패 처리** — 처리에 실패한 메시지를 무한 재시도하면 그 뒤 메시지가 전부 막힌다. 몇 번 재시도 후에는 DLQ(처리 실패 메시지를 따로 모아두는 큐)로 보내고 다음으로 넘어가야 한다. DLQ는 만들어두는 것보다 **쌓이면 알람이 오게 하는 것**이 중요하다.

**스키마 변경** — 생산자와 소비자가 따로 배포되므로, 새 필드를 추가하는 건 안전하지만 필드를 지우거나 타입을 바꾸면 구버전 소비자가 깨진다. 삭제는 "더 이상 안 쓰기 → 한참 뒤 제거" 순으로 간다.

**지연 모니터링** — 소비자가 생산 속도를 못 따라가면 lag이 쌓인다. 이건 장애가 아니라 정상 동작처럼 보이기 때문에 지표를 안 보면 며칠씩 모른다.

## 트랜잭션 아웃박스 패턴

메시징을 도입하면 새 문제가 하나 생긴다.

```java
@Transactional
public void order(Order order) {
    orderRepository.save(order);       // DB
    kafkaTemplate.send("order", event); // 브로커 — 별개 시스템
}
```

DB와 브로커는 하나의 트랜잭션으로 묶이지 않는다. DB는 커밋됐는데 발행이 실패하거나, 발행은 됐는데 DB가 롤백될 수 있다. 이걸 이중 쓰기(dual write) 문제라고 한다.

해결책은 **발행할 메시지를 DB에 같이 저장하는 것**이다. 같은 트랜잭션이니 원자적으로 묶인다.

```sql
CREATE TABLE outbox (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    event_type  VARCHAR(100),
    payload     JSON,
    published   BOOLEAN DEFAULT FALSE,
    created_at  DATETIME
);
```

```java
@Transactional
public void order(Order order) {
    orderRepository.save(order);
    outboxRepository.save(Outbox.of("OrderPlaced", order));  // 같은 트랜잭션
}
```

그리고 별도의 릴레이가 `published = false`인 행을 읽어 브로커로 보내고 발행 완료로 표시한다.

**중요한 점**: 발행은 성공했는데 완료 표시 직전에 죽으면 같은 메시지가 다시 나간다. 아웃박스를 써도 여전히 at-least-once이고, 소비자 멱등성은 어차피 필요하다. 아웃박스가 보장하는 건 "중복 없음"이 아니라 **"유실 없음"**이다.

릴레이가 폴링 방식이면 폴링 주기만큼 지연이 생기고, 테이블이 계속 커진다. `published` 컬럼에 인덱스를 걸고, 발행 완료된 오래된 행은 주기적으로 지워야 한다.

## 배치 전송

건별로 보내는 대신 모아서 한 번에 보낸다. 요청마다 붙는 네트워크 왕복과 헤더, 인증 처리 비용이 수백 건에 한 번으로 줄어드니 처리량이 크게 오른다.

모으는 기준은 보통 두 개를 함께 건다. **"100건이 모이거나, 1초가 지나면 보낸다."** 크기 조건만 있으면 트래픽이 적을 때 메시지가 영영 안 나가고, 시간 조건만 있으면 몰릴 때 배치가 너무 커진다.

**중요한 점**: 배치 크기는 처리량과 지연의 거래다. 크게 잡을수록 효율은 좋지만 마지막 건은 그만큼 늦게 처리된다. 지연에 민감한 작업이라면 배치가 답이 아닐 수 있다.

**중요한 점**: 진짜 어려운 건 **부분 실패**다. 100건 중 3건만 실패했을 때 전체를 재시도하면 나머지 97건이 중복 처리된다. 그래서 응답에서 실패한 건을 식별할 수 있어야 하고(대부분의 배치 API는 건별 결과를 준다), 그게 안 되면 결국 각 건이 멱등해야 전체 재시도가 안전해진다.

## CDC

Change Data Capture. 애플리케이션이 이벤트를 발행하는 대신, **DB의 변경 로그(MySQL이면 binlog)를 읽어서** 변경 사실을 이벤트로 만든다. Debezium이 대표적이다.

애플리케이션 입장에서는 그냥 평소처럼 DB에 저장할 뿐이고, 이벤트 발행 코드가 아예 없다. 그래서 손대기 어려운 레거시 시스템에서 데이터를 뽑아내야 할 때 강력하다. 커밋된 로그를 읽는 것이라 유실도 없다.

**중요한 점**: 대신 이벤트가 DB 스키마 그 자체가 된다. `orders` 테이블의 `status` 컬럼이 5에서 7로 바뀌었다는 사실은 전달되지만, 그게 "주문이 취소됐다"는 의미인지는 담기지 않는다. 소비자가 남의 테이블 구조를 알아야 하고, 컬럼명을 바꾸는 순간 소비자가 깨진다.

그래서 실무에서는 **아웃박스와 CDC를 함께** 쓰는 조합이 많다. outbox 테이블에는 의도가 담긴 이벤트를 쓰고, 그 테이블을 CDC로 읽어서 발행한다. 폴링 없이 즉시 발행되면서 이벤트 의미도 지켜지고, 소비자는 업무 테이블 구조를 몰라도 된다.
