## 동시성 문제

재고 1개짜리 상품에 두 명이 동시에 주문했다.

```java
public void order(Long productId) {
    Product product = repository.find(productId);  // 둘 다 stock = 1 을 읽음
    if (product.getStock() < 1) throw new SoldOutException();
    product.setStock(product.getStock() - 1);      // 둘 다 0 으로 만듦
    repository.save(product);
}
```

재고는 1개인데 주문은 2건이 성사된다. 문제는 `product.getStock() - 1`이 코드로는 한 줄이지만 실제로는 **읽기 → 계산 → 쓰기** 세 단계이고, 그 사이에 다른 스레드가 끼어들 수 있다는 것이다. 이렇게 실행 순서에 따라 결과가 달라지는 상황을 **경쟁 상태(race condition)** 라고 한다.

그리고 위에서 "끼어들면 안 되는 구간", 즉 공유 데이터를 읽고 고치는 저 세 줄을 **임계 영역(critical section)** 이라고 한다. 동시성 처리는 결국 임계 영역을 찾아내서 한 번에 한 명만 들어가게 만드는 일이다.

**중요한 점**: 문제가 되는 건 공유되면서 **바뀌는** 데이터다. 아무도 안 고치는 읽기 전용 데이터는 몇 개의 스레드가 동시에 봐도 아무 일도 없다.

## 잠금을 이용한 동시 접근 제어

임계 영역 앞에 문을 달고 열쇠를 하나만 둔다. 자바에서 가장 기본은 `synchronized`다.

```java
public synchronized void order(Long productId) { ... }
```

간단하지만 거칠다. 들어갈 때까지 무조건 기다리고, 중간에 포기할 수도 없다. `ReentrantLock`을 쓰면 이런 걸 제어할 수 있다.

```java
private final ReentrantLock lock = new ReentrantLock();

public void order(Long productId) {
    if (!lock.tryLock(1, TimeUnit.SECONDS)) {   // 1초 기다려보고 안 되면 포기
        throw new BusyException();
    }
    try {
        // 임계 영역
    } finally {
        lock.unlock();   // 반드시 finally 에서
    }
}
```

여기까지는 "한 명만" 들어가는 방식인데, 때로는 "동시에 N명까지"가 필요하다. 예를 들어 외부 API에 동시 요청을 20개로 제한하고 싶을 때. 이럴 때 쓰는 게 **세마포어**다. 열쇠를 여러 개 두고 빌려 쓴다고 보면 된다.

```java
private final Semaphore semaphore = new Semaphore(20);

public void callExternal() {
    if (!semaphore.tryAcquire()) throw new TooManyRequestsException();
    try {
        externalClient.call();
    } finally {
        semaphore.release();
    }
}
```

**중요한 점**: `unlock`과 `release`는 무조건 `finally`에 둔다. 예외가 터져서 열쇠를 반납 못 하면 그 뒤의 모든 스레드가 영원히 기다린다.

## 원자적 타입과 동시성 지원 컬렉션

단순한 카운터 하나 때문에 락을 거는 건 과하다. 그럴 때 쓰는 게 원자적 타입이다.

```java
private final AtomicLong viewCount = new AtomicLong();

public void view() {
    viewCount.incrementAndGet();   // 읽기+더하기+쓰기가 쪼개지지 않음
}
```

원리는 **CAS(Compare-And-Swap)** 다. "내가 읽었을 때 값이 5였는데, 지금도 5면 6으로 바꿔줘"라고 요청하고, 그사이 누가 바꿔놨으면 실패하고 다시 시도한다. 락처럼 기다리는 게 아니라 실패하면 재시도하는 방식이라 경합이 심하지 않을 때 훨씬 빠르다.

컬렉션도 마찬가지다. `HashMap`을 여러 스레드가 같이 쓰면 데이터가 깨지므로 `ConcurrentHashMap`을 쓴다.

```java
private final Map<Long, Integer> cache = new ConcurrentHashMap<>();

// 이건 안전하지 않다 — 확인과 저장 사이에 끼어들 수 있음
if (!cache.containsKey(key)) cache.put(key, load(key));

// 이건 안전하다 — 한 동작으로 처리됨
cache.computeIfAbsent(key, this::load);
```

**중요한 점**: 컬렉션이 스레드 안전하다는 건 **각 메서드 호출 하나**가 안전하다는 뜻이지, 여러 호출을 이어붙인 흐름이 안전하다는 뜻이 아니다. 위의 `containsKey` + `put` 조합이 정확히 그 함정이다. 이럴 땐 `computeIfAbsent`, `putIfAbsent`처럼 한 번에 끝내는 메서드를 찾아 쓴다.

## DB와 동시성

지금까지의 방법에는 큰 구멍이 있다. **서버가 2대면 전부 무용지물**이다. 자바의 락은 그 JVM 안에서만 유효해서, 각 서버가 자기 락을 잡고 사이좋게 재고를 같이 깎는다. 결국 모두가 공유하는 DB에서 통제해야 한다.

### 선점 잠금

먼저 잡고 시작하는 방식(비관적 잠금). 데이터를 읽는 순간부터 락을 걸어서 다른 트랜잭션이 못 건드리게 한다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)   // SELECT ... FOR UPDATE
@Query("select p from Product p where p.id = :id")
Product findByIdForUpdate(@Param("id") Long id);
```

확실하다. 대신 락을 잡은 트랜잭션이 끝날 때까지 나머지는 전부 줄을 선다. 충돌이 자주 일어나는 곳(인기 상품 재고, 선착순 쿠폰)에 적합하다.

### 비선점 잠금

일단 진행하고 나중에 확인하는 방식(낙관적 잠금). 실제로 락을 걸지 않고, 버전 번호로 "내가 읽은 뒤에 누가 바꿨나"를 검사한다.

```java
@Entity
public class Product {
    @Id private Long id;
    private int stock;

    @Version
    private Long version;   // 이 필드 하나면 끝
}
```

수정할 때 `UPDATE ... SET stock = ?, version = 6 WHERE id = ? AND version = 5`가 나간다. 그사이 누가 먼저 고쳐서 버전이 6이 됐다면 이 UPDATE는 0건이 되고 예외가 터진다.

**중요한 점**: 비선점 잠금은 충돌을 **막는** 게 아니라 **감지**하는 것이다. 그래서 예외가 났을 때 뭘 할지를 반드시 정해야 한다. 보통은 다시 읽어서 재시도하고, 몇 번 실패하면 사용자에게 알린다. 충돌이 드물 때(회원 정보 수정 같은) 락 비용이 없어서 유리하다.

### 증분 쿼리

사실 재고 차감 정도는 락 없이도 해결된다. **읽어서 계산하지 말고, DB에게 계산을 시키면** 된다.

```java
@Modifying
@Query("update Product p set p.stock = p.stock - 1 where p.id = :id and p.stock >= 1")
int decreaseStock(@Param("id") Long id);
```

```java
if (repository.decreaseStock(id) == 0) throw new SoldOutException();
```

UPDATE 한 문장은 DB가 알아서 원자적으로 처리하고, `stock >= 1` 조건이 재고를 마이너스로 만들지 못하게 막는다. 반환값이 0이면 조건에 안 맞았다는 뜻이라 품절 판단까지 된다.

**중요한 점**: 락을 고민하기 전에 "읽고-고치고-쓰기를 한 문장으로 합칠 수 있나"를 먼저 본다. 가능하면 이게 제일 간단하고 빠르다.

## 잠금 주의사항

**데드락** — A가 1번 락을 잡고 2번을 기다리는데, B는 2번을 잡고 1번을 기다린다. 둘 다 영원히 멈춘다. 해결책은 단순하다. **락을 잡는 순서를 항상 똑같이 정한다.** 계좌 이체라면 계좌 ID가 작은 쪽부터 잡는 식으로.

**라이브락** — 데드락과 달리 둘 다 계속 뭔가를 하고 있는데 진전이 없는 상태다. 충돌을 감지하고 양보했다가 재시도하는데, 상대도 똑같이 해서 계속 부딪히는 경우다. 좁은 복도에서 서로 비켜주다가 같은 방향으로만 움직이는 것과 같다. 낙관적 잠금 재시도에서 실제로 생길 수 있고, 재시도 간격에 랜덤을 섞으면(지터) 대부분 풀린다.

**락 범위는 최대한 좁게** — 락을 잡은 시간만큼 다른 요청이 대기한다. 필요한 줄만 감싼다.

**락 안에서 외부 API를 부르지 않는다** — 외부가 5초 걸리면 그동안 모두가 5초를 기다린다. DB 락이라면 커넥션까지 함께 묶여서 서버 전체가 마비될 수 있다.

**타임아웃을 건다** — 무한정 기다리는 락은 장애를 대기 행렬로 바꿀 뿐이다. `tryLock`이든 DB 락 타임아웃이든, 못 잡으면 실패하고 빠져나오는 길을 만들어 둔다.

**중요한 점**: 여러 서버에서 DB가 아닌 곳(Redis 등)의 분산 락을 쓸 때는 반드시 만료 시간을 준다. 락을 잡은 서버가 그냥 죽어버리면 아무도 그 락을 풀어줄 수 없기 때문이다.
