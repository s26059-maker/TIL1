## 인덱스

책 뒤에 붙은 "찾아보기"와 같다. 정렬된 별도 자료구조(보통 B-Tree)를 따로 만들어 두고, 원하는 값의 위치를 바로 찾아간다. 인덱스가 없으면 첫 페이지부터 끝까지 다 넘겨봐야 한다(풀 스캔).

**중요한 점**: 조회는 빨라지지만, INSERT/UPDATE/DELETE 때마다 인덱스도 같이 고쳐야 해서 쓰기는 느려진다. 그래서 "일단 다 걸어두자"는 안 된다.


## 단일 인덱스

컬럼 하나로 만든 인덱스.

```sql
CREATE INDEX idx_email ON users(email);
```

`WHERE email = 'a@b.com'` 처럼 조건이 하나일 때 강하다.

**중요한 점**: 조건이 두 개(`email AND age`)면 보통 인덱스 하나만 타고 나머지는 그 결과 안에서 걸러낸다. 단일 인덱스를 두 개 따로 만들어도 둘 다 동시에 쓰는 일은 드물다.

## 복합 인덱스

컬럼 여러 개를 묶어서 만든 인덱스. **순서가 전부**다.

```sql
CREATE INDEX idx_name_age ON users(name, age);
```

전화번호부로 생각하면 쉽다. (성, 이름) 순으로 정렬돼 있으니까

- "김" 씨 찾기 → 가능
- "김철수" 찾기 → 가능
- 이름이 "철수"인 사람 전부 찾기 → 불가능. 성을 모르니 처음부터 다 봐야 한다.

이게 **왼쪽 우선 법칙(leftmost prefix)** 이다. 앞 컬럼부터 순서대로 써야 인덱스를 탄다.

`(name, age)` 인덱스 기준

| 조건 | 인덱스 |
|---|---|
| `WHERE name = ?` | O |
| `WHERE name = ? AND age = ?` | O |
| `WHERE age = ?` | X |

**중요한 점**: 등호(`=`) 조건 컬럼을 앞에, 범위(`>`, `<`, `BETWEEN`) 조건 컬럼을 뒤에 둔다. 범위 조건을 만나는 순간 그 뒤 컬럼들은 정렬이 깨져서 인덱스 효율이 뚝 떨어진다.

**중요한 점**: 카디널리티(값의 종류가 얼마나 다양한지)가 높은 컬럼을 앞에 두는 게 유리하다. 한 번에 많이 걸러내니까. 성별처럼 값이 2개뿐인 컬럼을 맨 앞에 두면 절반밖에 못 걸러낸다.

## 커버링 인덱스

쿼리에 필요한 컬럼이 전부 인덱스 안에 들어 있어서, **실제 테이블을 안 읽어도 되는** 경우를 말한다.

원래 흐름은 두 단계다.
1. 인덱스에서 위치를 찾는다
2. 그 위치로 테이블에 가서 실제 행을 읽는다 ← 이걸 테이블 접근(랜덤 I/O)이라 하고, 여기가 느리다

커버링 인덱스는 2번을 통째로 생략한다. 찾아보기에 페이지 번호만 있으면 본문으로 넘어가야 하는데, 찾아보기에 답까지 적혀 있어서 거기서 끝나는 셈이다.

```sql
CREATE INDEX idx_name_age ON users(name, age);

SELECT age   FROM users WHERE name = '홍길동';  -- 커버링 O (name, age 둘 다 인덱스에 있음)
SELECT email FROM users WHERE name = '홍길동';  -- 커버링 X (email 때문에 테이블까지 감)
```

실행계획(`EXPLAIN`)의 Extra 컬럼에 `Using index`가 뜨면 커버링에 성공한 것이다.

**중요한 점**: `SELECT *`는 사실상 커버링이 안 된다. 필요한 컬럼만 골라 쓰는 습관이 그대로 성능이 된다.

**중요한 점**: 페이징에서 자주 쓰인다. 커버링 인덱스로 PK만 먼저 뽑고, 그 PK로 본 테이블을 조인해서 가져오면 뒷페이지로 갈수록 느려지는 문제를 크게 줄일 수 있다.

## 인덱스가 안 걸리는 경우

- 컬럼에 함수나 연산을 씌울 때 → `WHERE YEAR(created_at) = 2024` (X), `WHERE created_at BETWEEN ...` (O)
- `LIKE '%값'` 처럼 와일드카드가 앞에 올 때 → `LIKE '값%'` 는 가능
- 컬럼 타입과 조건 값 타입이 다를 때 → 내부 형변환이 일어나면서 인덱스가 깨진다
- `!=`, `NOT IN`, `IS NOT NULL` 같이 "아닌 것"을 찾을 때 → 결국 다 봐야 해서 풀 스캔이 낫다고 판단하기 쉽다
