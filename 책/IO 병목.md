## IO 병목

장애 상황에서 서버를 들여다보면 이런 그림이 자주 나온다. **CPU 사용률은 5%인데 응답은 안 나간다.**

원인은 대부분 하나다. 톰캣의 요청 스레드가 200개인데, 그 200개가 전부 DB나 외부 API의 응답을 기다리며 멈춰 서 있는 것이다.

```java
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderRepository.findById(id);   // 이 줄에서 스레드가 멈춤
    User user = userClient.find(order.userId());  // 여기서 또 멈춤
    return OrderResponse.of(order, user);
}
```

여기서 "멈춘다(블로킹)"는 말의 정확한 의미는 이렇다. 스레드가 OS에게 "이 데이터 받아와줘"라고 요청하고 **대기 상태로 전환**된다. CPU는 이 스레드를 스케줄링 대상에서 빼고 다른 일을 한다. 데이터가 도착하면 그때 다시 깨운다.

즉 **CPU는 놀고 있는 게 아니라 놀 준비가 돼 있는데, 스레드라는 자원이 다 묶여서 새 요청을 못 받는 상태**다. 이게 IO 병목이다.

**중요한 점**: IO 병목은 "느리다"가 아니라 "동시에 못 받는다"의 문제다. 그래서 응답 시간을 줄이는 방향이 아니라, 기다리는 동안 스레드를 안 붙잡는 방향으로 풀어야 한다.


## 네트워크 IO와 CPU

작업은 크게 두 종류다.

- **CPU 바운드** — 계산이 오래 걸린다. 이미지 처리, 암호화, 대량 정렬. CPU를 실제로 쓴다.
- **IO 바운드** — 기다리는 시간이 대부분이다. DB 조회, API 호출, 파일 읽기. 웹 서버 요청의 90% 이상이 여기 속한다.

이 구분이 중요한 이유는 **스레드 풀 크기를 완전히 다르게 잡아야** 하기 때문이다.

CPU 바운드는 코어 수보다 스레드를 많이 만들어도 소용없다. 어차피 동시에 계산할 수 있는 건 코어 수만큼이고, 오히려 스레드를 번갈아 바꾸는 비용만 늘어난다. 그래서 코어 수 + 1 정도가 적당하다.

IO 바운드는 다르다. 대기 시간에는 CPU를 안 쓰니 스레드를 많이 만들수록 동시 처리량이 는다. 대략 이렇게 잡는다.

```
스레드 수 = 코어 수 × (1 + 대기시간 / 계산시간)
```

계산에 10ms, 대기에 90ms 걸리는 작업이면 코어당 10개 정도가 나온다.

### 그럼 그냥 스레드를 왕창 만들면 되지 않나

안 된다. 두 가지 비용 때문이다.

**메모리** — 자바 스레드 하나는 기본 1MB 정도의 스택을 잡는다. 10,000개면 10GB다. 애초에 못 만든다.

**컨텍스트 스위칭** — CPU가 스레드 A를 잠시 멈추고 B로 넘어갈 때, A가 쓰던 레지스터 값과 상태를 저장하고 B의 것을 복원해야 한다. 이게 수 마이크로초씩 든다. 하나하나는 작지만 스레드가 많아지면 **CPU가 일은 안 하고 스레드 바꾸는 데만 시간을 쓴다.** 게다가 스레드가 바뀔 때마다 CPU 캐시에 올라와 있던 데이터가 무의미해져서 실제 손해는 더 크다.

**중요한 점**: 그래서 IO 병목의 해법은 두 갈래로 갈린다. **스레드를 안 기다리게 만들거나(논블로킹 IO)**, **기다려도 싼 스레드를 쓰거나(가상 스레드)**.

## 논블로킹 IO

발상을 바꾼다. 데이터를 요청해놓고 스레드가 서서 기다리는 대신, **"준비되면 알려줘"라고 등록만 하고 다른 일을 하러 간다.**

이게 가능한 건 OS가 `epoll` 같은 기능을 제공하기 때문이다. 수천 개의 연결을 한 곳에 등록해두면, 그중 데이터가 도착한 것들만 골라서 알려준다. 스레드 하나가 연결 하나를 지키고 있을 필요가 없어진다.

### 리액터 패턴과 이벤트 루프

이 구조를 정리한 게 **리액터 패턴**이다. 핵심은 두 부분이다.

1. **이벤트 루프** — 스레드 하나가 무한 루프를 돌면서 "준비된 이벤트 있어?"를 계속 확인한다.
2. **핸들러** — 준비된 이벤트가 있으면 거기에 등록된 콜백을 실행한다.

```
while (true) {
    준비된_이벤트들 = selector.select();     // 여기서만 잠깐 대기
    for (이벤트 : 준비된_이벤트들) {
        이벤트.핸들러_실행();                // 짧게 처리하고 바로 다음
    }
}
```

스레드 몇 개(보통 코어 수만큼)로 수만 개의 연결을 처리할 수 있다. 스프링에서는 WebFlux가 이 방식이다.

```java
@GetMapping("/orders/{id}")
public Mono<OrderResponse> get(@PathVariable Long id) {
    return orderRepository.findById(id)                    // 기다리지 않음
        .flatMap(order -> userClient.find(order.userId())  // 도착하면 이걸 실행하라고 등록
            .map(user -> OrderResponse.of(order, user)));
}
```

`Mono`는 값이 아니라 **"나중에 값이 올 통로"** 다. 실제 실행은 데이터가 도착했을 때 이벤트 루프가 시켜준다.

**중요한 점**: 여기서 가장 중요한 제약이 있다. **이벤트 루프 스레드를 절대 블로킹하면 안 된다.** 그 스레드 하나가 수천 개의 연결을 담당하고 있으므로, 중간에 JDBC 호출 하나를 그냥 끼워 넣는 순간 수천 개가 같이 멈춘다. 그래서 논블로킹은 DB 드라이버부터 HTTP 클라이언트까지 **전 구간이 다 논블로킹이어야** 의미가 있다. 이게 WebFlux 도입이 어려운 진짜 이유다.

대신 얻는 게 하나 더 있는데 **백프레셔**다. 소비자가 "나 지금 10개만 받을 수 있어"라고 생산자에게 알려서 감당 못 할 속도로 밀려오는 걸 막는 기능이다. 스레드 기반에서는 그냥 큐가 쌓이다 터지는 부분이다.

## 가상 스레드

논블로킹은 강력하지만 코드가 완전히 달라지고 디버깅이 어렵다. 자바 21의 가상 스레드는 다른 접근을 한다. **코드는 그대로 두고, 스레드를 싸게 만든다.**

```java
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderRepository.findById(id);   // 그냥 블로킹 코드
    User user = userClient.find(order.userId());
    return OrderResponse.of(order, user);
}
```

```properties
spring.threads.virtual.enabled=true
```

코드는 그대로인데 동시 처리량이 몇 배가 된다.

### 캐리어 스레드

원리는 이렇다. 가상 스레드는 OS 스레드가 아니라 **JVM이 관리하는 가벼운 객체**다. 실제 실행은 진짜 OS 스레드 위에서 이뤄지는데, 이 실행대 역할을 하는 OS 스레드를 **캐리어 스레드**라고 한다. 보통 코어 수만큼만 있다.

핵심은 가상 스레드가 IO를 만났을 때다.

- 블로킹 지점을 만나면 JVM이 가상 스레드를 캐리어 스레드에서 **떼어낸다(언마운트)**. 이때 스택 상태는 힙에 저장된다.
- 비워진 캐리어 스레드는 즉시 다른 가상 스레드를 올려서 실행한다.
- IO가 끝나면 그 가상 스레드를 다시 아무 캐리어 스레드에나 **올린다(마운트)**.

결과적으로 **개발자에게는 블로킹처럼 보이지만 실제로는 OS 스레드가 안 멈춘다.** 논블로킹의 효율을 블로킹 코드 모양으로 얻는 것이다. 게다가 이 교체는 JVM 안에서 일어나므로 OS 컨텍스트 스위칭보다 훨씬 싸고, 스택도 필요한 만큼만 쓰니 수십만 개를 만들어도 된다.

**중요한 점**: **가상 스레드는 풀링하지 않는다.** 만드는 게 거의 공짜이므로 요청마다 새로 만들고 버린다. `Executors.newVirtualThreadPerTaskExecutor()`가 이름 그대로 작업마다 하나씩 만드는 이유다. 여기에 굳이 풀을 씌우면 가상 스레드의 장점이 사라진다.

**핀닝(pinning)** 을 조심해야 한다. `synchronized` 블록 안에서 블로킹이 일어나면 가상 스레드가 캐리어 스레드에서 안 떨어지고 그대로 붙잡아버린다. 캐리어 스레드는 코어 수만큼밖에 없으니 몇 개만 이래도 전체가 막힌다. 그래서 가상 스레드를 쓸 거면 `synchronized`를 `ReentrantLock`으로 바꾸는 게 권장된다.

가상 스레드를 켜면 병목이 사라지는 게 아니라 **다음 지점으로 이동한다.** 스레드가 10,000개 동시에 돌아도 DB 커넥션 풀이 10개면 거기서 다시 줄을 선다. 오히려 그동안 톰캣 스레드 200개가 자연스럽게 해주던 유량 제한이 사라져서 DB에 부하가 몰릴 수 있다. 그래서 커넥션 풀 크기와 동시 요청 제한을 함께 다시 봐야 한다.
