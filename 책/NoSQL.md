## NoSQL이란

이름 때문에 "SQL을 안 쓴다"로 오해하기 쉬운데, 실제 의미는 **Not Only SQL**에 가깝다. 관계형 DB를 대체하는 게 아니라 **관계형이 잘 못하는 영역을 맡는 다른 선택지**다.

관계형 DB는 데이터를 잘게 쪼개 정규화하고, 필요할 때 조인해서 합친다. 중복이 없어 정합성이 좋고, 어떤 질문이든 SQL로 만들어낼 수 있다. 대신 **데이터가 커지면 조인이 무거워지고, 서버를 여러 대로 나누기가 어렵다.** 조인하려면 데이터가 한 곳에 있어야 하기 때문이다.

NoSQL은 이 전제를 뒤집는다. **조인을 포기하는 대신 확장을 얻는다.**

```
관계형: 데이터를 나눠 저장하고 → 읽을 때 조인해서 합침
NoSQL: 읽을 모양 그대로 뭉쳐서 저장하고 → 그대로 꺼냄
```

**중요한 점**: 가장 큰 차이는 **설계 순서**다. 관계형은 데이터 구조를 먼저 정하고 나중에 아무 쿼리나 만든다. NoSQL은 **어떤 쿼리를 쓸지 먼저 정하고 거기에 맞춰 데이터를 저장**한다. 나중에 새로운 조회 패턴이 필요해지면 데이터 구조 자체를 바꿔야 하는 경우가 생긴다.

"스키마가 없다"는 말도 오해를 부른다. 정확히는 **DB가 스키마를 강제하지 않는다**는 뜻이지 스키마가 없어도 된다는 게 아니다. DB가 안 막아주면 그 검증 책임이 애플리케이션으로 넘어온다. 필드 이름 오타 하나가 조용히 저장되고, 나중에 조회할 때야 드러난다.

대신 스키마 변경이 자유롭다는 건 진짜 장점이다. 수억 건 테이블에 컬럼을 추가하려고 락이 걸린 채 몇 시간 기다리는 일이 없다.

## NoSQL 종류

### 키-값 저장소

가장 단순한 형태. 키 하나에 값 하나. 구조가 단순해서 압도적으로 빠르다.

```bash
SET user:1000:session "abc123" EX 3600    # 1시간 뒤 자동 삭제
GET user:1000:session

INCR article:42:views                      # 원자적 증가
```

Redis, Memcached가 대표적이고, 캐시·세션·순위표·분산 락처럼 **빠르고 단순한 조회**에 쓴다.

**중요한 점**: Redis를 단순 캐시로만 아는 경우가 많은데, 자료구조를 제공하는 게 진짜 강점이다. 실시간 순위표는 정렬 집합으로 한 줄이면 된다.

```bash
ZADD ranking 1500 "user:1000"
ZREVRANGE ranking 0 9 WITHSCORES    # 상위 10명
```

같은 걸 관계형에서 하려면 매번 정렬하거나 별도 집계가 필요하다.

### 문서 저장소

JSON 형태의 문서를 통째로 저장한다. MongoDB가 대표적이다.

```javascript
db.orders.insertOne({
  _id: "order-1001",
  userId: 1000,
  userName: "홍길동",          // 회원 정보를 복사해 넣음 (비정규화)
  items: [                     // 관계형이면 별도 테이블
    { productId: 55, name: "키보드", price: 89000, qty: 1 }
  ],
  status: "PAID"
});

db.orders.find({ userId: 1000, status: "PAID" });
```

주문 하나를 보여주는 데 조인이 필요 없다. **화면에 필요한 모양 그대로 한 덩어리로 저장**되어 있기 때문이다.

**중요한 점**: 대신 중복이 생긴다. 회원 이름이 바뀌면 그 사람의 주문 문서를 전부 찾아 고쳐야 한다. **정합성을 포기하고 조회 속도를 얻는 거래**다. 그래서 잘 안 바뀌는 값이거나, 오히려 그 시점의 값을 남겨야 하는 경우(주문 당시의 가격)에 잘 맞는다.

### 컬럼 패밀리 저장소

행을 통째로 다루는 대신 **컬럼 단위로 나눠 저장**한다. Cassandra, HBase가 여기 속한다.

쓰기 처리량이 매우 크고 서버를 늘려 확장하기 좋아서, 로그·센서 데이터·메시지 이력처럼 **끝없이 쌓이는 데이터**에 쓴다.

**중요한 점**: 여기서는 **파티션 키 설계가 전부**다. 데이터를 어느 서버에 나눠 담을지 결정하는 키인데, 잘못 잡으면 특정 서버에만 요청이 몰린다(핫스팟). 그리고 파티션 키로 조회하지 않는 쿼리는 전체를 뒤져야 해서 사실상 못 쓴다. 나중에 바꾸는 것도 거의 불가능하다.

### 그래프 저장소

데이터보다 **관계 자체가 중요할 때** 쓴다. Neo4j가 대표적이다.

```cypher
MATCH (me:User {id: 1000})-[:FRIEND*1..3]-(friend:User)
RETURN friend
```

"내 친구의 친구의 친구"를 찾는 쿼리인데, 관계형이라면 조인을 세 번 중첩해야 하고 단계가 늘어날수록 급격히 느려진다. 그래프 DB는 관계를 따라가는 게 기본 동작이라 단계가 늘어도 비용이 덜 오른다.

소셜 관계, 추천, 이상거래 탐지, 권한 상속 구조에 쓴다.

### 그 밖에

**검색 엔진(Elasticsearch)** — 전문 검색과 로그 분석에 특화. 앞에서 본 CQRS의 읽기 전용 저장소로 자주 쓰인다.

**시계열 DB(InfluxDB, Prometheus)** — 시간 축으로 쌓이는 지표 데이터에 특화. 오래된 데이터를 자동으로 압축하거나 삭제하는 기능이 기본으로 있다.

## CAP 정리

분산 시스템에서 세 가지를 동시에 만족할 수 없다는 이론이다.

- **C(일관성)** — 어느 노드에 물어도 같은 값을 준다
- **A(가용성)** — 요청하면 어쨌든 응답한다
- **P(분단 내성)** — 노드 간 통신이 끊겨도 동작한다

핵심은 **셋 중 둘을 고르는 게 아니라는 것**이다. 네트워크는 언젠가 반드시 끊기므로 **P는 선택 사항이 아니다.** 실제 선택은 **통신이 끊겼을 때 C와 A 중 무엇을 버릴 것인가**다.

```
서버 A와 서버 B 사이 통신이 끊겼다. 사용자가 A에게 조회를 요청한다.

CP 선택: "B와 값이 같은지 확인할 수 없으니 응답을 거부한다"  → 정확하지만 멈춤
AP 선택: "일단 내가 아는 값을 준다"                        → 응답하지만 옛날 값일 수 있음
```

**CP를 택하는 쪽** — 잔액이나 재고처럼 **틀린 값을 주느니 안 주는 게 나은** 데이터. MongoDB, HBase가 기본적으로 이쪽이다.

**AP를 택하는 쪽** — 조회수나 타임라인처럼 **조금 틀려도 되니 항상 응답해야 하는** 데이터. Cassandra, DynamoDB가 이쪽이다.

**중요한 점**: CAP는 **통신이 끊긴 특수 상황**에 대한 이야기다. 평소에는 둘 다 만족한다. 그래서 실무에서는 **PACELC**가 더 유용하다. "분단이 나면(P) C와 A 중에, **그렇지 않으면(E) 지연시간(L)과 일관성(C) 중에** 골라야 한다"는 것이다. 여러 노드에 복제 확인을 받고 응답하면 정확하지만 느리고, 하나만 쓰고 바로 응답하면 빠르지만 어긋날 수 있다.

**중요한 점**: 관계형 DB의 ACID에 대비되는 개념으로 **BASE**를 쓴다. "기본적으로 가용하고(Basically Available), 상태가 잠시 흔들릴 수 있고(Soft state), 결국에는 일관돼진다(Eventually consistent)". 앞에서 이벤트 기반 아키텍처를 다룰 때 나온 결과적 일관성이 여기서도 그대로 등장한다.

**중요한 점**: 요즘은 이 구분이 이분법적이지 않다. 많은 NoSQL이 **요청 단위로 일관성 수준을 고를 수 있게** 해준다. 같은 DB에서 결제는 강한 일관성으로, 조회수는 약한 일관성으로 읽는 식이다.

## 도입 고려 사항

### 먼저 관계형으로 안 되는지 확인한다

**중요한 점**: NoSQL을 도입할 이유로 가장 많이 언급되는 게 성능인데, 그 성능 문제의 대부분은 **인덱스 하나로 해결된다.** 앞에서 본 복합 인덱스와 커버링 인덱스, 쿼리 튜닝, 캐시 도입을 먼저 해보는 게 순서다. 관계형 DB는 생각보다 훨씬 많은 트래픽을 감당한다.

### 조인이 필요 없는 구조인지

이게 가장 실질적인 판단 기준이다. **한 번에 꺼낼 데이터가 한 덩어리로 뭉쳐지는가?** 주문 화면이 주문+상품+회원+쿠폰+배송을 다 필요로 하고 각각이 독립적으로 변한다면, NoSQL로 옮겨도 결국 애플리케이션에서 여러 번 조회해 조립하게 된다. 그러면 DB가 하던 일을 코드가 하는 것뿐이라 더 나빠진다.

### 트랜잭션이 얼마나 필요한지

**중요한 점**: 요즘 NoSQL도 트랜잭션을 지원하지만 **범위가 제한적이고 비용이 크다.** 대부분 문서 하나 안에서는 원자성이 보장되지만 여러 문서에 걸치면 성능이 크게 떨어진다. 돈이 오가는 영역이라면 관계형이 여전히 안전한 선택이다.

### 운영 부담을 감당할 수 있는지

**중요한 점**: 새 저장소는 새 운영 대상이다. 백업과 복구 절차, 모니터링 지표, 장애 대응 방법을 전부 새로 익혀야 한다. 팀에 경험자가 없다면 이 비용이 성능 이득보다 클 수 있다. 특히 **장애가 났을 때 아무도 원인을 모르는 상황**이 가장 위험하다.

### 한 가지만 골라야 하는 게 아니다

**중요한 점**: 실무에서는 용도별로 나눠 쓴다. 이걸 **폴리글랏 퍼시스턴스**라고 한다.

```
주문·결제  → MySQL           (정합성이 핵심)
세션·캐시  → Redis           (빠른 조회)
상품 검색  → Elasticsearch   (전문 검색)
접속 로그  → Cassandra       (대량 쓰기)
```

다만 저장소가 늘어날수록 **데이터 동기화가 새 숙제**가 된다. MySQL의 상품 정보를 Elasticsearch에 반영하는 파이프라인이 필요해지고, 앞에서 본 아웃박스 패턴이나 CDC가 이 지점에서 등장한다. 저장소 하나 늘리는 결정은 곧 동기화 코드 하나 늘리는 결정이다.
