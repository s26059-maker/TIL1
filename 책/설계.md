# 설계 패턴 정리

## MVC 패턴

관심사를 세 덩어리로 나누는 방식이다.

- **Model** — 데이터와 규칙
- **View** — 화면에 보여주는 것
- **Controller** — 요청을 받아서 모델을 부르고 뷰를 고르는 것

```java
@Controller
public class OrderController {
    @GetMapping("/orders/{id}")
    public String detail(@PathVariable Long id, Model model) {
        model.addAttribute("order", orderService.find(id));  // Model
        return "order/detail";                               // View 이름
    }
}
```

핵심은 **화면이 바뀌어도 로직은 안 바뀌고, 로직이 바뀌어도 화면은 안 바뀌게** 하는 것이다. 같은 주문 조회 로직으로 HTML도 만들고 JSON도 만들 수 있다.

**중요한 점**: API 서버에서는 View가 사라진 것처럼 보이는데, 실제로는 **JSON 직렬화가 View 역할**을 한다. `@RestController`는 뷰 이름 대신 객체를 반환하면 그걸 JSON으로 바꿔주는 형태다.

MVC에서 가장 자주 깨지는 규칙은 **컨트롤러에 로직이 쌓이는 것**이다. 컨트롤러는 요청을 받아서 넘기고 결과를 포장하는 얇은 층이어야 한다. 여기에 조건문과 계산이 들어가기 시작하면 테스트가 어려워지고, 같은 로직을 배치나 다른 API에서 재사용할 수 없다.

## 계층형 아키텍처

MVC를 서버 안쪽으로 확장한 게 계층형이다. 스프링에서 가장 흔한 구조다.

```
Controller  →  Service  →  Repository  →  DB
  요청/응답     비즈니스 로직   데이터 접근
```

각 층의 역할이 명확하다.

```java
@RestController
class OrderController {
    @PostMapping("/orders")
    OrderResponse create(@RequestBody @Valid OrderRequest req) {
        return OrderResponse.of(orderService.create(req.toCommand()));
    }
}

@Service
class OrderService {
    @Transactional
    public Order create(OrderCommand cmd) {
        // 여기가 진짜 일하는 곳
    }
}
```

**중요한 점**: 의존은 **위에서 아래로만** 흘러야 한다. 리포지토리가 서비스를 부르거나 서비스가 컨트롤러를 부르면 층이 무너진다. 순환 참조가 생기고 테스트할 때 전부 다 띄워야 한다.

엔티티를 컨트롤러 밖으로 그대로 내보내지 않는다. 엔티티가 응답 형식이 되어버리면 **컬럼 하나 바꾸는 게 API 스펙 변경**이 된다. DTO를 따로 두는 이유가 이거다. 지연 로딩 때문에 직렬화 시점에 예외가 나는 문제도 여기서 갈린다.

계층형의 진짜 약점은 **모든 게 DB를 향한다**는 것이다. 서비스가 JPA와 트랜잭션에 직접 묶여 있으니, DB를 바꾸거나 로직만 따로 테스트하기가 어렵다. 이 방향을 뒤집자는 게 헥사고날(포트-어댑터) 구조다. 도메인이 가운데 있고, DB나 외부 API는 **바깥에서 꽂히는 부품**이 된다.

```java
// 도메인이 정의하는 규격(포트) — JPA를 모른다
public interface OrderRepository {
    Order findById(Long id);
    void save(Order order);
}

// 바깥에서 구현(어댑터)
@Repository
class JpaOrderRepository implements OrderRepository { ... }
```

## DDD와 전술 패턴

계층형으로 짜다 보면 흔히 이런 코드가 나온다.

```java
@Service
class OrderService {
    public void cancel(Long orderId) {
        Order order = repository.findById(orderId);
        if (order.getStatus() == SHIPPED) throw new IllegalStateException();
        if (order.getCreatedAt().isBefore(LocalDate.now().minusDays(7))) throw ...;
        order.setStatus(CANCELED);
        order.setCanceledAt(LocalDateTime.now());
    }
}
```

엔티티는 데이터만 담고(**빈약한 도메인 모델**), 규칙은 전부 서비스에 있다. 문제는 "주문을 취소할 수 있는 조건"이 이 메서드 안에만 있다는 것이다. 다른 곳에서 취소하면 규칙이 통째로 빠진다.

DDD는 **규칙을 그 규칙이 지켜야 할 데이터 옆에 두자**는 발상이다.

```java
@Entity
public class Order {
    public void cancel() {
        if (status == SHIPPED) throw new AlreadyShippedException();
        if (createdAt.isBefore(LocalDate.now().minusDays(7))) throw new TooLateException();
        this.status = CANCELED;
        this.canceledAt = LocalDateTime.now();
    }
}
```

이제 서비스는 흐름만 조율한다. **주문을 취소하는 방법은 세상에 하나뿐**이 된다.

### 전술 패턴

DDD가 제안하는 구성 요소들인데, 실무에서 실제로 쓰이는 건 몇 개다.

**엔티티** — 식별자로 구분되는 것. 이름과 주소가 바뀌어도 회원 ID가 같으면 같은 회원이다.

**값 객체** — 값 자체로 구분되는 것. 식별자가 없고 바뀌지 않는다.

```java
public record Money(BigDecimal amount, Currency currency) {
    public Money add(Money other) {
        if (!currency.equals(other.currency)) throw new CurrencyMismatchException();
        return new Money(amount.add(other.amount), currency);
    }
}
```

`int price` 대신 `Money price`를 쓰면 **통화가 다른 금액을 더하는 실수가 컴파일 시점이나 명확한 예외로 잡힌다.** 값 객체는 도입 비용이 낮고 효과가 커서 가장 먼저 써볼 만하다.

**애그리거트** — 항상 함께 바뀌어야 하는 것들의 묶음이고, 그 대표를 **애그리거트 루트**라고 한다. 주문과 주문상품이 대표적이다. 바깥에서는 항상 루트를 통해서만 접근한다.

```java
order.addItem(product, quantity);   // O — 루트를 통해 총액 재계산까지 보장
orderItemRepository.save(item);     // X — 주문 총액이 안 맞게 됨
```

**중요한 점**: 애그리거트는 **트랜잭션의 경계**이기도 하다. 한 트랜잭션에서는 애그리거트 하나만 바꾸는 게 원칙이고, 여러 개를 동시에 바꿔야 한다면 그건 경계를 잘못 그었거나 이벤트로 나눠야 할 신호다.

**리포지토리** — 애그리거트 단위로 저장하고 꺼내는 창구. 애그리거트 루트마다 하나씩 둔다.

**도메인 서비스** — 어느 한 엔티티에 넣기 애매한 규칙. 환전이나 계좌 이체처럼 둘 이상에 걸친 것들이다. 다만 이걸 남발하면 다시 빈약한 도메인 모델로 돌아간다.

**중요한 점**: DDD의 진짜 핵심은 이 패턴들이 아니라 **유비쿼터스 언어**다. 기획자가 "환불"이라고 부르는 걸 코드에서도 `refund()`라고 쓰는 것. 용어가 어긋나면 회의 때마다 번역이 필요하고, 그 번역 과정에서 버그가 생긴다.

**중요한 점**: DDD가 항상 정답은 아니다. **규칙이 거의 없는 CRUD 화면**에 애그리거트와 값 객체를 다 갖추면 코드만 늘어난다. 도메인 규칙이 복잡하고 자주 바뀌는 영역에만 쓰는 게 맞다.

## 마이크로서비스 아키텍처

하나의 큰 애플리케이션(모놀리스)을 독립적으로 배포 가능한 여러 서비스로 쪼개는 것이다.

```
모놀리스                    마이크로서비스
┌──────────────┐           ┌──────┐ ┌──────┐ ┌──────┐
│ 주문 회원 결제 │           │ 주문  │ │ 회원  │ │ 결제  │
│    하나의 DB  │           │  DB  │ │  DB  │ │  DB  │
└──────────────┘           └──────┘ └──────┘ └──────┘
```

**중요한 점**: 서비스마다 **DB를 따로 갖는 게 핵심**이다. 코드만 나누고 DB를 공유하면, 스키마 하나 바꿀 때 모든 서비스가 같이 배포돼야 해서 나눈 의미가 없다. 이런 걸 **분산 모놀리스**라고 하고, 모놀리스의 단점과 분산의 단점을 동시에 갖는 최악의 형태다.

경계는 기술이 아니라 **업무 단위**로 나눈다. "컨트롤러 서비스, 리포지토리 서비스"가 아니라 "주문, 배송, 정산"이다. 앞서 나온 애그리거트가 서비스 경계를 정하는 좋은 출발점이 된다.

### 나누면 생기는 문제들

DB가 나뉘면 **조인과 트랜잭션이 사라진다.** 이게 마이크로서비스 비용의 대부분이다.

주문에서 회원 이름을 보여주려면 조인 대신 API를 호출하거나 데이터를 복제해야 한다. 그리고 "주문 생성 + 결제 + 재고 차감"을 하나의 트랜잭션으로 묶을 수 없다. 그래서 **사가 패턴**을 쓴다. 각 단계를 따로 처리하고, 실패하면 앞 단계를 되돌리는 보상 작업을 실행하는 방식이다.

```
주문 생성 → 결제 완료 → 재고 차감 실패
                ↓
         결제 취소(보상) → 주문 취소(보상)
```

**중요한 점**: 이 시점에서 앞에서 정리한 것들이 전부 필요해진다. 서비스 간 호출은 외부 연동이므로 타임아웃, 재시도, 서킷 브레이커가 필수고, 재시도하려면 멱등성이 있어야 한다.

**중요한 점**: **모놀리스로 시작하는 게 대부분 옳다.** 처음에는 경계를 어디에 그어야 할지 아무도 모르고, 잘못 그은 경계를 고치는 비용은 마이크로서비스에서 훨씬 비싸다. 모놀리스 안에서 패키지로 경계를 잘 나눠두고(모듈러 모놀리스), 특정 부분이 확실히 독립적이고 별도 확장이 필요할 때 떼어내는 순서가 안전하다.

## 이벤트 기반 아키텍처

서비스가 서로를 직접 부르는 대신, **일어난 일을 알리고 관심 있는 쪽이 알아서 반응**하는 구조다.

```java
// 직접 호출 — 주문 서비스가 모든 후속 처리를 알아야 함
public void order(Order order) {
    orderRepository.save(order);
    pointService.earn(order);
    couponService.use(order);
    notificationService.send(order);   // 하나 추가될 때마다 이 코드를 고침
}

// 이벤트 — 주문 서비스는 "주문됐다"만 알림
public void order(Order order) {
    orderRepository.save(order);
    eventPublisher.publish(new OrderPlaced(order.getId(), order.getUserId()));
}
```

**중요한 점**: 새 기능이 추가돼도 **생산자 코드를 안 고친다.** 이게 이벤트 기반의 가장 큰 이점이다. 포인트 적립을 추가하려면 이벤트를 구독하는 코드만 새로 만들면 된다. 앞서 비동기 연동에서 본 이벤트와 커맨드의 차이가 여기서 구조 전체로 확장된 것이다.

**중요한 점**: 대가는 **흐름을 한눈에 못 본다**는 것이다. 주문 코드만 봐서는 뒤에 무슨 일이 일어나는지 알 수 없다. 그래서 어떤 이벤트를 누가 구독하는지 문서로 관리하고, 요청 ID를 이벤트에 실어 로그를 이어 볼 수 있게 만드는 게 중요하다(분산 추적).

**중요한 점**: 이벤트를 쓰면 **즉시 일관성을 포기하게 된다.** 주문 직후 포인트를 조회하면 아직 적립 전일 수 있다. 이걸 결과적 일관성이라 하고, 화면 설계에서 미리 감안해야 한다. 조회 결과가 잠깐 어긋나도 되는 것과 절대 안 되는 것을 구분하는 게 설계의 시작점이다.

## CQRS

Command Query Responsibility Segregation. **쓰기 모델과 읽기 모델을 분리**하는 패턴이다.

배경은 단순하다. 쓰기와 읽기는 요구사항이 정반대다. 쓰기는 규칙 검증과 정합성이 중요해서 잘 정규화된 도메인 모델이 유리하고, 읽기는 화면에 필요한 데이터를 빠르게 한 번에 가져오는 게 중요하다. 하나의 모델로 둘 다 하려니 조인이 늘고 엔티티가 비대해진다.

가장 가벼운 형태는 같은 DB를 쓰면서 **경로만 나누는 것**이다.

```java
// 쓰기 — 도메인 모델, 트랜잭션, 규칙 검증
@Transactional
public void cancel(Long orderId) {
    Order order = orderRepository.findById(orderId);
    order.cancel();
}

// 읽기 — 엔티티를 거치지 않고 화면에 맞는 DTO로 바로 조회
@Transactional(readOnly = true)
public OrderSummaryView getSummary(Long orderId) {
    return queryRepository.findSummary(orderId);   // 필요한 컬럼만 프로젝션
}
```

**중요한 점**: 이 정도만 해도 효과가 크다. 읽기가 엔티티에서 자유로워지면 N+1이나 지연 로딩 문제를 신경 쓸 필요가 없고, 필요한 컬럼만 뽑으니 앞에서 본 커버링 인덱스도 활용할 수 있다. **CQRS를 무겁게 이해할 필요가 없다는 게 여기 있다.**

더 나아가면 저장소 자체를 분리한다. 쓰기는 RDB에 하고, 이벤트를 받아 읽기 전용 저장소(엘라스틱서치, 비정규화된 조회 테이블)를 갱신하는 형태다.

```
[쓰기] Order 저장 → OrderPlaced 이벤트 → [읽기] 조회용 테이블 갱신
```

**중요한 점**: 저장소를 분리하면 **읽기 모델이 항상 조금 늦는다.** 앞의 결과적 일관성 문제가 그대로 온다. 주문하고 목록으로 돌아갔는데 방금 주문이 안 보이는 상황을 어떻게 처리할지 정해야 한다.

**중요한 점**: 저장소 분리는 **읽기 부하가 쓰기보다 압도적으로 클 때** 의미가 있다. 그렇지 않다면 같은 DB 안에서 경로만 나누는 수준에서 멈추는 게 낫다. CQRS를 도입했다가 동기화 코드가 도메인 로직보다 복잡해지는 경우가 흔하다.

**중요한 점**: CQRS는 이벤트 소싱과 자주 같이 언급되지만 **별개 개념**이다. 이벤트 소싱은 현재 상태 대신 변경 이력을 저장하는 방식이고, CQRS 없이도 쓸 수 있다. 둘을 한 세트로 오해해서 필요 이상으로 어렵게 시작하는 경우가 많다.
