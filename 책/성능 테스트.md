# 성능 테스트 정리

## 성능 테스트 종류

목적에 따라 부하를 주는 모양이 다르다. 이름은 비슷해 보여도 알고 싶은 게 서로 다르다.

**부하 테스트(Load Test)** — 예상되는 정상 트래픽을 주고 **목표를 만족하는지** 확인한다. "동시 사용자 500명에서 응답시간 200ms 이내"를 검증하는 것. 가장 기본이고 가장 자주 한다.

**스트레스 테스트(Stress Test)** — 부하를 계속 올려서 **어디서 무너지는지** 찾는다. 목표는 통과가 아니라 한계를 아는 것이다. 어느 지점에서 응답시간이 급격히 꺾이는지, 무엇이 먼저 터지는지(CPU인지 커넥션 풀인지)를 본다.

**스파이크 테스트(Spike Test)** — 트래픽을 한순간에 몇 배로 올린다. 티켓 오픈이나 광고 노출처럼 갑자기 몰리는 상황을 재현한다. 서서히 올릴 때는 버티던 시스템이 급증에는 무너지는 경우가 많다. 오토스케일링이 따라오기 전에 이미 죽기 때문이다.

**내구성 테스트(Soak Test)** — 보통 수준의 부하를 **몇 시간~며칠** 유지한다. 짧은 테스트로는 절대 안 보이는 문제를 찾는 게 목적이다. 메모리 누수, 커넥션 누수, 디스크가 차오르는 문제, 캐시가 계속 커지는 문제가 여기서 드러난다.

**중요한 점**: 이 순서대로 하는 게 좋다. 부하 테스트로 기준을 만족하는지 보고 → 스트레스로 한계를 알고 → 스파이크와 내구성으로 특수 상황을 검증한다. 한계를 모르는 상태에서는 알람 임계치도 정할 수 없다.

## 성능 지표

무엇을 측정할지 정하지 않으면 테스트해도 해석이 안 된다.

**처리량(Throughput)** — 초당 몇 건을 처리하는가. TPS, RPS로 표기한다.

**응답 시간(Latency)** — 한 요청이 얼마나 걸리는가.

**동시 사용자(VU)** — 동시에 요청을 보내는 가상 사용자 수.

이 셋은 독립적이지 않고 **리틀의 법칙**으로 묶여 있다.

```
동시 사용자 수 = 처리량 × 응답 시간
```

예를 들어 응답 시간이 0.2초인 시스템에서 초당 500건을 처리하려면 동시 사용자 100명이 필요하다. 거꾸로 응답 시간이 2초로 늘어나면 같은 100명으로는 초당 50건밖에 안 나온다. **응답 시간이 나빠지면 처리량도 같이 무너진다**는 게 이 식에 들어 있다.

**중요한 점**: **평균 응답 시간은 거의 쓸모가 없다.** 100건 중 99건이 50ms이고 1건이 5초여도 평균은 99ms다. 그런데 그 1건을 겪은 사용자는 서비스가 고장 났다고 느낀다. 그래서 **백분위(p95, p99)** 를 본다.

```
p95 = 300ms   → 100명 중 95명은 300ms 안에 응답받았다
p99 = 2.1s    → 100명 중 1명은 2.1초 넘게 기다렸다
```

**중요한 점**: p99가 특히 중요한 이유는 한 페이지가 여러 API를 부르기 때문이다. 한 화면에서 API를 20개 호출하면 **그중 하나가 p99에 걸릴 확률은 18%**다. 개별 요청 기준으로는 드문 일이 사용자 기준으로는 흔한 일이 된다.

**에러율을 반드시 같이 본다.** 부하를 올렸을 때 응답 시간이 좋아 보이는 경우가 있는데, 알고 보면 절반이 에러로 즉시 실패하고 있어서 그런 것이다. 성공한 요청만 놓고 재면 시스템이 멀쩡해 보인다.

## 테스트 설계 고려사항

### 목표부터 정한다

"빨라야 한다"는 목표가 아니다. 숫자로 적을 수 있어야 한다.

```
동시 사용자 1,000명 기준
- 주문 API p95 < 500ms
- 조회 API p95 < 200ms
- 에러율 < 0.1%
```

기준이 없으면 결과를 봐도 통과인지 실패인지 판단할 수 없다.

### 시나리오는 실제 사용 패턴을 따른다

특정 API 하나만 두들기는 건 그 API의 한계만 알려줄 뿐 실제 상황을 재현하지 못한다. 실제 사용자는 여러 API를 섞어서 부른다.

```
조회 70% : 검색 20% : 주문 10%
```

**중요한 점**: 사용자는 요청 사이에 생각하고 화면을 읽는다. 이 간격(**Think Time**)을 안 넣으면 현실보다 훨씬 가혹한 부하가 된다. 반대로 이걸 빼먹고 "동시 사용자 100명도 못 버틴다"고 결론 내리는 실수가 흔하다.

### 테스트 데이터가 결과를 좌우한다

**중요한 점**: 데이터가 100건인 DB와 1,000만 건인 DB는 완전히 다른 시스템이다. 100건이면 인덱스가 없어도 빠르다. **운영과 비슷한 규모의 데이터를 넣고 테스트해야** 의미가 있다.

**중요한 점**: 같은 데이터만 반복 조회하면 캐시에 다 올라가서 실제보다 훨씬 좋은 숫자가 나온다. 조회 대상을 흩어야 한다.

```javascript
// 나쁨 — 캐시에 한 건만 올라감
http.get('https://api.example.com/products/1');

// 좋음 — 실제처럼 흩어짐
const id = Math.floor(Math.random() * 100000) + 1;
http.get(`https://api.example.com/products/${id}`);
```

### 환경은 최대한 운영과 같게

**중요한 점**: 사양이 다르면 결과를 운영에 대입할 수 없다. 특히 DB 사양과 인스턴스 개수가 다르면 아예 다른 결과가 나온다. 완전히 같게 못 만든다면 **최소한 어떤 차이가 있는지 기록해두고 해석에 반영**해야 한다.

## 성능 테스트 도구

**k6** — 자바스크립트로 시나리오를 쓰고, Go로 만들어져 가볍다. 코드로 관리하고 CI에 넣기 좋아서 요즘 가장 무난한 선택이다.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 100 },   // 1분 동안 100명까지 서서히 증가
    { duration: '3m', target: 100 },   // 3분 유지
    { duration: '1m', target: 0 },     // 서서히 감소
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],  // p95가 500ms 넘으면 실패
    http_req_failed: ['rate<0.01'],    // 에러율 1% 넘으면 실패
  },
};

export default function () {
  const res = http.get('https://api.example.com/products/1');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);                            // Think Time
}
```

**JMeter** — 자바 기반의 오래된 표준. GUI로 만들 수 있어 진입 장벽이 낮고 자료가 많다. 대신 무겁고 시나리오가 XML이라 코드 리뷰가 어렵다.

**Gatling** — 스칼라/자바 DSL로 작성한다. 성능이 좋고 리포트가 훌륭하다.

**nGrinder** — 네이버에서 만든 도구. 여러 대에 분산 부하를 주는 구성이 편하다.

**wrk / ab** — 단일 URL을 빠르게 때려보는 용도. 시나리오는 못 짜지만 간단한 확인에는 이게 제일 빠르다.

```bash
wrk -t4 -c100 -d30s https://api.example.com/health
```

**중요한 점**: 도구 선택보다 중요한 건 **시나리오를 코드로 관리하고 CI에서 자동 실행**하는 것이다. 성능 테스트는 한 번 하고 끝내는 이벤트가 아니라, 배포마다 회귀를 잡아내는 안전망일 때 가치가 있다.

**중요한 점**: 부하 도구는 "얼마나 느린지"만 알려주고 "왜 느린지"는 안 알려준다. 반대편에서 APM(Pinpoint, Scouter, Datadog)이나 최소한 지표 모니터링을 같이 봐야 원인을 짚을 수 있다.

## 실행 주의사항

### 워밍업 없이 측정하지 않는다

JVM은 처음에 인터프리터로 실행하다가 자주 쓰이는 코드를 기계어로 컴파일한다(JIT). 그래서 **시작 직후 몇 분은 원래 느리다.** 여기에 커넥션 풀 초기화, 캐시 적재, JPA 메타데이터 로딩까지 겹친다.

이 구간을 포함해서 재면 실제보다 나쁜 숫자가 나온다. **부하를 서서히 올리고(램프업), 초반 구간은 통계에서 제외**한다.

### 부하 생성기가 먼저 죽는 경우

**중요한 점**: 이게 정말 흔한 함정이다. 테스트 도구를 돌리는 컴퓨터의 CPU나 네트워크, 파일 디스크립터가 먼저 한계에 걸려서 **서버가 아니라 도구가 병목이 되는** 것이다. 그러면 서버는 여유로운데 응답 시간이 나쁘게 나온다.

부하 생성기 쪽 CPU와 네트워크 사용률을 항상 같이 봐야 하고, 노트북에서 돌리는 테스트는 특히 의심해야 한다. 필요하면 여러 대로 나눠서 부하를 준다.

### 병목은 한 번에 하나씩 옮겨간다

성능 테스트의 결과는 보통 이런 식으로 흐른다.

```
1차: 커넥션 풀 10개가 한계 → 30개로 증설
2차: 이번엔 CPU가 100% → 쿼리 튜닝
3차: 이번엔 외부 API가 느림 → 캐시 도입
```

**중요한 점**: **한 번에 하나씩만 고친다.** 여러 개를 동시에 바꾸면 무엇이 효과를 냈는지 알 수 없고, 심지어 하나가 개선되고 하나가 악화돼서 상쇄되는 경우도 구분할 수 없다.

병목은 사라지는 게 아니라 **다음 지점으로 이동한다.** 앞에서 가상 스레드를 켜면 병목이 DB 커넥션 풀로 옮겨간다고 했던 것과 같다. 그래서 "어디까지 개선할 것인가"를 목표 지표로 정해두지 않으면 끝없이 이어진다.

### 운영 환경에 영향을 주지 않는다

**중요한 점**: 운영 DB를 바라보는 상태로 테스트를 돌리면 실제 사용자가 피해를 본다. 그리고 테스트가 만든 주문 데이터가 정산이나 통계에 섞이는 사고도 흔하다. 환경 분리를 먼저 확인해야 한다.

외부 연동이 있다면 더 조심해야 한다. 결제나 알림 API에 부하 테스트를 그대로 흘리면 **상대방 서비스를 공격하는 것**이 되고, 실제 요금이 청구되거나 계정이 차단될 수 있다. 이런 구간은 반드시 모의 서버로 대체한다.

클라우드 환경에서는 **부하 테스트 전에 사전 고지가 필요한 경우**가 있다. 갑작스러운 대량 트래픽이 공격으로 탐지되어 차단될 수 있다.

### 결과는 조건과 함께 기록한다

숫자만 남기면 나중에 비교가 안 된다. 서버 사양, 데이터 규모, 시나리오 비율, 테스트 시각, 그때의 커밋 해시까지 같이 남겨야 **다음 테스트와 비교**할 수 있다. 비교할 수 없는 성능 수치는 기록해도 쓸모가 없다.
