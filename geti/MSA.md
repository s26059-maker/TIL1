## Monolithic

모든 기능이 하나의 코드베이스, 하나의 배포 단위로 묶인 구조. 회원가입, 결제, 주문 같은 기능이 전부 한 프로젝트 안에 같이 들어있다. 개발 초기엔 빠르고 간단하지만, 커질수록 배포할 때 전체를 다 내렸다 올려야 하고 코드 하나 잘못 건드리면 전체 서비스가 다 죽을 수 있다.

## MSA (Microservice Architecture)

큰 애플리케이션을 독립적인 여러 서비스로 쪼갠 구조. 회원 서비스, 결제 서비스, 주문 서비스가 각각 따로 배포되고 따로 돌아간다. 결제 서비스에 버그가 나도 회원가입은 멀쩡하게 동작한다. 대신 서비스끼리 통신해야 하니 복잡도가 올라간다.

중요한 점: MSA는 무조건 좋은 게 아니라 트레이드오프다. 서비스가 많아질수록 관리 포인트, 네트워크 통신, 장애 지점도 같이 늘어난다.

## Bounded Context

도메인마다(=업무 영역마다) 같은 단어라도 뜻이 다르게 쓰일 수 있다. 예를 들어 "주문"이 배송팀 입장에서는 "보낼 물건"이고 결제팀 입장에서는 "돈 받을 건"이다. 이렇게 맥락(Context)별로 모델과 용어를 분리해서 관리하는 개념이 Bounded Context다.

## Service Boundary

서비스를 어디까지 쪼갤지 정하는 책임 경계선. 이걸 잘못 그으면 서비스 하나 고치려는데 다른 서비스 코드까지 같이 고쳐야 하는 상황이 생긴다. 보통 Bounded Context가 그대로 Service Boundary가 된다.

## Data Ownership

각 서비스가 자기 데이터의 유일한 주인이 되는 원칙. 회원 서비스만 회원 테이블을 만지고, 다른 서비스가 직접 그 테이블에 접근하면 안 된다. 남의 데이터가 필요하면 그 서비스한테 요청해서 받아와야지 직접 손대면 안 된다.

## Database per Service

Data Ownership을 실제로 지키기 위한 방법. 서비스마다 DB를 아예 따로 둔다. 회원 서비스는 회원 DB, 주문 서비스는 주문 DB, 이런 식으로 나누면 한 서비스의 DB 스키마를 바꿔도 다른 서비스가 영향을 안 받는다.

## REST 통신

서비스끼리 데이터를 주고받는 방법 중 하나. HTTP 메서드(GET, POST, PUT, DELETE)로 자원을 주고받는다. 주문 서비스가 회원 정보가 필요하면 회원 서비스한테 GET 요청을 보내서 받아온다.

중요한 점: 이 통신은 네트워크를 타기 때문에 모놀리식처럼 메서드 하나 호출하는 것보다 느리고, 실패할 수도 있다는 걸 항상 고려해야 한다.
